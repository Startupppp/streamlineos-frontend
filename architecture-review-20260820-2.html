Row two is the tell: its entire cost is the guard chain. Tuple volume is inflated by re-parse/re-plan catalog reads, because prepared statements are disabled for the Neon pooler — deliberately, so the lever is fewer statements, not statement reuse.

Problem

Five modules and ~24,600 lines answer "may this person do this", and no single one owns establishing tenant context. So every request pays for three or four separate transactions before the handler runs — on every endpoint, for every user.

Solution

Establish tenant context once at the earliest point in the request and have guards reuse it. One transaction per request, with a test asserting the ceiling so it cannot regress.

Wins

  • Locality: tenancy established in one place
  • Every endpoint gets faster
  • Database compute billed goes down
  • Cost stops scaling with module count

2 · The module ladder reaches 10 of 18 modules

Strong

Returns not-found — no ladder at all

Chat, Mail and Calendar are phase-one surfaces.

Problem

Your model says every module except Home and Knowledge Base gets an owner who appoints admins and members and authors grants. Eight modules can only be run by an org admin — there is no middle rung, so delegating them means over-privileging.

Solution

The API is already generic on the module key and the web app is already one shared screen with thin per-module routes. Adding the eight is configuration plus a resolver that answers standing in one question instead of two.

Owner is a lifecycle record; admin is a ranked role assignment. Two storage shapes for two rungs of one ladder — which is why nothing forced a new module to acquire both. Unify the resolution, not the storage: the ten working modules then aren't migrated. Detailed in the PRD.

Problem

An untyped entity pair on the channel, a hard deal FK beside it, and free-form message metadata all describe "this points at that". The only actions are four Build endpoints importing Build's tables directly. Sharing a lead or an employee means writing that controller again.

Solution

One interface: resolve returns a card or nothing when the reader lacks access; actionsFor returns what this actor may do. Each module registers an adapter.

Security, not style. An unfurled ticket renders from metadata captured at send time. A reader who lost access still sees it in scrollback. Resolving at read time degrades it to "a ticket you can't see".

5 · AI model choice is two global tiers, not per-task routing

newWorth exploring
  • modules/ai/core/providers/llm-provider.config.ts · gateway/ai-gateway.service.ts

Before — one provider, two tiers, globally

fastModel = gpt-4o-mini
standardModel = gpt-4o

Every feature — HR summaries, CRM copilot, KB retrieval, chat assistant, blog drafting — picks one of two. Provider is a single global switch.

After — a routing policy keyed by feature

ModelRouting

routeFor(feature) → { provider, model, chain, cap }

kb.retrieval → cheap
hr.summary → cheap
crm.copilot → standard
payroll.explain → strongest

Problem

You asked for each task to be able to use a different provider and model so the cheapest reliable one wins. Today that decision is two constants shared by every AI feature, so a trivial classification and a payroll explanation pay the same rate.

Solution

A routing module mapping feature to provider, model, fallback chain and output cap. The gateway already meters tokens per call, so cost per feature becomes measurable — and tunable — rather than assumed.

Wins

  • Cost per feature becomes visible
  • Locality: model policy in one module
  • Swap a provider without touching features
  • Cheap tier for the many, strong for the few

8 · Two rich-text stacks — but this one contradicts a written decision

Speculative
  • components/editor/tiptap-editor.tsx · components/editor/plate/** (24 files)

⚠ Contradicts a documented decision — but worth reopening because you raised it directly.

The project rules explicitly sanction two stacks: simple fields (tickets, blog, comments) extend Tiptap; Notion-style surfaces (the KB wiki) use Plate. You asked for one editor maintained in one place, with props for the differences. Those are incompatible positions and only you can settle it.

The case for keeping both

A comment box and a Notion-style document editor have genuinely different interfaces — block handling, slash menus, drag reordering and collaborative structure only exist in one of them. Collapsing them yields a single component with two disjoint prop sets, which is a shallow module wearing one name.

The case for collapsing

Two stacks means two toolbars, two serialisation formats, two upload paths and two sets of bugs — and content authored in one may not render in the other. If documents and tickets should share content, one stack is the only way.

My read: keep both, but unify what actually should be shared — the serialisation format and the upload path — so content is portable even though the editing surfaces differ. That is a smaller, safer change than one editor.

Top recommendation

Do this first

1 · One tenant context per request

It is the only candidate that makes every other one cheaper. Authorization runs on every request, currently costs three to four transactions, and the module ladder is about to add eight more modules on top of it. Fixing the path first means the ladder rides something cheap; fixing it second means optimising a larger surface. It also directly serves the database bill, which you named as a goal.

Then, in order

2 · the ladder across all 18 modules — 3 · the list-view module, which fixes filters across HRMS, Payroll and Build at once — 4 · the reference seam, after which chat sharing is additive per module.

Where the architecture is genuinely healthy

  • Zero circular dependencies in both repos — verified with a module-graph tool, not asserted.
  • Tenant isolation has real depth: RLS policies are live, and they caught a missing application predicate during this review.
  • The module-access API and web screen are already generic, which is why the ladder is additive rather than a rebuild.
  • The permission catalog has a working parity guard, in the direction that matters.
  • Schema hardening is real — composite tenant keys, soft delete, row versions and actor FKs are widespread.
