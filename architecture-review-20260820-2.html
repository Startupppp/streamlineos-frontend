1 · Authorization pays a round trip per request — but not for the reason given

re-specifiedStrong
  • modules/access/access.service.ts:72 · common/rbac/access-invalidate.ts · common/auth/membership-state.service.ts
  • common/tenant/tenant-context.interceptor.ts · common/auth/jwt-auth.guard.ts · common/rbac/module.guard.ts

Why the original fix cannot be built

“Establish tenant context once at the earliest point and have guards reuse it” asks for three things the framework does not offer at once.

Nest's request lifecycle — the order is fixed

middleware
→
guards
→
interceptors
→
pipes
→
handler
  • Interceptors run after guards. TenantContextInterceptor is registered as an APP_INTERCEPTOR; a guard can never reuse a context it establishes.
  • Middleware runs early but knows nothing. The tenant id comes from a verified JWT and a membership row — both resolved inside JwtAuthGuard. There is no “earliest point” at which orgId is already known.
  • db.transaction(cb) is callback-scoped. It cannot be opened in a guard and closed after the handler. Spanning that boundary means hand-managing a borrowed connection and a manual BEGIN/COMMIT, with a filter to roll back — a different and far riskier change than the card implied.
  • It would not have removed the cost. Sharing one transaction removes the BEGIN/SET LOCAL/COMMIT envelope. The queries inside it — version, membership, entitlement, permission set — all still run.

The root cause the original missed, named exactly

modules/access/access.service.ts:72

const VERSION_CACHE_TTL_MS = 5_000;

getPermissionsVersion() is the first line of resolveUserPermissions(), which runs on every permission-checked request. On a miss it opens a full tenant transaction to read a single integer. The cache holding it lives five seconds.

common/rbac/access-invalidate.ts:10

const versionBumpListeners =
  new Set<VersionBumpListener>();

The invalidation channel is a module-level Set, notified synchronously in the same process. There is no cross-process channel. A grant changed on instance A never reaches instance B.

Put those two facts together and the five seconds stops being a tuning constant. It is the only mechanism by which a revoked permission propagates between instances. That is why it is so short, and it is why nobody could simply raise it. The transaction-per-request is not caused by five modules and 24,600 lines — it is caused by polling a database for cache coherence that a push channel should be delivering.

The TTL becomes a backstop rather than the mechanism, so it can be minutes. Warm requests stop touching the database at all — strictly better than sharing a transaction, which still runs the query.

The corrected solution, in two stages that must land in this order

1

Give the version bump a cross-process channel, then lengthen the TTL.

Promote access-invalidate.ts from an in-process Set to a module with one interface — publish(orgId) / subscribe(fn) — backed by Redis, with the in-process set as the local fan-out behind it. Only then raise VERSION_CACHE_TTL_MS. Doing it the other way round is a security regression, not an optimisation: it lengthens the window in which a revoked grant is still honoured.

Small, isolated, reversible. Removes most of the per-request cost on its own. This is the whole recommendation if you only do one thing.

2

Only if stage 1 proves insufficient: a request-scoped unit of work.

Middleware opens a lazily-borrowed connection and stores a handle; JwtAuthGuard calls bind(orgId) once membership resolves, which issues set_config('app.organization_id', …, true) mid-transaction — legal, because it applies for the remainder of the transaction; a terminal interceptor commits and an exception filter rolls back. The @NoTenantTransaction() escape hatch already exists and is already used by ten AI controllers, which is real evidence this is feasible.

Cost to weigh first: a pooled Neon connection is then held for the entire request, including JWT verification and every Redis call — a capacity trade, not a free win.

Noticed while verifying — one line, worth taking

Ten AI controllers carry @NoTenantTransaction(). ChatAssistantController does not, and its POST /chat handler returns the moment it calls pipeTextStreamToResponse(res) — so the request transaction commits while the stream is still running. It is not a live bug: tools are wrapped by withTenantScopedTools and onFinish uses runInNewTenantTransaction, both of which open fresh contexts. It is a latent trap — the handler's safety depends on every future tool remembering the wrapper — and it is the odd one out of eleven.

Wins

  • Locality: cache coherence in one module instead of a TTL in each
  • The interface is the test surface: “a bump on A invalidates B” becomes assertable
  • Revocation gets faster and cheaper at the same time
  • Cost stops scaling with instance count

Deletion test

Delete the proposed channel module and the polling TTLs must come back into every cache that holds an access fact — five of them in AccessService alone, plus MembershipStateService. It concentrates complexity rather than relocating it. Passes.

4 · The reference seam shipped — and the actions path did not finish crossing it

shippedWorth exploring
  • modules/entity-reference/** · modules/build/entity/** · modules/crm/entity/** · modules/chat/chat-actions.controller.ts

Built, and built well

interface EntityAdapter {
  readonly moduleKey: string;
  readonly types: readonly string[];
  resolve(actor, refs):    Promise<EntityResolution[]>;
  actionsFor(actor, refs): Promise<EntityAction[][]>;
  submitAction(actor, ref, actionId, input);
}
  • Every method takes an actor. The security property the report insisted on is in the type, so an adapter that cannot check access cannot be written.
  • Batched. Arrays in, arrays out, grouped per adapter — the N+1 an unfurl list invites is designed out.
  • Entitlement inverted. ModuleEntitlementPort is injected by symbol, so the seam does not import the access module.
  • Fails closed. An unknown type or a disabled module yields unresolved, not a leak.
  • Read-time resolution replaced send-time snapshots, and a follow-up closed the same leak in polls and thread replies (f4ba101d).

What is left — the guard still says “Build”

ChatActionsController's four handlers now call entities.submitAction() through the seam. Their decorators did not move:

POST ticket-status → build:tickets:update
POST create-task-from-message → build:tickets:create
POST assign-ticket → build:tickets:assign
POST set-due-date → build:tickets:update

So the seam can resolve a CRM deal into a chat bubble, but the moment someone wants to act on one, the route is gated on a Build permission and named after a Build noun. The adapter already authorises the actor internally; the guard-level key is a second gate that only ever narrows to the wrong module. The report's “four endpoints, Build only” is still literally true at the routing layer — the body changed, the door did not.

Finish it: one endpoint — POST /chat/actions { reference, actionId, input } — gated on chat membership, with the module permission enforced where it already is, inside the adapter. Then adding an HR or Accounting action is registering an adapter, which is what the seam was for.

Top recommendation — revised

Do this first

1 · Give the access-version bump a cross-process channel

Same candidate as before, different change. The original said “one tenant context per request”, which the framework will not allow and which would have left every guard query in place anyway. The actual lever is that VERSION_CACHE_TTL_MS = 5_000 is doing a job it was never meant to do: it is the only way a permission change on one instance reaches another. Replace that with a push channel and the guard chain's warm path stops touching the database — and revocation gets faster at the same time, which is the rare case where the security fix and the cost fix are the same commit.

Order matters and is not negotiable: the channel lands first, the TTL lengthens second. Reversed, it is a window in which revoked grants are still honoured.

Then, in order

9 · the module registry — it is small, and both C2's ghost and a past production bug are symptoms of its absence — 3 · lift Build's filter family out of Build, which fixes filters across HR, Payroll and Inventory without new behaviour — 4 · finish the reference seam's actions path so the second consumer can exist — 7 · the config seam, with the lint rule, or it will not hold.

Where the architecture is genuinely healthy — re-checked

  • The tenant boundary is deep. withTenant sets the GUC, the ALS-routed Drizzle proxy makes 557 non-transactional service files inherit it, and RLS denies anything that escapes. Three layers, and the outermost fails closed.
  • The escape hatches are documented and used correctly. withIdentity for the pre-tenant sign-in phase, runInNewTenantTransaction for background work, withTenantScopedTools for streaming — each with a comment explaining the failure it prevents.
  • The entity-reference seam is the best module in the tree. Actor in the type, batched, entitlement inverted by symbol, fails closed.
  • Refusals are recorded. The Home ladder being built and then retired on a rule, rather than kept because it was written, is the healthiest signal in the commit log.
  • The permission catalog is a folder with a parity guard, in the direction that matters.

What I could not verify, and did not restate as fact

  • Zero circular dependencies. madge is not a dependency of either repo, so the claim cannot be re-proven with the tooling in the tree. Installing it is a one-line change and would make a constitutional rule enforceable again.
  • Tests and lint were not run, per the standing instruction — reported as not run, never as passing.
