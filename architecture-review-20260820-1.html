Problem

Three unrelated mechanisms describe “this chat thing points at that business thing”: an untyped entityType/entityId pair on the channel, a hard linkedDealId FK next to it, and free-form metadata.entities on the message. The only actions that exist are four Build endpoints that import tickets, projects and project_members schema directly — cross-module access through another module's tables, which §1 forbids. Adding leads or HRMS records means writing that controller again per module.

Solution

One module, one interface: resolve returns a display card or null when the reader lacks access; actionsFor returns the actions this actor may take. Each product module registers an adapter.

Security note, not a style note. Today an unfurled ticket is rendered from metadata.entities, captured at send time. A reader who never had — or has since lost — build:tickets:view still sees it in scrollback. resolve() re-asserts object-level access at read time, so the reference degrades to “a ticket you can't see” instead of leaking its title.

Wins

  • Leverage: one interface, every module
  • Chat stops importing Build schema
  • Access re-checked at render, not send
  • Two adapters justify the seam on day one
  • Mentions, unfurls and slash-actions share it
  • Delete the polymorphic pair and linkedDealId

Problem

The frontend's runtime PERMISSIONS array — what a module owner picks from when granting a permission — is 206 keys short of the backend catalog. And the resolver silently drops any stored grant whose key is unknown (access-permission.resolver.ts:160 mergeIfKnown): a grant can be saved, shown as saved, and never take effect.

Solution

Backend catalog is the module. The frontend key union is generated from it in CI; the picker reads the live endpoint. Delete the hand-maintained PERMISSIONS array.

This is also where your module-owner model is only two-thirds built

ACCESS_MANAGED_MODULES lists hr, crm, build, accounting, inventory, support, surveys, payroll, sign, timesheets. You said every module except Home and Knowledge Base should have owner/admin/member and owner-authored permissions. Chat, Mail, Calendar, Notifications, Blog, Workflows, Directory and Billing have no per-module access surface at all — assertKnownModule 404s them.

Module admin is a rank-20 role assignment (module-access.helpers.ts:77) while module owner is a module_ownerships row — two different storage mechanisms for two rungs of one ladder, which is why the ladder only exists in ten modules.

Wins

  • Drift becomes a compile error
  • Module owners can grant all 631 keys
  • Silent grant-drop stops
  • Owner/admin/member ladder reaches every module

Top recommendation

Fix first, this week

1 · The Chat tenancy seam is severed

Not an architecture preference — chat_messages.org_id is NOT NULL in the database and absent from the Drizzle schema and both inserts. Chat can't accept a message, and the next db:generate would propose dropping the column from eight tables. Everything else on this page can wait behind it.

Deepen first, before building on it

2 · The EntityReference seam

You want to share tickets, leads and HRMS records in chat. Today that means a fourth mechanism and a second controller that imports another module's tables. One interface — resolve + actionsFor — with one adapter per module gives you every combination, re-checks access at read time, and is the same seam Knowledge Base, notifications and calendar will need.

Suggested order for a phase-one release

  1. C1 — chat tenancy + the scale items, while the tables are being rewritten
  2. C3 — one catalog; unblocks module owner/admin/member on every module
  3. C4 — route registry; makes “sidebar shows what I can open” true by construction
  4. C5 — list-view module; fixes the filter overflow across all of HRMS, Payroll and Build at once
  5. C2 — EntityReference seam; then chat sharing is additive per module
  6. C7 — config sweep; mechanical, can run in parallel
  7. C6 — person consolidation; needs your decision on whether it precedes or follows the release
