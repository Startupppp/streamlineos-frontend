# contracts/

Vendored API contract for build-time drift detection (`scripts/check-contract-drift.mjs`).

## openapi.json

Generated by the backend and checked in here so the frontend CI can compare its hook types against the real Zod schemas without booting the API.

**To vendor after a backend change:**

```bash
pnpm --filter streamlineos-api openapi:generate
cp backend/openapi.json frontend/contracts/openapi.json
```

The check fails with a clear actionable message if this file is absent.

## __fixtures__/

`timesheets-fixture.json` — a hand-crafted subset of real timesheets operations (derived from `backend/src/modules/timesheets/**/*.controller.ts` and their `dto/*.schemas.ts`). Used by `--use-fixture` to demonstrate drift rules against request body schemas. It is a partial contract — not all paths are present — so running against it produces path violations and may produce stale-baseline warnings for entries that only appear in the real contract.

## What the check detects (timesheets module)

1. A path the frontend calls that the contract does not contain — renamed or deleted endpoint.
2. A method mismatch on a known path.
3. A request-body field the frontend sends that the contract's schema does not list in `properties` — silently stripped by Zod; the mutation has no effect.
4. A `required` field the contract demands that the frontend never sends — backend returns 400 every time.
5. An enum member the frontend can send that the contract's schema does not include — the value is silently rejected.

Narrowings (contract allows values the frontend type does not use) are reported as informational, not failures.

## Resolution floor

The check prints `body resolved: N` on every run and fails if the resolved fraction drops below 40%. A drop signals a refactor broke the body-type extractor.

## KNOWN_DRIFT baseline

`KNOWN_DRIFT` in `scripts/check-contract-drift.mjs` is a dated list of confirmed frontend/backend disagreements that are not yet resolved because they depend on a product decision. The baseline exists so CI does not fail every commit while that decision is pending.

**These are NOT accepted behaviour.** Each entry is an unfixed defect with a `since` date, a specific endpoint+field+offending-members identity, and a `reason` stating exactly what decision is blocking the fix. The baseline is printed in full on every run so no CI pass can hide the existence of these defects.

**The check enforces two invariants:**
- A violation whose identity matches a baseline entry is reported but does not fail CI.
- A baseline entry that no longer matches any actual violation fails CI and instructs the reader to delete the entry. This ensures the list cannot silently re-permit a defect that someone already fixed.

**A violation on the same endpoint with a different enum member or a new field is NOT baselined** — it produces a new failure. Matching is exact: `type + endpoint + field + sorted offending members`. A partial change (e.g. the fix removes one member of a multi-member drift) produces a new violation string that does not match the old key, so it is caught.

### Removing a baseline entry

Once the product decision lands and either the frontend type or the backend schema is corrected:

1. Fix the source of the disagreement (frontend `types.ts` or backend `dto/*.schemas.ts`).
2. Run `node scripts/check-contract-drift.mjs` to confirm the violation no longer appears.
3. Delete the corresponding entry from `KNOWN_DRIFT` in `scripts/check-contract-drift.mjs`.
4. Run again — the stale-baseline guard will fail if you leave the entry after the fix.

### Adding a baseline entry

Adding a `KNOWN_DRIFT` entry is a deliberate act that requires the same evidence and decision process as removing one. An entry must carry:
- The exact `type`, `method`, `path`, `field`, and `offendingMembers` that appear in the violation output.
- A `since` date.
- A `reason` that names the specific product question blocking the fix — not a generic placeholder.

Do not add an entry to silence a CI failure without first understanding and documenting what decision needs to be made. An undocumented entry is a blindfold, not a ratchet.

## Commands

```bash
node scripts/check-contract-drift.mjs              # check against vendored openapi.json
node scripts/check-contract-drift.mjs --use-fixture # check against the hand-crafted fixture
node scripts/check-contract-drift.mjs --self-test   # run 16 in-memory cases, exit 0 if all pass
```
