# Authentication Architecture

## NextAuth-as-Adapter Pattern

NextAuth is kept as a thin session cookie manager. All auth business logic runs in the NestJS backend.

```
Browser → NextAuth (credentials provider)
  authorize() → POST /api/auth/login (NestJS backend)
  → validates credentials, subscription, creates session
  → returns { userId, orgId, sessionId, forceChangePassword, daysUntilExpiry? }

NextAuth JWT callback:
  → fetches user profile from DB
  → caches in Redis (key: user:session:{userId}, TTL 300s)
  → stores orgId, role, permissions, plan, enabledModules in JWT cookie

Server components:
  → auth() → reads JWT cookie → returns session
  → NO additional DB queries (session is in cookie)

Client components:
  → useSession() → TanStack Query hooks → apiClient → backend API
```

## How Frontend Calls Backend

1. Protected Next.js API routes (thin proxies): `app/api/auth/**` forward to NestJS with a signed JWT
2. Direct backend routes via `MIGRATED_PREFIXES` in `lib/api-client.ts`
3. JWT for backend calls: generated by `lib/api/make-backend-token.ts` (HS256, 10 min expiry)
4. Token refresh: `apiClient` caches token, refreshes 30s before expiry via `/api/auth/backend-token`

## Session Lifecycle

```
Login → JWT cookie set (8h) → Redis cache (5m TTL)
  → Each request: cookie validated → Redis hit (fast path)
  → Cache miss: DB query → cache refreshed
  → Logout: Redis invalidated, session revoked in DB
  → Password change: all sessions revoked + Redis invalidated
```

## Key Files

| File | Purpose |
|------|---------|
| `lib/auth.ts` | NextAuth config, jwt/session callbacks |
| `lib/api/backend-proxy.ts` | Generic HTTP proxy helper |
| `lib/api/make-backend-token.ts` | Signs JWT for backend calls |
| `app/api/auth/backend-token/route.ts` | Endpoint to get backend JWT |
| `types/next-auth.d.ts` | Session/JWT type augmentation |
| `types/auth.ts` | Shared auth entity types |
| `hooks/use-feature-flag.ts` | Client-side feature flag check |
