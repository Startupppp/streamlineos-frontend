## Acceptance criteria

- [x] Verify Calendar source/event/attendee/recurrence/exception/reminder/sync models, RRULE use, timezone/DST, bounded expansion, privacy and tenant-safe relations. — **found and fixed a P0: the calendar list never expanded recurrences at all.** `calendar-event-source.loader.ts` filtered on `startDate < end AND endDate > start` with no `rrule` branch, so a series whose base occurrence ended before the window was excluded outright, and `calendar-native-event-source.ts` emitted one projection per DB *row* without calling `expandToOccurrences` or joining exceptions. A weekly all-hands showed only its first instance and then vanished — while the reminder sweep, which does expand, kept notifying attendees about meetings absent from their own calendar. Both paths now use the rrule-aware predicate already proven in `calendar-conflict.service.ts:77-93`, batch-load exceptions and expand per occurrence, capped at `CALENDAR_EVENTS_CAP`. RRULE is the `rrule` library (`RRule.fromString`/`between`), not hand-rolled; expansion is bounded at `MAX_OCCURRENCES_PER_WINDOW = 500` per event; DST round-trips through `toZonedTime`/`fromZonedTime` and `calendar-dst-edge.spec.ts` carries explicit BITE PROOF cases. Privacy holds on every read path (list, export, attendees all apply the `visibility = 'org' OR creator OR attendee` clause). Evidence: `calendar-native-source-recurrence.spec.ts` (8 tests).
- [ ] Prove free/busy/conflict/reminder/export range bounds, indexed plans, replacement/deduplication and provider-sync retry/order/tombstone/drift guarantees. — **one residue left, and it needs a product decision, not code.** PROVEN: `listEventsSchema` 120 days and `exportSchema` 366 days were already bounded; `externalEventsQuerySchema` was **unbounded**, letting any member drive Composio calls over an arbitrary span, and now enforces `end > start` and `CALENDAR_MAX_SPAN_DAYS` (121-day, reversed and 99-year ranges rejected; 90 days accepted, verified end-to-end). Reminder dedupe is `onConflictDoNothing` on `(orgId, dedupeKey)` with move/cancel tombstoning in the same transaction. **A silent truncation was fixed:** the reminder sweep read attendees with one `.limit(10_000)`, no `ORDER BY` and no continuation, so past that count a nondeterministic subset of people were never reminded — now keyset-paged with chunked inserts, bite-proven. Provider sync has monotonic `order by id`, `FOR UPDATE SKIP LOCKED` leases, 5 attempts with `[0, 30s, 120s, 600s, 1800s]` backoff, delete tombstones, and a Zod-parsed payload so a malformed row enters the retry path instead of pushing wrong data. **`synced`/`failed` status and user retry now exist** — `GET /calendar/events/:eventId/sync-status` and `POST /calendar/events/:eventId/sync-retry`, both `@Universal()` like the rest of own-calendar, authorized at the data layer by the same visibility predicate as attendee reads, with retry restricted to the event's creator exactly as `updateEvent` is; a cross-tenant or invisible id returns `NotFoundException`, never 403. The frontend consumes them: a failed sync now renders a danger-toned notice with the attempt count and a Retry control, and polls only while the status is unsettled. Indexing: `(org_id, start_date, recurrence_end) WHERE rrule IS NOT NULL` is authored as migration `0982` with a journal entry above the DB watermark — **authored, deliberately not applied** (see below). RESIDUE: **drift reconciliation is not built, and building it needs your decision first** — nothing re-pulls provider state to detect divergence, and the moment it does it has to answer which side wins when a Google edit and a local edit disagree (local wins / provider wins / surface the conflict). That is a product rule, not an implementation detail, so I have not picked one. **Index plans are now MEASURED, and the measurement disproved my own recommendation.** Seeded a dormant, empty scratch cell (`cell2`, 900 tables, 0 rows — never the shared dev database) with 200,000 `calendar_events` across 20 orgs, 30,000 recurring, the measured org holding a deliberate 2.5% MINORITY share so RLS post-filtering is exercised. `EXPLAIN (ANALYZE, BUFFERS)` as `streamline_app` (`rolbypassrls = false`) with the tenant GUC set by `SET LOCAL app.organization_id` inside the transaction, because the Neon pooler drops startup parameters. Measured in buffers, not milliseconds. Results:
  - **The calendar list query: 2,594 buffers with the index and 2,594 without — a byte-identical plan.** The planner never chose it. A partial index `WHERE rrule IS NOT NULL` cannot serve a predicate containing an `rrule IS NULL` branch, because `(A AND rrule IS NULL) OR (B AND rrule IS NOT NULL)` does not imply `rrule IS NOT NULL`. No column ordering changes that; the index was unusable for the hot path by construction.
  - **The UNION rewrite my own notes prescribe for an OR-defeats-index shape is 19% WORSE:** 3,093 buffers versus 2,594, because the non-recurring branch dominates (2,616 of the 3,093) and can never use a recurring-only index.
  - Only the reminder sweep's recurring-only query benefited, 86 — 63 buffers, on a periodic 200-row background batch that was already cheap.
  - Cost: 1,128 kB plus write amplification on every recurring-event insert and update.
  **Verdict: migration `0982` was reverted** — file, journal entry and schema declaration all removed, journal re-verified monotonic. The existing `idx_calendar_events_org_date` is the correct index for this access path and no addition is warranted. The scratch cell was returned to empty.
- [x] Consolidate member list/search behind `directory:people:view` and test missing, granted and revoked access. — the premise of two backend paths was wrong; both were frontend hooks on the same `GET /org/members`, and `useCalendarMemberSearch` had NO gate at all while its sibling did. One `useCalendarMemberLookup` ANDs `useCan("directory:people:view")` into `enabled`; key confirmed verbatim at `rbac/permissions/directory.ts:5`. e2e bite proof builds a real app and a `holds`-forced-true app: 403 vs 200.
- [x] Verify one provider-neutral bounded Inbox/Mail contract for accounts, conversations, messages, participants, labels, sync cursors, attachments, send/reply/read/search/archive and unread counts. — 15 routes enumerated across `MailController` (11) and `InboxController` (4). Every one carries a classification decorator, every one with parameters carries `@Validate`, and both list contracts cap at 50/page (`listMessagesQuerySchema`, `inboxQuerySchema`); `check:bounded-contracts` and `check:bulk-id-limits` report 0 in-scope violations. Responses are provider-neutral: `mail-normalizers.ts` translates Gmail and Outlook into `MailMessageSummary`/`MailMessageDetail`, and no provider field name (`labelIds`, `conversationId`, `isFlagged`) reaches a response. The service dispatches on `acc.provider` rather than through a formal `IMailProvider` interface — recorded as a design observation, not a contract defect, since the published shape is already neutral.
- [x] Prove ownership/delegation, sanitization, unsafe-link/content handling, idempotent delivery/sync, bounce/retry/DLQ and exact list/thread/count invalidation. — **found and fixed a P0: every Gmail reply was addressed to a message id.** `mail.service.ts` called `replyToThread(userId, conn, threadId, messageId, bodyHtml, cc)` against a signature whose fourth parameter is `recipientEmail`; both are `string`, so the compiler could not see it and no reply reached its recipient. The provider now takes a named options object so the swap cannot compile, and the service resolves the real address from the original message (sender, or the first `To` when replying to one's own sent mail, else a 400 rather than a bogus send). Ownership: every read and write calls `assertOwnedConnection(orgId, userId, accountId)`, a three-column predicate, before any provider call. **A vacuous isolation spec was rewritten:** `mail-metadata-isolation.spec.ts` built the whole service out of `jest.fn()`s and asserted that a mock called with X was called with X — it could not detect a missing `orgId`; it now drives the real service and renders the predicate with `PgDialect.sqlToQuery`, proven to fail when the `orgId` predicate is removed. Idempotency: `POST /mail/send` and `/mail/reply` had none, so a retry duplicated an email to an external recipient — both now carry `@Idempotent`, and `check:idempotent-commands` was blind to them (its `CRITICAL_ROUTE_RE` listed `send-signin` and `test-send` but not a bare `send`), so the gate was widened and proven load-bearing by removing a decorator and watching it fail. Sanitization is at the render boundary: `MailHtmlViewer` runs DOMPurify with a tag/attribute allowlist, `ALLOW_UNKNOWN_PROTOCOLS: false`, remote-image blocking and `rel="noopener noreferrer"` link hardening, covered by a bite-proof XSS test; a new `mail-html-render-boundary.test.ts` fails if any second component in `features/mail/**` ever renders raw HTML (proven by injecting one). A hook leak on a sanitizer throw was closed with `try/finally`. Sync is idempotent by `onConflictDoUpdate` on `(accountId, folder)` and `(accountId, messageId)`. On bounce/DLQ: this surface sends through the *user's own* mailbox via Composio, so bounces return to that mailbox and we own no sending domain — an interactive compose failing synchronously with a user-visible error is the correct design, and `@Idempotent` now makes the user's retry safe. Platform-sent transactional email, which does need suppression and DLQ, is S08's `modules/email` and already has `email-webhook` + `email-suppression`.
- [x] Verify accessible responsive infinite/range UI, optimistic rollback, offline/reconnect and revocation states; remove legacy Inbox hooks only after caller proof. — **found and fixed a P1: `useMailAction`'s entire optimistic update was dead code.** It matched with `queryKeys.mail.messages()`, which yields a trailing `undefined` fourth element that TanStack's partial matcher never matches, so `getQueriesData` returned zero entries, every `setQueryData` was a no-op and `onError` restored nothing — archive, trash, mark-read and star were never optimistic. ## Newly discovered, still open

- ~~Calendar provider sync has no user-visible status~~ — **DONE.** `GET /calendar/events/:eventId/sync-status` and `POST /calendar/events/:eventId/sync-retry` ship with a frontend consumer; a sync that exhausted its retries is now visible and recoverable by the user who owns the event. **Drift reconciliation is still open and is blocked on a product decision**, not on effort: a reconciler must define who wins when provider and local state disagree. Owner: S09, pending that rule.
- ~~An occurrence rescheduled *into* the visible window is not rendered.~~ — **DONE.** The exception fetch now ORs on `modifiedStart` within the window (still keyset-paged and org-scoped), and list and export both run the second pass the reminder sweep already had, deduplicated against the first pass so a move inside the window is emitted exactly once. Fixing it surfaced a second bug in the pre-existing `expandToOccurrences`: when an exception set `modifiedStart` without `modifiedEnd`, the end was anchored to the **nominal** start, so a meeting moved to a later day rendered with an end before its start. Both anchors now derive from the modified start, pinned by regression tests.
- ~~Migration `0982` adds a `recurrence_end` index.~~ — **REVERTED after measurement.** It was authored, then benchmarked on a seeded scratch cell as `streamline_app` with the tenant GUC, and the calendar list plan was byte-identical with and without it (2,594 buffers either way): a partial index on `rrule IS NOT NULL` cannot serve a predicate that also has an `rrule IS NULL` branch. The UNION rewrite normally prescribed for that shape measured 19% worse. Reverted rather than shipped on reasoning alone.
- **`/inbox` exceeds its First Load JS ceiling by 34,392 bytes** (558,680 vs 524,288) and no S09 change can close it: only 13,519 bytes are inbox-specific and the shared authenticated shell alone is 545,161 bytes. Owner: S11 (frontend-wide budgets).
- **`hooks/api/notifications-inbox.ts` mutations have no `onError` and no rollback** for archive/delete/pin/snooze/approve/reject. S09 fixed this at its own call sites; the hook-level gap belongs to the Notifications session. Owner: S08.
