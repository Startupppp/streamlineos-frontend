## Acceptance criteria

- [x] Keep Home composition-only; verify bounded parallel section contracts, per-section failure/privacy/cache behavior, one access/membership resolution and no domain-table ownership. — `modules/dashboard/**` defines no table; every table it reads is imported from the module that owns it. Sections stay independent through `settle` + a per-section `degraded[]` (`dashboard-personal.service.ts:54-69`) and `HomeSectionBoundary`. **Three defects fixed:** `GET /dashboard/executive` shipped CRM revenue, pipeline, new-lead and conversion figures to any `hr:analytics:read` holder with no CRM gate — the frontend only *hid* them behind `useCan("crm:leads:view")`; the projection is now resolved before the query runs and the two shapes are cached under different keys. `getLeavesToday`, `getTeamAvailability` and `buildTeamAttendance` were unbounded org-wide reads; they are capped and now report a true total from their own aggregate rather than truncating silently. `resolvePersonalDashboardModules` issued 7 module-availability calls for 3 distinct modules. Membership is resolved once per request. 17 dashboard suites / 151 tests.
- [x] Verify person/membership/worker/employment identity seams, `/me/*` subject derivation, minimal directory projections and universal self-service independent of paid-module enablement. — One seam (`person-seam.ts`), every path org-scoped. All 26 `/me/*` routes repo-wide derive the subject from `@CurrentUser()`, none carries `@RequireModule`, and none accepts a client-supplied subject. Universal self-service survives a per-user module denial because `self` has no registry entry, so `isCoreModuleKey` keeps it out of `stripDeniedModules`. **P0 fixed:** `GET /directory/people` and `/people/:id` are `@Universal()` and returned the whole `organization_people` row — `dateOfBirth`, `gender`, `nationality`, `address` and `emergencyContact` for every colleague. A minimal projection now backs both reads; none of the removed columns was rendered anywhere. **P1 fixed:** `GET /directory/employment` was `@Universal()` and batch-read employment facts for up to 100 arbitrary user ids, rooted at the global `users` table; it now requires `settings:view` (the same gate as the member list it decorates) and re-enters the tenant through `organization_members`.
- [x] Audit HR people, employment, leave, attendance, recruitment, onboarding, performance, benefits, documents and approvals across API, DataScope, cache, jobs and UI. — Six parallel audits over the owned surface; every finding verified against current source before acting. **Fixed:** `leaveApprovalScope("team")` required the approver to also be the requester, which the self-approval guard then always denied, so a team-scope approver could never approve anything the roster listed for them; `LeaveCalendarController` was the only HR admin controller missing `@RequireModule("hr")`; the employee list cached under `hr:employees:cursor:*` was never invalidated by any mutation and now uses a versioned namespace bumped on update and onboarding. Four reported findings were **disproven** and deliberately not "fixed": announcements already invalidate by prefix, WFH notes are concatenated into `reason` rather than dropped, `approverMembershipId` is written at request time not approval time, and two Home widgets sharing one endpoint correctly fail together.
- [x] Classify every HR mutation as self/universal or exact-permission authorized; prove revocation during mutation and cross-person/cross-org denial. — All 566 S04 mutation routes carry either `@RequirePermission` or an explicit `@Universal()`; zero are undeclared. On the client, 219 unclassified HR/Directory mutation hooks were routed through `useAuthorizedMutation` using the key read from the backend handler itself, never guessed — repo-wide unclassified fell 895 → 677 and the gate baseline was ratcheted down. `check:permission-keys` confirms every key resolves in both catalogs. Revocation is proven by `hr-mutation-revocation.spec.ts`: a SUSPENDED, REMOVED or INVITED membership is refused at command time even with a valid token, because the acting membership is re-resolved from the database inside the command.
- [ ] Verify bounded filters/cursors/exports, no N+1, responsive and accessible Home/Directory/HR states and production-shaped focused query evidence. — **Partially proven, and the gap is infrastructural, not code.** Bounded reads, cursor/ORDER BY agreement across all 7 HR cursors, absence of N+1, and responsive/accessible states are verified; `getDirectReportUserIds` was bounded before it feeds an `IN (...)` clause. **Production-shaped query-plan evidence is not produced** — it needs a booted API against a seeded scratch database with a minority-size org, which the master PRD already records as open under "Read budgets need a reproducible seed". Nothing in this session can close it alone.

Removed with dependency proof: `HrDashboardReportsService.exportRows`, a routeless query that materialised up to 10,000 rows including a decrypted `taxId` and had zero callers, plus the orphaned `DirectoryPersonWithAccess` type and its dead re-export. The spec that had been guarding the dead export now asserts it stays deleted. No landing-page file was touched.

## Cross-session findings

Raised here, owned elsewhere; not edited from this session.

- **S02** — a composite-FK conversion in `db/schema/hr/hiring-candidates.ts` broke `recruitment-candidate-vault.spec.ts`, whose text scan only recognised the inline `.references(..., { onDelete: "set null" })` form. The FK rule is intact; the scan was blind to the new syntax and has been taught both forms. Two index gaps remain S02's to close: `leave_balances` has no `(org_id, user_membership_id, year)` index though three hot paths filter on exactly that, and the employee list and org chart sort on `lower(coalesce(users.name,''))` with no functional index.
- **S01/S12** — the four `/me/api-tokens` routes are gated on `settings:api-tokens:*` rather than a `self:*` key, the only `/me/*` routes repo-wide not using a self key.
- **S01/S02** — the whole recruitment candidate pipeline is gated on `hr:employees:view`/`:manage`; there is no `hr:candidates:*` key in either catalog, so a grant intended for the employee directory also opens the candidate pipeline. Closing this needs new catalog keys, role-template placement and a backfill migration.
- **S01** — a platform admin holding an org membership without `userOnboardingCompletedAt` is routed into the employee onboarding wizard, because the session type cannot express platform-admin status (`lib/wizard-gate.ts:34`, documented by its own test).
- **S05** — `hooks/api/hr/{expenses,travel,reimbursements}.ts` call `modules/expenses` routes and were left unclassified rather than guessed at; they are the remaining 7 unclassified hooks under `hooks/api/hr/`.
