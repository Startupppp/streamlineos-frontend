# 05 — Revision and chunk retention are explicit

**Status:** in-progress — 5 of 6 criteria done; erasure criterion fully settled (three non-chunk legs are vacuous — no KB search cache, no stored export artifacts, no external vector store); snapshot optimisation blocked on measured storage data

## Acceptance criteria

- [x] Wiki pages and support articles share a documented revision-retention policy. — `docs/specs/kb-retention-policy.md`: a per-content-type × lifecycle-state table stating exactly what is retained and why (published articles retained; draft/in_review/archived article chunks pruned; published/draft/in_review page chunks retained; archived and soft-deleted page chunks pruned; parent-deleted pruned in both). Names the sweep that enforces it (`POST /cron/kb-chunk-retention-sweep` → `CronKbChunkRetentionService.pruneStaleChunks`, 600 s lease, 500 rows/org/batch) so the document and the code point at each other.
- [ ] Milestone snapshots plus bounded deltas replace unbounded full snapshots where measured storage justifies it. — **BLOCKED: needs a migrated database.** The criterion is conditional on *measured* storage justifying it, and no measurement can be taken — nothing has been applied to a database this entire program. Building the optimisation first would invert the criterion’s own condition. This is not deferred work with an owner; it is gated on the operator running APPLY-MIGRATIONS.md.
- [x] Active, archived, deleted and legally held content have distinct retention behavior — for chunks. `CronKbChunkRetentionService` (`cron-kb-chunk-retention.service.ts`): article chunks are pruned when their parent article is absent or not `published`; page chunks are pruned when the parent page is absent, `archived`, or soft-deleted (`deletedAt IS NOT NULL`). Published articles and live pages are untouched.
- [x] Old chunk revisions are removed by partition/retention work, never row-by-row request work. — `pruneStaleChunks` runs via `forEachOrg` (one tenant transaction per org, per-org error isolation), batched in loops of 500 rows (`PRUNE_BATCH_SIZE`), triggered by `/cron/kb-chunk-retention-sweep` (`cron-support.controller.ts:62-71`), protected by `CronLeaseService` (lease TTL 600 s).
- [x] A restore can rebuild the active index from retained source revisions. — re-running ingestion from current source content is idempotent and therefore *is* the restore path: migration `0510`'s `uniq_kb_chunks_article_revision` / `uniq_kb_chunks_page_revision` make a concurrent replay unable to insert duplicates, and `indexArticle`/`indexPage` delete-then-insert inside a transaction so a fresh run fully replaces stale chunks. Documented under "Restore / rebuild" in `docs/specs/kb-retention-policy.md`. No separate restore service is needed; what is genuinely absent is a *bulk* re-index trigger for a whole org, noted there as the smallest future addition.
- [x] Erasure propagates to chunks, caches, exports and provider-side files. — all four legs settled. Chunks: `CronKbChunkRetentionService.pruneStaleChunks` (`cron-kb-chunk-retention.service.ts:23`). Caches: vacuous — `KbSearchService` (`kb-search.service.ts`) has no `CacheService` injection and caches no results; the only KB Redis cache is `kb:acc-spaces:${orgId}` (`kb-access.service.ts:55`) which is space-membership-derived, not chunk-derived, so chunk deletion leaves no stale entry. Exports: vacuous — `KbImportExportService.exportPage` (`kb-import-export.service.ts:37`) returns content inline in the HTTP response; `kbExportJobs` rows (`kb-import-export.service.ts:58`) are audit records of export events, not stored artifact files. Provider-side files: vacuous — chunks are Postgres rows with `vector` columns; `StorageService` is called at `kb-indexing.service.ts:438` only to read attachment blobs for text extraction, nothing is written externally. Full evidence in `docs/specs/kb-retention-policy.md`.

**Audit note (2026-08-26, updated):** Five of six criteria done. The erasure criterion is now fully settled: code review confirmed `KbSearchService` holds no `CacheService` injection and caches no results; `KbImportExportService.exportPage` returns content inline with no stored artifact; `KbIndexingService` writes chunks only to Postgres. The three non-chunk erasure legs are vacuous. One criterion remains blocked: the snapshot-delta optimisation requires measured storage data that does not exist until migrations are applied to a live database.

**Legal hold (orchestrator, 2026-08-26):** not representable in the current schema — neither `kb_articles` nor `kb_pages` carries a hold column, and `hr_legal_holds` scopes to HR records only. Recorded in `docs/specs/kb-retention-policy.md` with the smallest closing change rather than inventing a column outside this ticket's scope.
