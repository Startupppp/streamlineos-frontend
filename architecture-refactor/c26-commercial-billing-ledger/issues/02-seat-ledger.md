## Acceptance criteria

- [x] Billable seat types and inclusion rules are explicit. — no longer prose: `seat-definition.ts:29-58` is a `SeatEventType` union and a `SEAT_EVENT_DELTAS` lookup covering all nine types, and `seat-ledger.service.ts:91` reads the delta out of it rather than accepting one from the caller. `seat-ledger.service.spec.ts:240-290` walks every type and pins the four rules a reader gets wrong (accept is net zero, suspend/reactivate are net zero, deactivate and both dead-invitation states release the seat).
- [x] Membership and billing consume the same seat definition. — the definition is shared, not duplicated: `seat-definition.ts:8-18` holds the one `seatCount()` expression, `plan-limits.service.ts:303` enforces the members quota with it and `seat-ledger.service.ts:70-71` stamps `billedQuantityAfter` from it. `seat-ledger.service.spec.ts:203-237` renders both statements through `PgDialect` and asserts they are the same string, so the two cannot drift. **And membership now writes it:** all five write sites call `recordSeatEvent` with the transaction that performed the membership write — `organization/core/invitations.service.ts:268` (INVITE_SENT) and `:554` (INVITE_CANCELLED), `organization/core/invitation-acceptance.service.ts:93` (INVITE_ACCEPTED), `users/users.service.ts:128` and `:191` (existing-user and new-user direct create), `hr/directory/employee-onboarding.service.ts:161` and `:280`. `users/users-seat-limit.spec.ts:60-140` asserts the event fires once carrying the transaction handle itself, so a refactor onto a fresh connection fails the test rather than silently reading a post-commit count.

- [x] Seat changes serialize under the existing per-organisation quota lock. — `seat-ledger.service.ts:70` executes `lockMembersQuota(orgId)` as the first statement of every write, before the count read, the replay check and the insert. The key is built by `seat-definition.ts:20-27` as `quota:${orgId}:members` with `hashtextextended(…, 0)`, byte-identical to what `organization/core/invitations.service.ts:236` and `users/users.service.ts:109` already take, and it is `pg_advisory_xact_lock`, so it releases on commit or rollback. Ordering asserted in `seat-ledger.service.spec.ts:118-150` — including on the replay path, so two retries cannot interleave.
- [x] Every quantity change records actor, reason, effective time and idempotency key. — `seat-ledger.ts:41-48` (`actorId`, `reason`, `effectiveAt`, `idempotencyKey`; partial unique index `uq_billing_seat_events_idem` on `(orgId, idempotencyKey)`) written by `seat-ledger.service.ts:82-99`; asserted in `seat-ledger.service.spec.ts:249-273`. Migration `0521_billing_seat_ledger.sql`, journal `idx` 294.
- [x] Invitations, suspended members, external guests and deactivated accounts have documented treatment. — `seat-definition.ts:39-57` documents and encodes the treatment of each, and `seat-ledger.ts:18-33` carries the same table in the schema. The encoding is what the writer reads, so the documentation cannot go stale against the behaviour.
- [x] A reconciliation query explains billed quantity from ledger facts. — `seat-ledger.service.ts:150-204` (`reconcileBilledQuantity`) returns `ledgerQuantity` as `SUM(quantity_delta)`, the live `seatCount()`, their `drift`, the latest `billedQuantityAfter`, the event count, the last effective time and a `byEventType` breakdown whose deltas sum to `ledgerQuantity` — so the number is explained, not asserted. `seat-ledger.service.spec.ts:331-393` proves the breakdown reconciles, that drift is named when a membership write happened with no seat event beside it, that an empty ledger reports zero rather than throwing, and that an uncomputable live count refuses instead of reporting zero drift. `listSeatEvents` (`:206`) is the per-row detail behind it, capped at 100.
