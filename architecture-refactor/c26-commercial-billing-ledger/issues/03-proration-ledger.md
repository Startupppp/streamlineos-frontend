## Acceptance criteria

- [ ] Upgrade, downgrade and seat-quantity changes produce immutable proration line items. — **the producer exists; the caller does not.** `proration-ledger.service.ts:85-172` (`ProrationLedgerService.recordPlanChange`) inserts one immutable line per change and never updates a financial column afterwards — `reconcileProviderAmount` (`:216-259`) writes only `providerAmountMinor`, `providerRef` and `reconciledAt`, asserted at `proration-ledger.service.spec.ts:302-323`. The line type is **derived from the money** by `classify` (`:61-70`), so a caller cannot label a downgrade an upgrade, and all three types are covered at `proration-ledger.service.spec.ts:129-176`. **Blocker:** `billing.service.ts` owns plan change and subscription updates and belongs to S1 this session, so nothing calls `recordPlanChange` yet. The exact injection and call are in [`../../lane-requests/s2.md`](../../lane-requests/s2.md).
- [x] Each line names old/new price version, effective interval, quantity, currency and rounding. — `proration-ledger.ts:24-32` holds the columns; `proration-ledger.service.ts:131-147` populates every one of them, taking currency from the **price version** rather than the caller (`proration-ledger.service.spec.ts:196-204`) and refusing a cross-currency change outright (`:206-214`). Rounding is an explicit `RoundingRule` stored on the row and applied deterministically by `proration-math.ts:48-79`, which computes in `bigint` so unit × quantity × milliseconds never loses precision past `Number.MAX_SAFE_INTEGER` and refuses an out-of-range amount instead of wrapping; all four rules are pinned on exact halves in both signs at `proration-math.spec.ts:122-177`. Schema + migration `0522_billing_proration_ledger.sql`.
- [x] Provider-calculated proration is stored and reconciled; it is not blindly trusted. — `proration-ledger.service.ts:117-127` computes `amountMinor` from the two price versions, and `:216-259` (`reconcileProviderAmount`) stores the provider figure beside it and returns `varianceMinor` + `agrees` **without overwriting the computed amount**. `listUnreconciled` (`:261-289`) serves the outstanding ones off the partial index. Asserted at `proration-ledger.service.spec.ts:302-350`, including that the update statement's key set does not contain `amountMinor`.
- [x] Retry with the same idempotency key returns the same result. — `proration-ledger.service.ts:93-94` returns the stored line before doing any work, `:148-157` recovers it when a concurrent writer wins the unique index, and it raises rather than returning an unwritten line. `proration-ledger.service.spec.ts:254-300` proves all three, including that a replay **does not re-read the catalog at all** — so editing a price version cannot change money already recorded.
- [x] Negative adjustments become credits, never mutation of an issued invoice. — a downgrade produces a **negative `amountMinor`** as a new row (`proration-ledger.service.spec.ts:143-152`); nothing updates an existing line's amount. `listForSubscription` (`:291-325`) reports `chargeMinor` and `creditMinor` separately so a credit is never netted away silently (`proration-ledger.service.spec.ts:355-370`). The issued-invoice side is `invoice-snapshot.ts:104-127` (`billing_credit_notes`, `originalSnapshotId` FK `onDelete: "restrict"`) plus the immutability trigger delivered under c26-05.

**Progress (2026-08-27, S2):** `ProrationLedgerService` (`modules/billing/core/proration-ledger.service.ts`) and the pure `proration-math.ts` seam are written, registered at `billing.module.ts:25` / exported at `:26`, with 47 passing tests (22 service + 25 math). The service injects `VersionedCatalogService`, which is the first live consumer of c26-01's newly-registered catalog.

**Design decision:** `computeProrationMinor` takes a quantity on **both** sides rather than one shared quantity. A seat-count change at an unchanged unit price prorates to exactly zero under the one-quantity form, which silently loses the whole `QUANTITY_CHANGE` case.

**Audit note (2026-08-26):** All five structural criteria are covered by schema; no migration. The single behavioral gap is the proration-line producer — a service that inserts rows on upgrade/downgrade/quantity change does not exist. The idempotency constraint (criterion 4) prevents double-write but a service must also return the stored result on replay. *(Superseded: the migration is journalled as `idx` 295 and the producer now exists with the replay-return path. What remains is the call site.)*
