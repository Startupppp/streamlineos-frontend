## Acceptance criteria

- [x] Each usage event has tenant, meter key, subject, quantity, occurred time and unique source key. — `db/schema/billing/usage-events.ts:17-35` holds the columns; `usage-metering.service.ts:75-101` (`ingestEvent`) writes every one of them and refuses a fractional quantity before it touches the database (`usage-metering.service.spec.ts:443-448`). Migration `0523_billing_usage_events.sql`, journal `idx` 296.
- [x] Duplicate and out-of-order events do not double-count. — `usage-metering.service.ts:91-93` infers the conflict on `(orgId, meterKey, sourceKey)` and reports `{ id: null, duplicate: true }` rather than inserting again; a late event keeps its own `occurredAt` instead of being reordered. `usage-metering.service.spec.ts:415-449`.
- [x] Raw events are append-only; hourly/daily rollups are rebuildable projections. — no code path updates `billing_usage_events`. `usage-metering.service.ts:308-355` (`rebuildRollup`) recomputes a period from the raw events and upserts `billing_usage_rollups` on `(org, meter, granularity, periodStart)`, so rebuilding is idempotent, and it **refuses rather than writing a zero rollup it could not compute** (`usage-metering.service.spec.ts:451-480`).
- [x] Quota enforcement uses an atomic reservation where the action spends money. — `usage-metering.service.ts:104-156` (`acquireReservation`): one transaction takes `pg_advisory_xact_lock(hashtextextended('usage:<orgId>:<meterKey>', 0))` (`:64-66`), reads committed usage, and inserts — in that order, asserted at `usage-metering.service.spec.ts:155-178`. It is **never check-then-spend**: the read and the insert cannot be interleaved by a second caller, a refused reservation inserts nothing (`spec:191-201`), and it refuses rather than reserving against a usage figure it could not read (`spec:254-263`). `settleReservation` (`:159-207`) converts the reservation into a usage fact keyed `reservation:<id>`, so a second settle is a no-op; `releaseReservation` (`:209-230`) returns the quota with no usage recorded; both refuse to unwind money already spent. 31 tests.
- [x] Late events and corrections are represented as new facts. — insert-only, unique `sourceKey` per event; a correction ingests under a new source key. `usage-metering.service.ts:75-101` has no update path, and `usage-metering.service.spec.ts:426-441` pins that a late event is stored at its own `occurredAt`.
- [x] Retention preserves invoice evidence after raw operational detail expires. — `rebuildRollup` writes the durable `billing_usage_rollups` row that `invoice-snapshot.ts:92-93` (`billing_invoice_line_snapshots.usageRollupId`) points at, so raw events can be pruned while the rollup — and therefore the invoice evidence — remains.

**How `expiresAt` is honoured (2026-08-27, S2):** committed usage counts only reservations that are `status = 'ACTIVE'` and an unexpired `expiresAt` (`usage-metering.service.ts:260-262`), asserted at `usage-metering.service.spec.ts:227-252` by rendering the built predicate through `PgDialect` rather than grepping a hand-written string, so an abandoned reservation stops holding quota the moment it lapses even before the sweep runs. `sweepExpiredReservations` (`:357-396`) then marks them `EXPIRED`; it has no ambient tenant context, so it opens one `runInNewTenantTransaction` per organisation rather than borrowing a dead handle, and it logs a failure instead of swallowing it.

**Fixed in review (2026-08-27):** `readUsage` and `rebuildRollup` bounded their period with a JS `Date` interpolated into a raw drizzle ``sql`` template, which throws `ERR_INVALID_ARG_TYPE` at postgres.js — and every mocked test passed because none of them reaches the driver. Both now use column-aware `gte`/`lt`/`gt`; `usage-metering.service.spec.ts:515-528` asserts the only raw statement this service executes is the advisory lock.

**Design decision:** `acquireReservation` takes `limit: number | null` explicitly rather than resolving a meter's entitlement itself. There is no plan-level meter catalog wired yet — `VersionedCatalogService.resolveOrgEntitlements` returns per-org overrides only — and inferring "no override therefore unlimited" would fail open, which is the exact defect c17-04 fixed one layer up. An explicit `null` means unlimited and still writes the reservation, so the ledger stays complete.

**Audit note (2026-08-26):** All three tables (`billing_usage_events`, `billing_usage_rollups`, `billing_usage_reservations`) exist in schema; no migration. Five of six criteria are satisfied structurally. The one gap is the quota-enforcement service — no code exists that acquires a reservation, performs the action, and settles or cancels on outcome. *(Superseded: the migration is journalled as `idx` 296, and `UsageMeteringService` now acquires, settles and cancels.)*
