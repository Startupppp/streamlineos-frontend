## NEW FINDINGS

### NF-1 (P1) — Billing adapter seam violated: frontend callers consume Razorpay-specific identifiers and SDK

**Evidence:**

`hooks/api/subscription.ts:16–46` exposes:
```ts
interface SubscriptionPayment {
  razorpayPaymentId: string | null;
  razorpayOrderId: string | null;
  …
}
interface Subscription {
  razorpaySubscriptionId: string | null;
  razorpayCustomerId: string | null;
  razorpayPlanId: string | null;
  …
}
interface SubscriptionResponse {
  razorpayKeyId: string | null;
  …
}
interface VerifySubscriptionInput {
  razorpay_order_id: string;
  razorpay_payment_id: string;
  razorpay_signature: string;
  …
}
```

`hooks/api/subscription.ts:79,88,96` calls:
- `apiClient.get("/billing/razorpay")` — GET
- `apiClient.post("/billing/razorpay", data)` — POST
- `apiClient.patch("/billing/razorpay", data)` — PATCH

`features/billing/components/plan-tab.tsx:163–165` and `features/billing/ai-credits-settings-page.tsx:154–156` construct the Razorpay verification payload directly from the Razorpay SDK callback fields (`razorpay_order_id`, `razorpay_payment_id`, `razorpay_signature`).

`features/billing/components/plan-tab.tsx:87` and `features/billing/ai-credits-settings-page.tsx:93` load `https://checkout.razorpay.com/v1/checkout.js` directly in the browser.

**Backend side:** `billing.controller.ts:123,128,141` exposes `@Get("razorpay")`, `@Post("razorpay")`, `@Patch("razorpay")` as named routes. The `billing.controller.e2e-spec.ts:37–55` tests these routes by Razorpay-specific path.

**Failure scenario:** Adding Stripe as a second adapter requires:
1. Renaming or duplicating the `/billing/razorpay` backend routes.
2. Changing frontend hook API calls.
3. Changing frontend contract types.
4. Changing frontend UI components that handle provider-specific callback fields.

The requirement "a Stripe-ready contract test requires no Billing caller change" is not met.

**What is missing:**
- A provider-neutral checkout-session route (e.g., `POST /billing/checkout-session → { sessionId, publicKey, providerHint }`) that the frontend calls regardless of provider.
- A provider-neutral confirmation route (e.g., `PATCH /billing/checkout-session/:id/confirm → { orderId, paymentId, signature }`) that accepts a provider-neutral envelope.
- Frontend types that do not name a provider.
- The backend adapter (currently Razorpay) translates between the neutral contract and the provider-specific wire format behind the seam.

**Severity: P1** — Not a data-loss bug today (Razorpay is the only provider), but the adapter abstraction was the stated non-negotiable requirement, and it is absent. Any second provider requires breaking frontend contract changes.

### NF-2 (P2) — Chat presence: per-tab 15-second HTTP heartbeat not replaced with Ably connection presence

**Evidence:**

`frontend/app/(authenticated)/chat/page.tsx:58–72`:
```ts
useEffect(() => {
  if (!currentUserId) return;
  heartbeatRef.current.mutate();
  const interval = setInterval(() => {
    if (document.visibilityState === "visible") heartbeatRef.current.mutate();
  }, 15_000);          // line 63 — every 15 seconds per open chat tab
  …
}, [currentUserId]);
```

`backend/src/modules/chat/chat-presence.controller.ts:39–44` still exposes `POST /chat/presence/heartbeat`.

**Failure scenario:** With multiple browser tabs open on `/chat`, each fires an HTTP request every 15 seconds independently. There is no leader election and no backoff. At 10,000 concurrent users each with 2 tabs open, this is 20,000 POST requests every 15 seconds (≈1,333 req/s) purely for presence — before any message activity. The bullet explicitly requires replacing this with Ably's authoritative connection-state events plus a single leader-elected fallback with jitter and backoff, with "multitab/reconnect load budgets" proved.

**Severity: P2** — Not immediately data-corrupting, but the load profile is unbounded under concurrent usage and the requirement is explicitly stated.
