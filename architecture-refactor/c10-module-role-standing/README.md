# c10 — Make module-level standing answerable

PRD: [`prd.md`](prd.md) · Program: [`../README.md`](../README.md)

**Wave 3** · 5 tickets, all closed.

The engine is built — `MODULE_REGISTRY`, a real `ROLE_RANK` ladder, a `SCOPE_RANK` grant ceiling. What is missing is the read: nothing can answer *who holds standing in this module, and who may I grant to?* without assembling it from three places. These five tickets add that read and the one operation it enables.

## Closed ticket digests

**01 — A module's roster is readable.** `module-standing-roster.service.ts:listStanding` is the single canonical read, deriving rank from the role's module key. Each entry carries a `source` marker (module role / org-level standing / direct grant) so owners can see what they cannot revoke. Permission key `${moduleKey}:access:view|manage` is generated by `MODULE_ACCESS_PERMISSIONS` and wired into the frontend permissions barrel. Controller e2e covers the allow/deny matrix and cross-tenant isolation in `module-access.controller.e2e-spec.ts`.

**02 — An actor knows what they may grant, before they try.** `GET :moduleKey/standing/grantable` (`module-access.controller.ts:80`) calls `describeGrantable` in `module-standing-roster.service.ts:367`, which filters `GRANTABLE_VIA_PERMISSIONS` via `canGrantToRank` and returns a `scopeCeiling` (`module-standing-roster.service.ts:395`). Org admins receive `canGrantModuleOwnership: false`; module owners and admins see distinct option sets. The frontend grant form renders from this endpoint, not a static list.

**03 — The read and the write share one predicate.** `canGrantToRank` extracted to `common/rbac/grantability.ts:59` and imported by both `describeGrantable` and `grantAdminStanding`, so drift between the form and the enforcer is structurally impossible. `standing-grantability-agreement.spec.ts` asserts the full rank/scope matrix: every rank the read offers is accepted by the writer, and every rank it omits throws `ForbiddenException`.

**04 — Standing can be granted and revoked.** Grant path calls `bumpPermissionsVersion(tx, orgId)` + `cache.invalidate(userSession(userId))` at `module-standing-mutations.service.ts:137,145` — the grantee's permissions are live on their next request without re-login. Revoke deletes all module role assignments for the membership (line 196). Exceeding the actor's rank or scope ceiling throws `ForbiddenException` naming the ceiling. Both actions emit an audit row with actor, subject, moduleKey, and rank (`module_access.standing_granted` / `standing_revoked` at lines 147, 218).

**05 — Module ownership transfers in one operation.** `directTransferOwnership` in `module-standing-mutations.service.ts:274` runs upsert + revoke inside `runInTenantTransaction`, reusing `revokeModuleOwnerRole` + `assertModuleOwnerRoleAssigned` from `ownership/module-owner-role.helper.ts`. A mid-transaction failure rolls back to the previous owner — never both owners, never neither. Refused for non-administrable modules. `GET /ownership/modules` via `OwnershipService.listModuleOwnerships` surfaces orphaned modules. Spec at `standing-mutations.spec.ts:339` asserts the transaction mock invokes its callback so the security assertions actually run.
