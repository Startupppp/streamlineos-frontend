# Re-proof at journal head 691, and three findings that only running it could produce — 2026-09-04

Covers PRD-C064, PRD-C143 and PRD-C152. **The release baseline moved during this session.** Everything
below is measured against the new head, not the one the earlier evidence was captured at.

## The baseline moved: 685 → 691

`BOOTSTRAP-PARITY-2026-09-04.md` and `RELEASE-RECORD-2026-09-04.md` both certify **685/685**. The journal

## Finding 1 — migration 1067 cannot apply to a seeded database (P1)

Applying the six new migrations to `scratch_boot_d`, the production-shaped seeded database:

```
OK    [1062_mail_metadata_unread_count_index]
OK    [1063_invoice_item_immutability_trigger]
OK    [1064_revenue_events_currency]
OK    [1065_t02_survey_live_session_metadata_index]
OK    [1066_chat_reactions_org_id_unique]
FAIL  [1067_t07_hr_identity_and_search_keys] hr_people holds 500 (org_id, user_id) group(s)
      with more than one live person row.
RESULT: FAILED at 1067_t07_hr_identity_and_search_keys (690/691 ok before failure)
```

The migration's precondition guard fired correctly — it refused rather than corrupting. Measured shape
of the offending data:

| | |
|---|---|
| live `hr_people` rows | 7,100 |
| rows carrying a `user_id` | 2,000 |
| duplicate `(org_id, user_id)` groups | 500 |
| largest group | 4 |
| organisations affected | 1 — `Scratch E2E Corp`, the seed fixture |

500 users × exactly 4 rows each, all inside the seed org. **This is not production data and not a defect
in 1067.** The same migration applies cleanly to a database with no `hr_people` rows (below), which
isolates the cause to the seed.

### Root cause — an `ON CONFLICT` clause that could never fire

A bare `ON CONFLICT DO NOTHING` suppresses an insert only when a real unique constraint is violated, and
`(org_id, user_id)` on `hr_people` was unconstrained — **migration 1067 is the change that introduces
that very index**. So the clause was inert, the seed was not idempotent, and each re-run appended
another row per member. Four runs produced the groups of four, and 1067 then refused to apply.

The offending statement is `src/scripts/seed-scratch-e2e.mjs:250`, raw SQL:

```sql
INSERT INTO hr_people (org_id, user_id, created_at, updated_at)
VALUES ($1, $2, now(), now())
ON CONFLICT DO NOTHING
```

It runs once per active member of `LARGE_ORG` — the org named **`Scratch E2E Corp`**, which is exactly
where all 500 duplicate groups were measured. 500 members × 4 runs reproduces the measured shape
precisely: 500 groups, max group size 4, 2,000 rows carrying a `user_id`. The neighbouring
`generate_series` insert for user-less people is guarded by a count check and the `hr_employments`
insert uses `NOT EXISTS`, which is why only the user-linked rows duplicated and why the total is
7,100 rather than a multiple of 2,000.

**Correction to an earlier draft of this document.** This was first attributed to
`src/scripts/seed-enterprise-workspace.ts`, which also held a bare `onConflictDoNothing()` on
`hr_people`. That attribution was wrong: that script seeds an org named `Enterprise Demo Co` under
`ORG_ID e1000001-…`, not `Scratch E2E Corp`, so it cannot have produced the measured rows. The initial
search missed the real site because it looked for the Drizzle symbol `hrPeople` and the real statement
is raw SQL in a `.mjs` file. The mechanism described above was right; the file was not.

Fixed at the real site with `INSERT … SELECT … WHERE NOT EXISTS`, matching the pattern the
`hr_employments` insert two statements below already uses. That form does not depend on the index this
seed has to be able to precede. The invariant 1067 declares is the correct one — root `CLAUDE.md` §1
states a human in an organisation is exactly one person row.

`seed-enterprise-workspace.ts` was separately hardened at 16 further bare-`onConflictDoNothing()` sites
that a constraint audit confirmed are inert (`attendance`, `candidates`, `assets`, `holidays`,
`leave_policies`, `review_cycles` and others). That is real latent-defect removal of the same class, but
it is **unverified by execution**: the script fails on a fresh database for a separate, pre-existing
reason — it inserts `organizations` with a non-null `owner_membership_id` outside a transaction, so the
deferred owner-membership FK fires immediately. That failure predates this work and is recorded here
rather than fixed.

## Finding 2 — the re-proof at head 691

Two databases advanced 685 → 691, and one replayed from **empty**:

| Database | Route to 691 | Result |
|---|---|---|
| `scratch_boot_a` | advanced from 685 | `REACHED_HEAD 691/691` |
| `scratch_boot_b` | advanced from 685 | `REACHED_HEAD 691/691` |
| `scratch_boot_c` | **wiped, replayed from empty** | `REACHED_HEAD 691/691` |

`scratch_boot_a` and `scratch_boot_b` were *advanced*, not bootstrapped from empty at 691. That
distinction is kept because "two clean bootstraps" is the criterion's wording and an advanced database
does not satisfy it on its own; `scratch_boot_c` is what answers it — a full 691-migration replay from
an empty database, including `1067`, which is also what isolates the 1067 failure above to seed data
rather than to the migration.

**Catalog parity at 691** — `compare-catalog-parity.mjs`, comparison by full definition. Run twice:

```
advanced_to_691 (boot_a) vs advanced_to_691 (boot_b)   → 9 sections, 0 differences
advanced_to_691 (boot_a) vs empty_to_691   (boot_c)    → 9 sections, 0 differences
```

Both at `tables 1026 · columns 13511 · constraints 14027 · indexes 4773 · policies 983 · functions 467
· triggers 170 · extensions 6 · enums 476`, exit 0. The second comparison is the load-bearing one: a
database that replayed the whole chain from empty and a database that was migrated forward arrive at
**byte-identical catalogs**, which is the property PRD-C159 asks for.

### A false alarm, recorded because it nearly became a finding

The first attempt at the empty replay **failed at `0315_recon_pm_workspaces`** — *"there is no unique or
exclusion constraint matching the ON CONFLICT specification"*, 34 of 691 applied. That looked like a
cold-bootstrap regression contradicting the certified evidence, and it was not. The cause was the wipe
script: `.scratch/wipe.mjs` drops only `public` and `drizzle` and had errored partway with
`reportDependentObjects`, leaving other schemas behind. Re-wiping with `.scratch/wipe2.mjs`, which drops
**every** non-system schema and reports the resulting object counts, produced a clean 691/691.

The migration chain was never at fault. This is logged because reporting that first result as a P0
would have been wrong, and the thing that distinguished them was re-running with the correct tool rather
than trusting the first red result.

**Gates re-run with `DATABASE_URL` bound to a database at 691**, so the applied-watermark check actually
ran rather than skipping:

|---|---:|---|
| `check:migration-chain` | 0 | migration chain verified — no issues found |
| `check:migration-ledger` | 0 | no orphan, duplicate or unreachable entries |
| `check:migration-immutability` | 0 | every sealed migration still builds the same database |
| `check:migration-discipline` | 0 | passed |
| `check:tenant-relationships` | **0** | 691 of 691 journal entries · 214 single-column FKs · **0 actionable** |

`check:tenant-relationships` was the single blocker named against PRD-C064. It previously exited **2 —

Note it refused twice before producing a number: once because the target was not explicitly chosen, and
once because the ledger held 685 of 691. Both refusals were correct, and neither was worked around — the
database was brought to head instead.

## Finding 3 — PRD-C143 is measurable, and the recorded blocker is wrong

The recorded blocker reads *"cache-hit latency not measurable without Redis against this seed."* Redis
**is** configured and reachable. Measured from this machine against the configured Upstash endpoint:

| Operation | n | p50 | p95 | min |
|---|---:|---:|---:|---:|
| `GET` (200-byte value) | 25 | **120.8 ms** | 137.6 ms | 119.2 ms |
| `PING` (no payload) | 25 | 120.0 ms | 128.8 ms | 118.4 ms |
| 10 concurrent `GET`s | — | 445.2 ms wall | | |

`PING` and `GET` are indistinguishable, so the figure is **transit, not work**: the cache is an HTTPS
service roughly 120 ms away from this machine.

PRD-C143 requires cache-hit application paths at p95 ≤ 100 ms. **A single cache read costs 120 ms p50
here, so the target is unreachable from this machine by construction** — not because of application
code. This is a property of where the dev box sits relative to the Upstash region, and it would be
dishonest to record either a pass or a code-level failure from it. The criterion needs a co-located
measurement, which makes it deployed-environment evidence.

This also supplies the missing term in the recorded `GET /me/access` p50 of **503 ms**. The access
snapshot's version cache has a **1-second** TTL, so virtually every authenticated render pays at least
one Redis round trip — ~120 ms of the 503 ms is this, before any application work. The remainder is
`runInTenantTransaction` acquiring a Neon pooled connection to set the tenant GUC, which runs even on a
full cache hit, plus the frontend→backend hop.

**A fix that was proposed and rejected on measurement:** parallelising the `for...await` loop over
`CATALOG_MODULES` in `access-snapshot.resolver.ts:119`. The loop looks like N sequential awaits, but
`moduleAvailability` is fed closures over already-resolved values (`async () => rawMap`), and
`module-availability.ts` states in its own contract that it "adds no new per-request queries." The loop
costs microseconds. Changing it would have produced a plausible-looking commit worth nothing.

## Finding 4 — PRD-C152's two latency targets are met, measured

Both harnesses already existed and were runnable; the recorded blocker *"depends on PRD-C140 — needs a
fresh capture"* was discharged by the benchmark manifest. Run at HEAD, 2 suites / 6 tests, exit 0:

```
ai.stream.dispatch.overhead   n=50 p50=0.153ms p95=0.240ms io_allowance=22ms budget=50ms
ai.stream.first-byte.app      n=30 p50=1.839ms p95=3.876ms budget=150ms threshold=112ms
```

| Target | Criterion | Measured | Verdict |
|---|---:|---:|---|
| Application overhead before provider dispatch | p95 ≤ 250 ms | 0.240 ms + 22 ms declared I/O allowance | **MET** |
| First visible streamed state | ≤ 100 ms | p95 3.876 ms | **MET** |

The second is worth noting precisely: the repository's declared budget is 150 ms while the criterion
says 100 ms. That discrepancy is moot here — the measurement passes the **stricter** number, so no
budget needed reconciling and none was moved.

What these numbers do **not** cover, stated rather than implied:
- The dispatch spec stubs `streamText` and adds back a declared 22 ms allowance for the two I/O legs the
  stub makes free. It is application overhead, not a provider round trip.
- The first-byte spec uses a fake provider with zero delay, so it measures application time-to-first-byte,
  not end-user time including provider TTFT.
- `ChatAssistantService.processChat` does **not** route through `AiGatewayStreamHelper`, so the chat
  endpoint's own pre-dispatch overhead — 9 parallel DB reads, a message append, persona resolution and
  tool-set construction — is not measured by either spec.
