## Published: the OrganizationActor seam (S1 ticket 06) — ready for S2, S3, S4

`backend/src/common/organization/organization-actor.ts`. Tickets 07–10 and 13–16 migrate their actors through this and nothing else. It lives in `common/` and takes a `DbOrTx`, so it is a plain function, not an injectable — importing it creates no module edge and no DI cycle (`madge --circular` is still zero).

```ts
resolveOrganizationActor(db, orgId, ref): Promise<OrganizationActorResolution>
assertOrganizationActor(db, orgId, ref): Promise<OrganizationActor>   // throws OrganizationActorError
resolveOrganizationActorsByUserIds(db, orgId, userIds): Promise<Map<string, OrganizationActor>>
legacyUserIdOf(actor): string
organizationActorHttpError(error): NotFoundException | ForbiddenException
```

- `ref` is `{kind:"user",userId}` | `{kind:"membership",membershipId}` | `{kind:"person",organizationPersonId}`. The resolved `OrganizationActor` always carries `orgId`, `membershipId`, `userId`, `organizationPersonId`, `role`, `isOwner` and `resolvedVia`, so one type covers all four identities.
- **It fails closed.** `no-membership`, `membership-inactive`, `membership-in-another-organization` and `ambiguous-membership` are returned as an `unresolved` *value*; `assert*` turns the same thing into an `OrganizationActorError` carrying `toAuditMetadata()`. Only `membership-inactive` maps to 403 — every other reason maps to **404**, so another organization's id is never confirmed to exist.
- **Additive, not a cutover.** Nothing is removed. Use `legacyUserIdOf(actor)` to keep an existing `users.id`-keyed column working while the row is being migrated; ticket 11 contracts the legacy form once 07–10 are green.
- **Use the batch resolver in list paths.** `resolveOrganizationActorsByUserIds` is two queries regardless of input size; resolving per row reintroduces the N+1 these tickets exist to remove.
- Proof: `backend/src/common/organization/organization-actor.spec.ts`, 14 tests, including the multi-organization case where one global user resolves to two different membership ids with different roles and owner flags.

## Published: the shared route-access registry (S5 ticket 27) — ready for S1–S4, S6

`frontend/lib/rbac/route-access/`. One resolver answers module, permission and universal status for any pathname, and it is what server layouts and navigation both derive from.

```ts
resolveRouteAccess(pathname): RouteAccessDecision   // "universal" | "permission" | "unknown"
enforceRouteAccess(fallbackPath)                    // server-only; redirects on deny
UNIVERSAL_ROUTES · ROUTE_ACCESS_EXTENSIONS          // the two declared tables
```

- **It fails closed.** An unregistered path resolves `unknown`, and `enforceRouteAccess` denies it. All 553 `(authenticated)` routes currently resolve; a new route with no navigation entry must add a `ROUTE_ACCESS_EXTENSIONS` row with a reason, or it is denied.
- **Navigation is the source, not a second copy.** Permissions come from the existing `NAV_GROUPS`/`HOME_NAV_GROUPS` graph via `resolveNavRouteAccess`, so server gating cannot contradict what the sidebar shows — asserted per route by `route-access-keys.test.ts`.
- **Universal is now an explicit table with reasons**, promoted out of a test-local constant. `<module>/access` is never universal, and `/settings` is universal only as the exact personal landing page.
- Proof: `lib/rbac/route-access/__tests__/`, 16 tests, including every route resolving, no frontend-only key, no nav/registry conflict and no stale extension.
