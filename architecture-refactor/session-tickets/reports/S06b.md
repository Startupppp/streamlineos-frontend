## Item 1 — Attachment malware scanning and signed URLs

**State:** Infrastructure absent — no antivirus integration exists in the codebase. `listChannelFiles` returns direct Composio/storage URLs with no signed-expiry or malware-scan gate.

**Operator runbook (until infrastructure lands):**

1. Do not expose chat file download links to untrusted contexts — the URL is a direct storage link with no expiry or scan gate.
2. To add scanning: wire a ClamAV / VirusTotal webhook through the Composio integrations layer. On upload, emit a `chat.attachment.uploaded` outbox event; a relay calls the scanner; on clean result emit `chat.attachment.cleared`; the download endpoint refuses until the row's `scanStatus = 'clean'`. Add a `scan_status` column to `chat_attachments` (`'pending' | 'clean' | 'infected' | 'error'`), default `'pending'`.
3. Signed URLs: replace the raw storage URL with a short-lived pre-signed URL (TTL ≤ 15 min) generated at fetch time by the storage provider SDK. Gate on `scanStatus = 'clean'` before signing.
4. Until these ship, document in the security runbook that chat attachments are unscanned. No code changes made here.

## Item 2 — BOLA proofs for chat and mail

### Ably capability audit
**CLEAN.** `ably.service.ts createChatTokenRequest` grants explicit per-channel capabilities `chat:${orgId}:${channelId}` — never the wildcard `chat:${orgId}:*`. `listMemberChannelIds` filters by `orgId + membershipId`. The known P0 shape (wildcard) is NOT present.

### Fixes applied

**`chat-channel-members.service.ts`**
- `markRead`: UPDATE WHERE was missing `eq(chatChannelMembers.orgId, orgId)` — a cross-org user could mark another org's channel read. Fixed.
- `joinOpenChannel` existing member check: WHERE lacked orgId — could collide across orgs. Fixed.
- `listChannelFiles`: inner chatMessages query in both cursor/non-cursor branches was missing `eq(chatMessages.orgId, orgId)`. Fixed.

**`chat-invite-links.service.ts`**
- `assertAdmin(channelId, userId)` had no orgId — queried `chatChannelMembers` without org binding, so a user in org-A could manage invite links for a channel in org-B. Fixed: added `orgId` param, added `eq(chatChannelMembers.orgId, orgId)` to WHERE, changed missing-member response from `ForbiddenException` (existence oracle) to `NotFoundException`.
- `getOrCreateInviteLink` and `regenerateInviteLink` updated to accept and thread `orgId`.

**`chat-invite-links.controller.ts`**
- `getOrCreate` and `regenerate` handlers now pass `u.orgId` to the service.

**`chat-reply-reminders.service.ts`**
- `scheduleForMessage` fetched channel members with `eq(chatChannelMembers.channelId, channelId)` and no orgId — could notify cross-org members. Fixed: `and(eq(chatChannelMembers.orgId, orgId), eq(chatChannelMembers.channelId, channelId))`.

**`mail-accounts.service.ts`**
- `markNeedsReauth(accountId)` updated by PK only — defense in depth: added `eq(userIntegrationConnections.orgId, orgId)` to WHERE. Signature updated to `markNeedsReauth(accountId, orgId)`.

**`mail.service.ts`**
- All 3 `markNeedsReauth` call sites updated to pass `orgId`.

### New spec: `chat-bola-proof.spec.ts`
10 tests covering `ChatChannelMembersService` and `ChatReplyRemindersService`:
- DENY: `getChannel` returns `NotFoundException` (not 403) for cross-org channel id
- DENY: `listMembers` throws for cross-org channel
- DENY: `markRead` WHERE predicate binds orgId
- CONTROL: owner can mark their channel read
- DENY: 404 not 403 for cross-org oracle prevention (existence oracle test)
- DENY: `scheduleForMessage` member lookup binds orgId
- CONTROL: `scheduleForMessage` inserts only for owner-org members
- DENY: cross-org member collision cannot schedule reminders
- 2 parametrized 404-not-403 cases (getChannel, listMembers)

All 10 pass.
