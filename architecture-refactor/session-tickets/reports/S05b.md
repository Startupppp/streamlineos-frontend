### 3. Bounded async export work — void-after-commit fixes

**Status: CLOSED**

Two `void` patterns that caused DB writes to run after the request transaction committed (GUC gone → 42501) were fixed:

**`finance/controls/approvals.service.ts` line 183**
Before: `void this.dispatchDecisionNotification(...)`
After:  `await this.dispatchDecisionNotification(...)`

`NotificationDispatchService.emit` writes to `notification_outbox` INSIDE the ambient transaction (via `writeIntent(ambient.tx, input)`). Firing it void meant this write ran after the transaction committed, failing 42501. After the fix it completes within the same transaction. Errors are swallowed by the existing `.catch(logSideEffectFailure(...))`.

**`finance/ap/payment-run-executor.service.ts` line 201**
Before: `void this.postRunItemFxGainLoss(...)`
After:  `await this.postRunItemFxGainLoss(...)`

Also: inside `postRunItemFxGainLoss`, the inner `this.fx.postRealizedGainLoss(...)` was fire-and-forget (would run after `executeRun` returned). Now awaited inside a single try-catch that handles both rate-lookup failures and FX-posting failures. The method never throws; all errors are logged as warnings. Payment run execution is unaffected (items are never wrongly SKIPPED).

All 12 payment-run tests pass. All 3 finance/controls tenant-isolation tests pass.

`registerAfterCommit` fallback pattern is already correctly implemented in `versioned-catalog.service.ts` line 203-204:
```typescript

if (!deferred) await this.bustOrgEntitlementCache(orgId);
```
