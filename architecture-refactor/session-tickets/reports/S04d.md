# S04d — Bulk writes + Historical identity

## ROW 74: Bulk writes transactional, idempotent, bounded, per-ticket BOLA

**Findings:**

- `bulkUpdate` in `projects-tickets-query.service.ts` was NOT wrapped in a transaction. The membership check, status validation, ancestor CTE, and the actual `UPDATE` ran as separate queries with no rollback on partial failure.
- No per-ticket BOLA check. The authorization check only verified project-level membership. Cross-org ticket IDs were silently skipped by the WHERE clause; the requirement says they must return 404 semantics, not be silently ignored.
- No idempotency key on the controller handler.
- `importTickets` was already correct: `db.transaction()`, `@Idempotent("build.ticket.import")`, Zod `.max(500)`.
- `bulkUpdateSchema` already had `.max(100)` — the cap was in place.

**Fixes:**

1. **`ticket-status.util.ts`**: Changed `db: Db` → `db: Db | TenantTx` so `resolveValidTicketStatuses` can be called with a transaction client without a cast.

2. **`projects-tickets-query.service.ts`**: `bulkUpdate` now:
   - Runs membership check before the transaction (read-only, acceptable outside tx)
   - Enters `db.transaction(async (tx) => {...})` for all data operations
   - Verifies ALL `ticketIds` exist in `orgId + projectId` inside the transaction; throws `NotFoundException` (404, not 403) if any are missing
   - Calls `resolveValidTicketStatuses(tx, ...)` inside the transaction for status validation
   - Runs parent/ancestor checks and the final `UPDATE` on `tx`
   - Result is captured via outer `let updated` and returned after the transaction commits

3. **`projects-tickets.controller.ts`**: Added `@Idempotent("build.ticket.bulk-update")` to the `bulkUpdate` handler.

**Tests** (`projects-bulk-write-isolation.spec.ts`, 5 tests):
- DENY: cross-org ticket IDs resolve empty → NotFoundException
- CONTROL: same-org tickets → update returns count and IDs
- DENY: partial cross-org batch (1 valid + 1 missing) → NotFoundException
- DENY: non-member gets ForbiddenException before transaction starts
- CONTROL: org owner bypasses membership and enters transaction

## ROW 76: Historical identity in activity/comments/assignee

**Findings:**

- `getComment` joined global `users` for `authorName` and `authorImage`. `users` rows persist but the display name is not the org-specific canonical name from `organizationPeople`.
- `getActivity` (subresources service) joined `ticketActivityLog → organizationMembers → organizationPeople`. A fully removed member whose `organizationMembers` row is deleted would produce null display data even though `organizationPeople` might still exist.
- `resolveUserNames` (activity service) queried global `users` for assignee name changes in the activity log. No `orgId` scoping, not using the canonical display identity source.

**Fixes:**

1. **`projects-ticket-comments.service.ts`** (`getComment`): Replaced `leftJoin(users, ...)` with `leftJoin(organizationPeople, and(eq(organizationPeople.userId, ticketComments.userId), eq(organizationPeople.organizationId, u.orgId)))`. No `deletedAt` filter in the join (display purposes — departed members should still render). Uses `displayName` → `firstName + lastName` fallback chain (matches the activity pattern). Removed `users` import.

2. **`projects-ticket-subresources.service.ts`** (`getActivity`): Replaced the two-hop join (`ticketActivityLog → organizationMembers → organizationPeople`) with a direct join: `leftJoin(organizationPeople, and(eq(organizationPeople.organizationId, ticketActivityLog.orgId), eq(organizationPeople.userId, ticketActivityLog.userId)))`. Removed `organizationMembers` and `users` imports (now unused in this file).

3. **`projects-activity.service.ts`** (`resolveUserNames`): Added `orgId: string` parameter. Query changed from `users` to `organizationPeople` filtered by `organizationId = orgId` and `inArray(userId, unique)`. Display name built from `displayName → firstName+lastName → workEmail → userId` fallback chain. Call site in `logTicketFieldChanges` updated to pass `orgId`.

**Tests** (`projects-comment-identity.spec.ts`, 5 tests):
- CONTROL: active member — display name from `organizationPeople.displayName`
- CONTROL: departed member (no `organizationPeople` row) — comment returns, `author.name = null`
- DENY: comment not found (cross-org) → HttpException
- DENY: ticket not found (cross-tenant) → NotFoundException
- CONTROL: `firstName + lastName` fallback when `displayName` is null

**Tests** (`projects-activity-identity.spec.ts`, 4 tests):
- CONTROL: `displayName` from `organizationPeople` written into activity log `toValue`
- CONTROL: `firstName + lastName` fallback used when `displayName` null
- CONTROL: departed member (no `organizationPeople` row) — falls back to userId string
- DENY: separate orgId per caller (cross-tenant isolation in `resolveUserNames`)
