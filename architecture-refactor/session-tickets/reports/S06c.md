# S06c — Departed-Member Display + Huddle assertMember Fix

## What was done

### 1. `assertMember` security fix — `chat-huddles.service.ts`

`assertMember` previously checked `chatChannelMembers` by `channelId + userId` only, with no `orgId` binding and no check for active org membership. A member whose `organizationMembers.status` had become `LEFT` could still invoke huddle actions (start, join, mute, raise hand, screen share, kick, signal, invite) because the channel-member row persists after departure.

Fixed:
- Added `orgId: string` parameter; all 10 callers updated.
- Bound `chatChannelMembers.orgId = orgId` in the member lookup.
- Added `organizationMembers.findFirst` query with `status = "ACTIVE"`; returns 403 if absent.
- Bound `chatChannels.findFirst` to `orgId` (previously unchecked).

Evidence: `backend/src/modules/chat/chat-huddles.service.ts:42–67`

### 2. `resolvePeopleIdentities` — `person-seam.ts`

Added `avatarUrl: string | null` to `PersonIdentity` and to the select projection in `resolvePeopleIdentities`. Required for chat sender shape compatibility.

Evidence: `backend/src/modules/directory/person-seam.ts:278` (type), `backend/src/modules/directory/person-seam.ts:319` (select), `backend/src/modules/directory/person-seam.ts:355` (identity construction)

### 3. Departed-member display — `chat-message-timeline.service.ts`

`list`, `poll`, and `listThreadReplies` previously loaded sender identity via `with: { sender: { columns: { id, name, image } } }`, a direct join to the global `users` table without `orgId` re-assertion. A cross-tenant `senderId` would have leaked that user's name.

Replaced with `resolvePeopleIdentities` from `person-seam.ts`:
- Messages are loaded without the `sender` relation; `replyTo` loaded without nested sender.
- All `senderId` values from the page (including `replyTo.senderId`) are batch-resolved via `resolvePeopleIdentities(this.db, actor.orgId, subjects)`.
- A `senderFromIdentity` helper maps `PersonIdentity → { id, name, image }` for backwards-compatible response shape.
- A private `enrich` method is generic over any message-shaped object and applies the map.

Departed members resolve correctly: `organizationPeople` is not deleted when `organizationMembers.status` becomes `LEFT`, so `resolvePeopleIdentities` finds them. A cross-tenant senderId returns `{ id: null, name: null, image: null }` (unresolved), never a cross-tenant name leak.

Evidence: `backend/src/modules/chat/chat-message-timeline.service.ts` (full rewrite, 197 lines)
