# S07c Lane Report

## Resumable Ingestion — Chunk-level Checkpoint

### What was done

Added a `kb_ingestion_checkpoints` table and `KbIngestionCheckpointService` that give article and page indexing chunk-level resume capability. When embedding fails mid-document, the next outbox retry picks up from the last successfully embedded chunk rather than restarting from scratch.

**Flow:**
1. `embedWithResumption` (private method on `KbIndexingService`) calls `checkpoint.loadCheckpoints(orgId, contentType, contentId, contentHash)` at the start.
2. For each chunk: if a checkpoint row exists for that chunk index with matching content hash, use the cached embedding. Otherwise embed and call `checkpoint.saveCheckpoint(...)` which runs in a **fresh `runInNewTenantTransaction`** — committed independently of the ambient outbox transaction so it survives a rollback.
3. On successful completion: the final `db.transaction` deletes the old chunks, inserts the new ones, and calls `checkpoint.clearCheckpoints(tx, ...)` to clean up all checkpoint rows for that document atomically.
4. If the content changes between runs (different hash), stale checkpoints for previous chunk indices are ignored on load (hash mismatch) and cleaned up at commit.

**Files added:**

### Malware scan — NOT DONE

No malware scanning infrastructure is available in this environment. Implementing a fake scan would provide zero security value. A human must provide one of:
- A ClamAV sidecar accessible over TCP (e.g. via `clamscan` CLI or `clamd` daemon with the `nclam` Node client).
- A cloud scanning API (e.g. Google Safe Browsing file endpoint, VirusTotal Enterprise API).
- An S3 event + Lambda scan pipeline that quarantines files before the `kbArticleAttachments` row is created.

The upload path in `KbMediaService.upload` should call the scanner BEFORE the `this.storage.upload(...)` call (or immediately after, with a quarantine state) and abort with `ServiceUnavailableException` if the scanner flags the file. The storage key must not be committed to the DB until the scan passes.

## HNSW Plan Measurement

**Dev DB state:** `kb_article_chunks` has 0 live rows (`n_live_tup = 0`, `n_dead_tup = 2`). VACUUM ANALYZE cannot generate meaningful statistics and EXPLAIN ANALYZE on an empty table proves nothing about production behaviour.

**Structural findings from pg_catalog (measured against real DB as neondb_owner):**

| Property | Value |
|---|---|
| Index | `idx_kb_chunks_embedding_hnsw` |
| Definition | `CREATE INDEX idx_kb_chunks_embedding_hnsw ON public.kb_article_chunks USING hnsw (embedding vector_cosine_ops)` |
| RLS enabled | true (policy `tenant_isolation`, cmd ALL, PERMISSIVE) |
| RLS qual | `org_id = current_org_id()` |
| Index columns | `embedding` only — `org_id` NOT in the index |

**Risk:** The HNSW index covers only `embedding`. Under RLS, the `tenant_isolation` policy filters by `org_id = current_org_id()`. For ANN searches this means the planner will scan the HNSW index across ALL orgs (returning up to `LIMIT` candidates) and then apply the RLS filter. With many orgs, the ANN candidates may predominantly be from other orgs, causing the top-K to shrink below the requested limit (post-filter bleed). This is different from the "covering index" issue: an Index Only Scan is not the goal here; the HNSW is used for ordering only.

**Mitigation that does NOT require re-creating the index:** Include `org_id = $orgId` in the `WHERE` predicate (already done — all vector search calls include `eq(kbArticleChunks.orgId, orgId)`). pgvector can use the HNSW for ordering and apply the equality predicate as a post-filter. The effectiveness depends on tenant data density.

**Cannot measure:** The plan cannot be verified without live data. To measure:
1. Ingest at least one KB article or page with `OPENAI_API_KEY` (or equivalent) configured, so `kb_article_chunks` has rows.
2. `VACUUM ANALYZE kb_article_chunks;` as `neondb_owner`.
3. Inside a transaction as `streamline_app` with `SET LOCAL app.organization_id = '<orgId>'`, run:
   ```sql
   EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
   SELECT c.article_id, c.embedding <=> '[0.001, ...]'::vector AS distance
   FROM kb_article_chunks c
   WHERE c.org_id = '<orgId>'
     AND c.article_id IS NOT NULL
   ORDER BY c.embedding <=> '[0.001, ...]'::vector
   LIMIT 20;
   ```
   Expected: `Index Scan using idx_kb_chunks_embedding_hnsw`. If `Seq Scan` appears, add a partial HNSW index: `CREATE INDEX … WHERE org_id IS NOT NULL` (not possible since org_id is NOT NULL anyway) — or accept post-filter and increase `hnsw.ef_search`.

The script `backend/scripts/measure-hnsw-plan.mjs` is ready; it runs all the above steps automatically when data is present.
