### Content-hash dedup on source text

`sha256(article.contentText)` and `sha256(page.contentText)` are hashed directly from the raw source text before chunking, at the top of `indexArticle` and `indexPage` respectively. The hash is NOT taken from rejoined chunks. The existing test `"skips re-embedding when the stored hash matches the current article text"` uses `sha256(text)` where `text` is the raw source string, and the hash guard spec confirms the embedder is NOT called when the source text is unchanged. This is correct — rejoined chunk text would differ from source due to chunking boundaries, causing false re-embeds.

## Row 58 — Vector queries and the HNSW index (clustered re-measurement)

### Prior negative result (HNSW3) was fixture-specific

HNSW3 measured with uniform random 1536-dim vectors, which are near-orthogonal in high-dimensional space. The test query vector `[0.1, 0.001, ...]` did not land near org-b's cluster because no cluster existed — every org's rows were uniformly distributed across the hypersphere. The HNSW traversal (and iterative scan with up to 20,000 candidates) found 0 org-b rows. That result was valid for the fixture but cannot be generalized to real semantic embeddings.

### New measurement — semantically clustered vectors

**Setup:** All existing seeded rows deleted. 30,000 rows reseeded using `src/scripts/seed-hnsw-clustered.mjs`:

| Org | Rows | Vector distribution |
|---|---|---|
| seed-org (`73e5076a…`) | 15,000 | Near random unit centroid A |
| org-b (`c5b82e53…`) | 7,500 | Near random unit centroid B |
| org-c (`ed6e823a…`) | 7,500 | Near random unit centroid C |

Each chunk's embedding = centroid + U(-0.025, 0.025) per dimension (σ ≈ 0.05). Centroids A, B, C are independently generated random unit vectors — near-orthogonal in 1536-dim space (expected cosine similarity ≈ 0). `VACUUM ANALYZE` run after insert.

**Query vector:** Mean of all org-b's embeddings (centroid B, derived from `avg(embedding)` as `streamline_app`-role owner query). This simulates a user query that is semantically close to their own org's content.

All measurements taken as `streamline_app` with `SET LOCAL app.organization_id = '<org-b>'` inside a transaction.

### Results

| Scenario | Rows returned (org-b) | Shared buffers | Plan |
|---|---|---|---|
| (a) Plain ANN, RLS post-filter | **20** | **258** | Index Scan on `idx_kb_chunks_embedding_hnsw`, 1 Index Search |
| (b) MATERIALIZED fence (`app.search_kb_chunk_ids`) | **20** | **22,688** | ProjectSet (sequential scan + sort) |
| (c) Iterative scan (`SET LOCAL hnsw.iterative_scan = relaxed_order`) | **20** | **227** | Index Scan on `idx_kb_chunks_embedding_hnsw`, 1 Index Search |

Cross-check: seed-org plain ANN with the org-b query vector returns **0 rows** — correct, seed-org's content is not near org-b's centroid, and RLS filters out all HNSW candidates (which are org-b rows near the query).

### What the numbers mean

**Scenario (a) — plain ANN now works.** With semantically clustered vectors, the HNSW graph traversal navigates into org-b's region because the query vector lies there. All 20 candidates are org-b rows; the RLS post-filter passes all 20. Buffers: 258. This is why real-world users rarely observe the under-retrieval bug: in production, queries are semantically close to the querying org's own content.

**Scenario (b) — MATERIALIZED fence is correct but 88× more expensive.** It abandons the HNSW index entirely, sequentially scans org-b's 7,500 rows, and sorts by distance. 22,688 buffers. Cost grows linearly with tenant size regardless of embedding clustering quality. Migration 0703 is still correct.

**Scenario (c) — iterative scan works with clustered vectors.** 227 buffers — fewer than even the plain ANN because iterative_scan's relaxed_order mode terminates as soon as 20 candidates survive the RLS filter, so fewer heap fetches are needed. The Neon platform restriction (cannot set `hnsw.iterative_scan` in a function's SET clause — 42501) is unchanged; session-level `SET LOCAL` is the only viable path.

### Why iterative scan cannot replace the fence today

`app.search_kb_chunk_ids` is a SECURITY DEFINER function. `hnsw.iterative_scan` cannot be set inside it (42501 on Neon, same class of restriction as `ALTER FUNCTION … LEAKPROOF`). All workarounds tested in HNSW3 (PL/pgSQL `set_config`, dynamic SQL with `RETURN QUERY EXECUTE`) were also tested against the Neon cluster and all fail. Session-level `SET LOCAL` before calling the outer ANN query would work, but the outer query runs under RLS — it is NOT inside the SECURITY DEFINER function. That means the outer query is back to the original post-filter problem: it uses the HNSW index globally, applies RLS as a post-filter, and would return 0 rows for org-b on the random-vector fixture (the correctness bug that migration 0703 was written to fix).

The fence is the only solution that is correct regardless of how well the embeddings cluster.

### Recommendation

**Keep migration 0703 (MATERIALIZED fence).** It is the only correctness guarantee that does not depend on embedding quality. For production tenants with well-clustered semantic embeddings (the normal case), plain ANN performs well and the fence provides the safety net when anomalous query vectors arise.

If tenant sizes reach a scale where 22,688 buffers per search is unacceptable (rough threshold: 500k+ chunks per tenant, which implies 75MB+ sequential scans), the correct next step is partitioning `kb_article_chunks` by `org_id` so each partition gets its own HNSW index. Per-org partial HNSW indexes are not feasible at the current schema level because partial indexes require static predicates, and the number of orgs is unbounded.

### Row 58 disposition

The correctness bug (0 rows returned for minority tenant) is fixed by migration 0703. The re-measurement with semantically clustered vectors confirms that iterative scan produces correct and efficient results (227 buffers) when embeddings are well-clustered, and that the MATERIALIZED fence is a safe but expensive fallback (22,688 buffers) for all cases.

**This row can be ticked if the acceptance criterion is "correctness guaranteed."** The fence provides that. The linear-scan cost is a known and documented trade-off, not an open bug.
