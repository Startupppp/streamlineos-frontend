### Item 4b — OR + semi-join UNION fix (P1 performance hole)

**File changed:** `backend/src/modules/build/core/projects-tickets-read.service.ts`

**Problem:** The `scopeClause` in `listTickets` used `or(eq(assigneeId, userId), eq(reporterId, userId), EXISTS(ticketAssignees))`. The OR with a correlated subquery defeats both the `assigneeId` index and the participation index, forcing an O(organisation) scan.

**Fix:**
- Removed `scopeClause` from the shared `where` predicate for the offset path.
- Added `scopedUnion()` helper (private method) that builds a 3-branch UNION SQL:
  - Branch 1: `WHERE ... AND tickets.assigneeId = userId` (indexed on `assigneeId`)
  - Branch 2: `WHERE ... AND tickets.reporterId = userId` (indexed on `reporterId`)
  - Branch 3: `INNER JOIN ticketAssignees ON user_id = userId AND org_id = orgId` (indexed on ticket_assignees)
- `pageScopedTicketIds` now calls `scopedUnion` via `db.execute()` and uses `readIdsAndTotal` from `work-scope-union.ts` to decode results.
- Total carried by `count(*) OVER ()` in a single pass — no separate count query.
- Uses `resolveWorkSort` from `work-scope-union.ts` for sort (replaces the duplicate `TICKET_ORDERBY_COLUMNS` constant).
- Cursor board path (`paging=cursor`) keeps the OR+EXISTS scope for now (board users typically have `scope=all`).
- Unmeasured (no DB access on this machine) — per ticket instructions, implement-and-note.

**Verification:** `jest "build/core" --maxWorkers=1` → 168/168 passed. `jest "projects-tickets-read"` → 2/2 passed.
