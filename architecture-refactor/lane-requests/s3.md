## 1. c25-03 — four navigation gates name a permission no route enforces

`pnpm check:navigation-permissions` (new, `backend/src/scripts/check-navigation-permissions.mjs`)
reproduces this on demand and names every offender. **Re-run it rather than trusting this table.**

The defect in one sentence: the sidebar shows a destination to whoever holds key A, and the endpoints
behind it enforce key B. Holding A shows a link that 403s; holding B works but the link is hidden.
Neither is visible in review because both keys exist in both catalogs.

| Nav gate | Where | The route actually enforces | Destinations affected |
|---|---|---|---|
| `accounting:view` | `frontend/components/layout/sidebar/sidebar-nav-groups-finance.ts:9` (group) and every route from `:16` to `:259` | `accounting:read` and its per-surface siblings (`accounting:receivables:read`, `accounting:journal:read`, `accounting:periods:read`, `accounting:settings:read`, …) | ~40 |
| `accounting:report` | `sidebar-nav-groups-finance.ts:273, 279, 285, 291, 297, 303` | `accounting:reports:read` | 6 |
| `crm:deals:approve` | `sidebar-nav-groups-crm.ts:107` → `/crm/deals/approvals` | `crm:deals:read` (`backend/src/modules/deals/deals-approvals.controller.ts:53`) | 1 |
| `hr:goals:view` | `sidebar-nav-routes-hr-employee-experience.ts:72` → `/hr/goals` | `hr:performance:view` (`backend/src/modules/hr/performance/performance.controller.ts:65`) | 1 |

**Which side is wrong is not symmetric.** `accounting:view` and `accounting:report` live in
`permissions/shared.ts:17,30` and are enforced by **zero** routes, while `accounting:read` and 23
sibling keys in `permissions/accounting.ts` are enforced by the real controllers. The nav is the
stale side; move each destination to the key its own endpoint checks. That is per-destination work —
`/accounting/banking` and `/accounting/taxes` do not read the same key — so it is a real frontend
task, not a find-and-replace, which is why S3 did not guess it.

`hr:goals:view` and `crm:deals:approve` are granted by role templates
(`role-templates.constants.ts:115, 210`) but enforced nowhere, so they currently confer nothing.

**Not blocking anything of S3's** except wiring `check:navigation-permissions` into CI, which stays
unwired while it exits 1.

## 3. c25-02 — two handlers resolve the caller's DataScope and never apply it

`pnpm check:scope-application` (new, `backend/src/scripts/check-scope-application.mjs`) reproduces
this on demand: **119 scope resolutions across the codebase, 117 applied, 2 not.** Both are below.

The shape is always the same, and it is worse than a missing check: the handler resolves the scope,
refuses only `"none"`, and then runs a query that takes no scope. A reviewer sees scope handling and
stops looking. The `=== "none"` guard is the half that does not matter — `own` and `all` behave
identically once it passes.

### 3a. `LeavesService.analytics` — `backend/src/modules/hr/time/leaves.service.ts:211-221` (HR)

Handed to S3 by the session brief, confirmed at source and now confirmed by the checker.

`resolveLeavesViewScope` resolves `hr:leaves:approve`, `:213` refuses only `"none"`, and `:218` calls
`this.queryAnalytics(u.orgId, year)` — signature `(orgId: string, year: number)` at `:223`. There is
no scope parameter to thread. An `own`- or `team`-scoped approver receives **org-wide leave analytics
broken down by department**.

**The change:** give `queryAnalytics` a `scope: DataScope` parameter and apply
`applyScope(scope, u.orgId, u.userId, { ownerColumn: leaveRequests.userId })` as a SQL predicate in
each of the four aggregates, rather than filtering after aggregation. Note `leaves-scope.ts:21`
already has `leaveApprovalScope(scope, orgId, actorUserId)`, which is the approver-side predicate and
is probably the right one to reuse.

**Not a cache bug.** The key at `:217` is `` `${scope}:${year}` ``, so the cache is merely finer than
the data it stores. That interpolation is also what made the method read as careful.

*What* an `own`-scoped approver should see is a genuine product question. *Whether* the endpoint
honours the scope it just resolved is not, and today the answer is no.

### 3b. `DashboardLeaveService.getPendingApprovals` — `backend/src/modules/dashboard/dashboard-leave.service.ts:80-96` (unowned)

**New, found by the checker.** Same defect, same module family, not previously reported.

`resolveLeavesDashboardScope` at `:81`, `:82` refuses only `"none"`, and then `:92-95` counts
`leaveRequests` filtered on `orgId` and `status = 'PENDING'` and nothing else. The `isApprover`
boolean at `:85` selects which *resignation* statuses to count; it does not scope the leave count. So
an `own`-scoped member's dashboard shows the **organisation's** pending-leave count.

**The change:** thread the scope into the count as
`applyScope(scope, orgId, u.userId, { ownerColumn: leaveRequests.userId })`, or use the same
approver predicate 3a settles on — these two should be fixed together and agree, since they answer
the same question on two surfaces.

### Fix these and the check goes green

Nothing else in the codebase resolves a scope without spending it, so `check:scope-application` can
be wired into CI as a required step the day these two land. Until then it exits 1 and is not wired,
for the same reason `check:route-classification` is not.

**Three shapes are deliberately not reported**, because the first version of the checker reported all
three and all three were wrong: a ternary that returns the scope in its else branch
(`attendance-scope.ts:24`), a guard and a surviving use on one line
(`employee-mutations.service.ts:173`), and a comparison against a *different* scope value
(`leads-reports.controller.ts:79`). All are pinned in the self-test.

## 4. Pre-existing red suites, reported rather than fixed

`NODE_OPTIONS=--max-old-space-size=8192 pnpm -C backend exec tsc --noEmit` is **clean**. These are
test failures on `main` that S3 did not cause and deliberately did not fix.

### 4a. A cache double went stale a day ago — 7 suites, ~65 tests, in S3's own territory

Every failure in `src/modules/access` is one of two lines: **123 × `this.cache.cachedForOrg is not a
function`** and **28 × `this.cache.invalidateForOrg is not a function`**. The real `CacheService` has
both (`common/cache/cache.service.ts:167,195`); the `{ provide: CacheService, useValue: {…} }`
doubles in the specs stub only `cached` and `invalidate`. Suites: `access.service.spec`,
`entitlements.service.spec`, `access-cache-scope`, `rbac-resolution`, `warm-cold-parity`,
`access-membership-coherence`, `access-resolution-cost`. The same cause reds
`org-hierarchy-cost-centers.service.spec` in `modules/organization`.

Both sides landed 2026-08-26: `cachedForOrg` reached `cache.service.ts` in `3b1c7cd7` and
`entitlements.service.ts` in `a9166e06`, and no double was updated.

**S3 did not patch the doubles, on purpose.** Doing so would ratify the source change, and the
question that should be answered first is whether `CACHE_KEYS.*` → `*ForOrg` should stand at all:
that migration was tried across ~50 sites once before and **fully reverted**, because the
`CACHE_KEYS` factory is already tenant-safe. That is a call for whoever owns `a9166e06`, not
something to settle by repairing the tests around it. Whichever way it goes, a double that does not
invoke its fetcher would void every assertion inside it, so the repair is not a one-liner.

### 4b. `backfill-slugs-exist.spec.ts`

`src/modules/rbac/__tests__/backfill-slugs-exist.spec.ts` fails on
`0226_repair_crm_module_role_grants.sql: CRM_ADMIN`, a migration added after the spec's
`KNOWN_INERT_BACKFILLS` list was written. The list needs the new entry, or the migration needs to
name a slug the seeder produces. Owner: whoever added `0226`.

### 4c. Organization invitation suites

`invitation-decline`, `invitations-plan-limit`, `invitations-state-machine` and
`organization-member-status` fail in `modules/organization/core`. Not investigated — S3 changed only
decorators in that folder, and none of those specs imports a controller.
