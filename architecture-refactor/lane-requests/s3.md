## 1. Still open, and not S3's to decide

### 1a. `listMembersSchema` — clamp or reject?

`src/modules/organization/core/dto/organization.schemas.spec.ts` expects
`listMembersSchema.parse({ limit: 101 })` to **throw**, but `pageSizeField`
(`common/pagination/list-query.schema.ts:20`) now **clamps** to the ceiling. S4 has an edit in the
working tree changing the assertion to expect clamping, which looks right — the decision is theirs
(c13, one list contract) and S3 left it alone.

### 1b. Seven uniqueness-conflict checks and their partial indexes

`check:record-access` classifies these separately from record reads and does not gate them, because
whether a soft-deleted row still holds its slug depends on whether that table's unique index is
partial — a per-table question:

`hr/directory/employee-onboarding.service.ts:94` · `kb/wiki/kb-spaces.service.ts:96,158` ·
`organization/core/organization-settings.service.ts:72,76` ·
`organization/hierarchy/org-hierarchy-cost-centers.service.ts:118,152`

If the index is partial, each needs `isNull(x.deletedAt)` or a deleted row blocks a name nobody can
see. If it is not, they are correct as they stand.

### 1c. The tenant predicate on 148 reads

`pnpm -C backend check:record-access --tenant` lists every read on a tenant table with no application
tenant predicate. It is **reported, not gated**: RLS adds `org_id = app.current_org_id()` in the
database, and the public, portal and platform paths have no tenant in context by design. Turning 148
sites into a registry would be a category wearing a list's clothes. Worth a pass by each owning
module, not a blanket rule.
