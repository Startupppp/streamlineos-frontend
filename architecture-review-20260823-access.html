Where the architecture is genuinely good

You asked to be told when the architecture is fine. Most of this surface is. These are deep modules doing real work behind small interfaces, and they should not be touched:

authorize()

access/authorize.ts:12
51 lines. One call — (resolver, ctx, key) — and behind it sit plan gating, owner bypass, personal-token scope filtering and full RBAC resolution. Textbook depth.

assertPermissionsGrantable()

common/rbac/grantability.ts:120
One function encodes org-only namespaces, hold-what-you-grant, reserved propagation, rank ceilings and cross-module containment. Six call sites, one rule set. High leverage.

STANDING table

module-access/module-standing.ts:35

isStructuralOrgAdmin()

Org-admin is an active membership row, never a permission key. The one place the AC-04 lesson was correctly institutionalised.

One navigation model

components/layout/sidebar/sidebar-nav-items.ts:65
Sidebar, mobile nav, command palette and product switcher all consume one filtered tree. Four consumers, zero duplicated filtering.

One module-access screen

features/module-access/module-access-page.tsx
Ten routes, each a six-line adapter over one parameterised page. Exactly the thin-adapter-over-deep-module shape the ladder PRD asked for.

Invitation state transitions

organization/core/*
Every accept / decline / cancel / resend / role-change uses a conditional UPDATE plus an affected-row check, with a row lock and an in-transaction seat check. Correct, and better than the ownership module (C6).

Client access seam

Server and client both read GET /me/access. No permission is derived from a JWT or session claim anywhere in the frontend.

Grant union

access/access-permission.resolver.ts:57
Roles, group roles, delegations, per-person grants and module ownership merge in exactly one function. One seam for multi-level access — which is why C5 matters.

C1

“Which permission keys belong to this module?” has three answers

Strong
Files
  • common/rbac/module-vocabulary.ts:32–39 — the declared seam
  • modules/rbac/permissions/catalog.ts:96–101 — moduleScopedPermissions
  • common/rbac/grantability.ts:94–103 — buildPermissionModuleMap
  • modules/module-access/module-access.service.ts:81–83 — private naive copy
  • modules/module-access/module-access-groups.service.ts:79–81 — private aware copy
Problem

The rule “Home owns chat, mail, calendar and notifications” is stated once, in namespacesForModule. But the question is answered in four different places, and module-access.service.ts answers it by slicing the first segment itself — the exact thing the rule warns against. I measured the three answers for Home against the live catalog of 673 keys:

The 27 is not a rounding difference: namespacesForModule("home") returns the extra namespaces and forgets Home's own, so home:access:view and home:access:manage fall out of the set that seeds the HOME_MODULE_OWNER and HOME_MODULE_ADMIN templates.

What it costs today
  • The Home access screen's permission picker offers 2 keys. A Home module owner cannot grant a single chat, mail, calendar or notification permission through it — the write is rejected by module-access.service.ts:299 as an unknown key.
  • A Home module owner is refused the view action on their own module, because the seeded template never gave them home:access:view.
  • setRolePermissions computes which old keys to delete with the naive slicer, so any stored Home grant survives a save that was meant to replace it.
Solution

Make the module-vocabulary module the only place that can answer the question, and make it answer completely: a module's namespaces include its own. The two private moduleOf copies are deleted and their call sites import the shared one.

Benefits

Locality: adding a nineteenth module, or moving a namespace under a different owner, becomes one edit rather than four that must agree. Leverage: the catalog filter, the role seeder, the grantability check and the access screen all become correct by construction rather than by coincidence of key naming. Tests: one property test — “for every managed module, the three answers agree” — replaces the per-module cases that do not exist today. There is currently no test that exercises the Home module namespace at all.

C2

Module ownership expands past the org-only bar — and a test already says so

Strong
Files
  • access/access-permission.resolver.ts:297–301
  • common/rbac/grantability.ts:39–49 — the bar it bypasses
  • access/__tests__/home-surfaces-universal.spec.ts:165–169 — FAILING
Problem

chat:org-settings:manage is declared org-owner-and-org-admin-only, and assertPermissionsGrantable refuses it on every grant path including the owner's own. But module ownership is not a grant path — it is a resolution path. The resolver expands a module ownership row into every key the module owns, at scope all, with no filter: 

for (const { moduleKey } of ownershipRows) {
  for (const key of moduleScopedPermissions(moduleKey)) {
    merge(key, "all");          ← no isOrgOnlyPermission check
  }
}

Because Home owns the chat namespace, appointing a Home module owner hands them organisation-wide chat settings. The repository already knows this: the spec at home-surfaces-universal.spec.ts:165 asserts the opposite, its own docstring explains precisely this failure mode — and it is red on main today. Only the intent shipped; the enforcement did not.

Solution

Move the org-only bar from the grant paths into the merge itself. Delegability is already a property of the key, not of the actor (isDelegablePermission takes no actor) — so the resolver is where it belongs. Once the resolver refuses to produce an org-only key for a non-structural principal, the state becomes unrepresentable rather than merely guarded.

Benefits

Locality: one invariant in one function instead of four grant-path guards that a fifth path can walk around — which is exactly what happened here. Leverage: every future grant source (a new delegation kind, a group expansion, an imported role) inherits the bar for free. Tests: the existing failing spec becomes the regression net; no new test shape is needed.

C3

The ladder's view rung and manage rung resolve authority two different ways

Strong
Files
  • module-access/module-access.helpers.ts:44–69 — assertModuleAccessPolicy
  • module-access/module-standing.ts:194–245 — the seam, half-consumed
  • module-access/module-access.service.ts:170 · module-access-groups.service.ts:152, 175 — three wrappers
Problem

The PRD's promise was that a consumer asks one question — what is this person's standing in this module — and gets owner, admin, member or none. That function exists (resolveModuleStanding) and nothing in production calls it; its only consumer is its own spec. Production calls the narrower resolveModuleManagementStanding, and only for the manage action.

The view action never consults standing at all. It checks org owner, then structural org admin, then looks for the literal key <module>:access:view in the resolved set. A module owner passes manage structurally and passes view only because their seeded template happens to contain a key that starts with the module's own name — which, for Home, it does not (C1). Two mechanisms answering one question, agreeing by coincidence.

On top of that, three wrappers exist for the same check: assertModuleAccess, assertAccess and assertOwnershipRights — the last of which re-implements the isModuleEnabled precondition by hand instead of going through the policy.

Deletion test

Delete module-standing.ts and the STANDING table scatters into three services — complexity concentrates at each call site. It earns its keep. Delete the three assert* wrappers and nothing concentrates; they are pass-throughs. That is the shallow half.

Solution

Promote ModuleStanding to the module's whole interface. Both actions derive from it — manage from canManageAccess, view from “standing is at least admin, or the caller holds the view key”. The three wrappers collapse into one, and the ownership gate stops re-deriving its own precondition.

Benefits

Locality: “what may this person do in this module” has exactly one implementation, and the STANDING table becomes the only thing a reviewer must read. Leverage: the eight modules the ladder PRD still has to onboard inherit both rungs automatically instead of needing a key that happens to be named right. Tests: the existing module-standing.spec.ts already tests the full four-level answer — today it is testing code nobody runs. Routing production through it converts a dead spec into the ladder's regression net.

C4

Four copies of the rank resolver — and only one filters expired assignments

Strong
Files
  • common/rbac/resolve-actor-rank.ts:11 — “canonical”
  • modules/rbac/rbac.service.ts:218 — private copy
  • modules/rbac/role-permission.service.ts:91 — private copy
  • modules/module-access/module-access.helpers.ts:71 — hardened copy
Problem

The same join — role assignments → memberships → roles, reduced to a best rank and an allowed-module set — is written four times. They are not identical. The module-access copy filters organizationMembers.status = 'ACTIVE' and expiresAt IS NULL OR expiresAt > now(). The other three filter neither.

The membership predicate is defence in depth — a suspended member cannot reach these routes anyway. The expiry predicate is not. An active member whose elevated role assignment has already expired still contributes that role's rank to assertGrantable in role-permission.service and to both discovery endpoints in rbac.service. The rank ceiling at grantability.ts:174 is the thing that stops someone creating or editing a role at or above their own authority — and it is being fed a stale number.

Deletion test

Delete the three copies and the predicate concentrates in one place. That is a clean “yes”.

Solution

One rank resolver, carrying the strictest predicate of the four. The private copies are deleted and their three call sites import it.

Benefits

Locality: “what counts as a live role assignment” is one predicate. Today, fixing it means finding four queries and knowing they were meant to be the same. Leverage: every authority ceiling in the product tightens at once. Tests: the resolver becomes independently testable with a stub Db — “an expired assignment confers no rank” is one case, and it currently has nowhere to live.

C6

Ownership transfer: one table, two state machines, and terminal writes with no predicate

Strong
Files
  • ownership/ownership-transfers.service.ts:45, 147 — initiate ×2
  • ownership/ownership-transfer-response.service.ts:70, 365, 461 — accept · decline · cancel
  • …response.service.ts:268, 355, 409, 506 — ID-only terminal writes
  • ownership/ownership-transfers.service.ts:417 — expireStaleTransfers
Problem

Organization transfer and module transfer share one table and one lifecycle (PENDING → ACCEPTED | DECLINED | CANCELLED | EXPIRED) but are written twice. Two initiation methods of ~130 lines each differ only in what they read; two apply methods of ~80 lines each differ only in what they flip. The genuinely different part — organization flips isOwner and the structural role, module upserts module_ownerships and swaps the owner role — is a handful of lines buried in the middle of each.

Underneath, every terminal write is WHERE id = ? with no status predicate and no affected-row check. Accept survives this because both apply methods take SELECT … FOR UPDATE and re-assert the business invariant inside the transaction — a second accept fails with “initiator is no longer the owner”. Decline and cancel do neither. Their status check runs on an unlocked read outside the transaction, so an accept that commits during that window is overwritten: ownership has moved, and the transfer row says DECLINED.

expireStaleTransfers also busts only the transfers namespace, not moduleAccessOwnership — which initiateModuleTransfer does bust. Expiry leaves the module-access cache stale until TTL.

Solution

One transfer-lifecycle module owning the state machine: a single transition operation that does the conditional update and checks the affected-row count, plus the cache and notification obligations. The two scopes become two adapters behind that seam — each supplying only “what to read to validate” and “what to flip on apply”.

Benefits

Locality: the racy write pattern is fixed once for five call sites instead of five times. Adding a third transferable thing costs an adapter, not a fifth copy of the lifecycle. Leverage: the caller stops needing to know which caches to bust and whether to bump the permission version — the invitation module already gets this right, and this is the same shape. Tests: concurrency becomes testable at the seam — “two responses to one transfer, one wins” is one test instead of four near-duplicates. Today expireStaleTransfers has no unit test at all.

Two representations of “module owner”, kept in step by a function that silently gives up

Worth exploring
Files
  • ownership/module-owner-role.helper.ts:23–26, 52–54 — silent skips
  • rbac/assert-role-assignment.ts:19 — org owner short-circuit
  • rbac/seed-system-roles.ts:104–124 — which owner roles exist
  • module-access/module-standing.ts:151 — what standing actually reads
Problem

“Module owner” is stored twice: as a lifecycle row in module_ownerships, and as a *_MODULE_OWNER role assignment carrying the permission grants. Standing reads only the first; the resolved permission set comes from the second. Three ways they diverge:

  • The sync helpers no-op when the role is not seeded — assign logs a warning, revoke says nothing at all. The ownership row flips and the outgoing owner keeps their grants.
  • assertMayAssignRole returns immediately for an org owner, so POST /roles/:roleId/members can attach HR_MODULE_OWNER to someone who is not the module owner. Nothing rejects a MODULE_OWNER-rank role on that path.
  • Owner roles are seeded for the 14 access-managed modules; admin roles for the 18-module union — so KB and CHAT have an admin rung with no owner rung.
Solution

Make the ownership row the only writer of the owner role, and make failure loud: if the role is missing, the transfer fails rather than half-applying. Reject MODULE_OWNER-rank roles on the generic role-assignment path for everyone, org owner included, so the ownership service is the only door.

Benefits

Locality: one writer means “who owns this module” has one answer you can trust from either table. Leverage: every consumer of standing and every consumer of the resolved permission set agree without either having to know about the other. Tests: “ownership row and owner role never disagree” becomes a single invariant test; today the divergence is only observable in production.

C8

Email canonicalisation lives in three DTOs, and Postgres does not back it up

Strong
Files
  • users/dto/users.schemas.ts:50–56 — inviteEmailSchema, correct
  • users/dto/users.schemas.ts:106 — importUsersRowSchema
  • users/dto/users.schemas.ts:126 — createUserSchema
  • db/schema/common/auth.ts:106 — users.email .unique(), case-sensitive
Problem

Identity canonicalisation is a property of the identity, but it is implemented as a Zod transform on one of three DTOs. inviteEmailSchema trims and lowercases; importUsersRowSchema and createUserSchema are bare z.string().email(). Solution

One canonicalisation, owned by the identity module and applied where the email becomes an identity rather than at each request shape — with a case-insensitive unique index in Postgres as the invariant that makes a miss impossible rather than merely unlikely.

Benefits

Locality: a fourth entry point (HR onboarding, SSO provisioning, a CSV importer) cannot forget a rule it never has to remember. Leverage: the pending-invitation uniqueness index and the seat count both start meaning what they say. Tests: testable as one property — “these five entry points produce the same identity for these eight spellings” — instead of per-DTO assertions that only cover the DTO that had the bug.

C11

Nothing owns “what may happen to this invitation next”

Worth exploring
Files
  • organization/core/invitations.service.ts:155, 353
  • organization/core/invitation-lifecycle.service.ts:44, 150
  • organization/core/invitation-acceptance.service.ts:126
  • organization/core/invitations-read.service.ts:31, 39 — synthesised “expired”
Problem

The individual transitions are correct — conditional updates, affected-row checks, row locks, in-transaction seat reservation. What is missing is a module that owns the machine. The predicate “status = PENDING AND accepted_at IS NULL AND expires_at > now()” is restated in five places, and the list view synthesises an EXPIRED state that nothing ever writes, so the enum value and the derived state disagree about what expiry means.

The three services also split by size rather than responsibility: InvitationsService and InvitationAcceptanceService each pass the deletion test — the authorization difference between an admin-authenticated path and a public-token path is a real seam. InvitationLifecycleService does not; its three methods repeat the admin-mutation shape already in InvitationsService.

Solution

One invitation-state module that answers “what may happen next” and performs the guarded transition; the two authorization-shaped services keep their seam and call it. Expiry becomes one definition rather than an enum value and a synthesised filter.

Benefits

Locality: changing the expiry rule is one edit rather than six. Leverage: this is the same lifecycle shape as C6 — get it right here and the ownership transfer machine can adopt it. Tests: the transition table becomes directly testable without a database mock, which is currently the only way to reach it.

C12

The “six standings, no custom roles” model is not what the code offers

Speculative — needs your decision
Files
  • rbac/roles.service.ts:274 · 584 — createRole, cloneTemplate
  • rbac/roles.controller.ts:67, 151 — live routes
  • module-access/module-access-groups.service.ts:329 — createGroup, also a role
  • rbac/rbac.service.ts:46, 211–215 — checkActorAccess
Problem

The constitution says there are exactly six standings and no custom roles. The code ships three ways to make a new one: POST /roles, POST /roles/templates, and module role groups — which are roles rows with a moduleKey. Module role groups look like the right product surface; the two org-level ones may be drift.

There is also a seventh standing hiding in plain sight. Every route on /roles and /rbac is gated on the key settings:rbac:manage, and RbacService.checkActorAccess re-derives authority from that same key rather than structurally. That is the pattern is-structural-org-admin.ts:14–19 explicitly exists to prevent — “RBAC administrator” is a de-facto standing that the six-standing model does not name.

Solution

This is a product decision before it is a refactor, which is why it is marked speculative. Either the model gains a named RBAC-administrator standing and the constitution is corrected, or the roles surface becomes structurally gated and the two org-level creation routes are retired in favour of module role groups. I would not touch it without your call.

Benefits

Locality: the documented model and the code stop disagreeing, so the constitution can be trusted as the specification an agent reads first. Leverage: every future access question has one authority to resolve against. Tests: “these are the only standings” becomes an assertable invariant rather than prose.
