# Managed Product code audit — 2026-10-12

## Decision rule and scope

This audit compares current source code with the Manage Product and product-discovery requirements in `docs/build-module`. Markdown status labels and checkboxes were not used as evidence of completion. The scope is the managed-product directory, overview, feedback, insights and discovery, goals, linked projects, roadmap, releases, settings, and the product-specific value promises numbered 71–76. CRM, Timesheets, Accounting, generic project delivery, and the other Build modules are excluded except at a product-owned link or permission boundary.

**Result: not complete.** The main screens and service families exist, but the confirmed gaps below prevent completion. Source review establishes implementation state, not deployed behavior. An item labelled *present* has a concrete code path; it is not an end-to-end acceptance claim.

## Confirmed implementation backlog

The following are source-confirmed gaps, not copied Markdown TODO status. Complete each item and verify the stated result.

### P0 — Access and model integrity

1. **Enforce product membership in every product-scoped read and write.** `ManagedProductListService.listManagedProducts` receives `_callerMembershipId` and never uses it; its query filters only by organization. `ManagedProductsService.getManagedProduct`, summary, linked projects, discovery and members endpoints likewise receive an organization ID without product membership context. By contrast, `scope-directory.service.ts` filters product entries through `managedProductMemberships`. Centralize the product reach decision with the intended unrestricted-manager exception, apply it consistently to list, facets, detail, summary, releases, members, goals, feedback, opportunity/score/evidence/review, linked-project and roadmap endpoints, and test a member of product A trying product B, direct IDs, filters, mutation IDs and cache reuse. Evidence: `backend/src/modules/build/managed-products/managed-product-list.service.ts:36-76`, `managed-products.controller.ts:60-73`, `managed-products.service.ts:76-77`, `scope-directory/scope-directory.service.ts:176-204`. Contract: `acceptance/sidebar/04-access-lifecycle-prd.md:35-42`.

2. **Implement the accepted many-to-many project/product association.** The schema and linking command store one `projects.managedProductId`, and a new link replaces the previous product. Linked-project reads, directory counts, overview counts and discovery acceptance all use that singular field. The accepted model specifies `build.project_managed_products`, a unique project/product pair and one explicit primary per project. Add the relation and migration/backfill, update commands and authorized selectors, preserve existing links during a move, update all rollups/filters/roadmap acceptance, and test one project linked to two products with one primary plus unlink without project deletion. Evidence: `backend/src/db/schema/build/core.ts:46`, `backend/src/modules/build/core/project-crud/projects-write.service.ts:395-465`, `backend/src/modules/build/managed-products/managed-products-linked-projects.service.ts:105-107`, `managed-product-summary.service.ts:116-135`. Contract: `architecture/07-architecture-data-api-cache-ai.md:215,605`.

3. **Close scope validation on linked sources.** `EvidenceService.add` validates Feedbucket evidence against the selected product, but the `feedbackPosts` branch checks only organization and record ID. Opportunity acceptance and outcome-review creation accept any same-organization goal ID without checking its product link. Define the allowed cross-product linking rule, require explicit authorized handoff where applicable, enforce it on the server, and test cross-product IDs. Evidence: `backend/src/modules/build/managed-products/discovery/evidence.service.ts:47-87`, `discovery/acceptance.service.ts:122-141`, `discovery/outcome-reviews.service.ts:142-158`.

### P1 — Incorrect or incomplete product workflows

4. **Fix the Insights-to-Projects status links.** Insights writes `filterStatus=ACTIVE|COMPLETED`; the destination reads `pp_status`. Both cards open an unfiltered list. Use the destination's canonical parameters and test click, URL, request and matching rows. Evidence: `frontend/features/build/managed-products/product-insights-panels.tsx:142-152`, `projects/use-product-projects-page.ts:20,73,109`.

5. **Implement correct cursor back-navigation in Opportunities and Linked Projects.** Both Previous handlers clear the cursor. From page three this returns to page one; Opportunities also decrements its displayed number to two. Keep cursor history, use a shared cursor pager, or expose a valid previous cursor. Test at least three pages after filtering and browser back/forward. Evidence: `frontend/features/build/managed-products/insights/product-discovery-section.tsx:79-88`, `projects/use-product-projects-page.ts:210-219`.

6. **Expose the declared opportunity filters.** The API accepts `theme`, `scoreMax`, multi-value state/segment/owner/confidence, and search; the UI provides no opportunity-theme filter, no upper score bound, no search and single-value selectors. Provide the promised typed filter controls, query serialization, removable chips, clear/reset and filtered-empty behavior. Test the actual backend predicate, not only UI state. Evidence: `backend/src/modules/build/managed-products/discovery/dto/discovery.schemas.ts:55-78`, `frontend/features/build/managed-products/insights/use-opportunity-discovery-filters.ts:29-115`, `insights/opportunities-filter-bar.tsx`. Contract: `experience/screens/product-discovery.md:109-136`.

7. **Paginate and handle failure for outcome reviews and themes.** The backend review list defaults to 25 items and returns a cursor; `ProductDiscoverySection` calls `useOutcomeReviews(managedProductId)` once and renders only `.data`, with no next-page control. It also passes neither review nor theme errors to their sections, so a failed request can appear as an empty collection. Add cursor loading, visible error/retry states, and tests for more than 25 reviews plus a rejected read. Evidence: `backend/src/modules/build/managed-products/discovery/dto/discovery.schemas.ts:176-190`, `frontend/features/build/managed-products/insights/product-discovery-section.tsx:55-59,224-225`, `insights/outcome-reviews-section.tsx`.

8. **Keep the outcome-review completion form open until the write succeeds.** `handleCompleteReview` calls the mutation callback and immediately clears `completingId`, closing the form before commit. Close on success, keep values on failure, display the conflict and allow correction/retry. Evidence: `frontend/features/build/managed-products/insights/outcome-reviews-section.tsx:184-191`, `insights/product-discovery-section.tsx:115-128`. Contract: `experience/screens/product-discovery.md:121-133`.

9. **Fix the product-directory search contract.** The UI says “Search by name or key,” but the backend searches only a name prefix (`name ILIKE search%`). Implement escaped contains matching for name and key, with stable paging and tests for middle-of-name and key matches. Evidence: `frontend/features/build/managed-products/managed-products-toolbar.tsx:91-101`, `backend/src/modules/build/managed-products/managed-product-list.service.ts:68-78`. Contract: `experience/screens/product-discovery.md:25-52`.

10. **Make the product roadmap preview complete and authoritative.** The product page passes only its current cursor page to `RoadmapPreviewSheet`, which filters those loaded rows locally and calls the count “visible to the public.” A later published item is omitted. Fetch the actual publication projection for the product and align preview with the public output and publication version; test more than one page, unpublished/private fields and unpublish. Evidence: `frontend/features/build/managed-products/product-roadmap-page.tsx:260-261`, `roadmap/roadmap-preview-sheet.tsx:58-83`. Contract: `acceptance/module/02d-scope-public-page-contracts-prd.md:33,65-75`.

11. **Complete the product settings contract.** Settings has only General and Members tabs. The declared product settings include project links, roadmap defaults, feedback channels, client publication and archive impact; selectors must paginate and last-owner/client-visibility checks must be transactional. Implement the missing sections against canonical owners and verify save/conflict/denial. Evidence: `frontend/features/build/managed-products/product-settings-tabs.ts:1-4`, `product-settings-page.tsx:185-237`. Contract: `acceptance/module/02d-scope-public-page-contracts-prd.md:37`.

12. **Make product release edits conflict-safe.** Product release creation/update exists, but `updateReleaseSchema` and `ManagedProductReleasesService.updateRelease` have no expected revision predicate; `version` is the release label string. Add a distinct record revision and 409 behavior, then verify concurrent edits and the release-to-roadmap/outcome links. Evidence: `backend/src/modules/build/managed-products/dto/managed-products.schemas.ts:179-198`, `managed-product-releases.service.ts:117-143`.

## Acceptance still required after code changes

17. **Product authority matrix:** authenticated manager/member/viewer and another tenant; list, facets, direct URL, goal/project selectors, Feedbucket widgets/submissions, roadmap publication, opportunities and outcome reviews. Verify both successful and denied reads/writes in HTTP and UI, with no existence or cached-data leak.

18. **Persisted product journey:** create product → link two projects → capture and classify feedback → deduplicate without losing provenance → create/score/override an opportunity → accept to roadmap/epic/release → deliver → record a measured outcome. Verify returned IDs, audit, revisions, cache changes and refresh after each step. Include retries and 409 races.

19. **Responsive and keyboard journey:** 375, 768 and 1280 px across all nine product routes; populated, empty, filtered-empty, loading, error, denied and not-found states; dialog focus, Escape, deep-link pane and return to query/scroll/focus.

20. **Public and client publication:** compare preview and actual published projection for the same product and grant/version, including hidden internal fields, later pages, revoked access and cache invalidation. The org-wide public roadmap is a boundary dependency, not an invitation to audit unrelated Build modules.

21. **Operational data checks:** migration replay/backfill for the association change, database constraints and indexes, cursor/query plans under large product and review lists, concurrent writes, outbox/cache freshness, and current deployed frontend/backend revision parity.

22. **Value reasons 71–76:** demonstrate feedback traceability, customer-impact comparison, explainable RICE, durable opportunity records, audience-safe roadmap and measured outcome follow-up with source records. A product-differentiation claim additionally needs customer and same-scope competitor evidence; working code alone does not prove superiority.

23. **Complete product directory and release projections.** The directory response has owner, lifecycle, a single team ID, linked-project count, next release and feedback trend, but no goal-health projection, per-row allowed actions or independent source freshness. Product releases store only product/name/version/description/status/date/creator/timestamps; they do not carry the declared release owner, membership in delivered work, QA/approval or deployment evidence. Add bounded authorized projections and source links through the owning records, or make an explicit product decision to narrow these contracts. Evidence: `backend/src/modules/build/managed-products/dto/managed-products-response.schemas.ts:25-63`, `backend/src/db/schema/build/managed-products.ts:84-115`. Contract: `experience/screens/product-discovery.md:25-52`, `architecture/screen-data-contracts.md:9-27`.

24. **Repair product-release cursor pagination.** The releases query orders `(releaseDate, id)` ascending but applies `keysetBeforeId`, whose predicate is `<`; after the first page, the cursor selects rows before the last item instead of later rows. Null release dates also need an explicit stable sort and cursor representation. Use an ascending keyset predicate with matching null ordering and test multiple pages with dated and undated releases. Evidence: `backend/src/modules/build/managed-products/managed-product-releases.service.ts:45-85`, `backend/src/common/pagination/keyset.ts:82-88`.
