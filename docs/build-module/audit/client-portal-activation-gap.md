Status: Current verified for the specifically named source, API and database observations below; complete activation, browser and deployment behavior remain Current unverified. Findings recorded 2026-10-03. Requirement: [BLD-005](../implementation/REQUIREMENT-LEDGER.md). Owner: `ARCH-17-CLIENT-PORTAL-ACCESS` in the [work claims](../implementation/WORK-CLAIMS.md).

## Customer outcome

An authorized Build owner or administrator selects a project and an external client, chooses the permitted artifacts and expiry, and submits once. Success means a durable scoped grant and a usable single-purpose invitation exist together. The client accepts a secure link and sees only published, permitted project content. Revocation, expiry, or unpublication blocks the next request, including file access.

## Canonical command and state

`POST /portal-access/activations` is the planned owner command. Its strict body includes `projectId`, a discriminated existing-contact or new name/email recipient, explicit client-visible capabilities, optional expiry, expected `portalPublishedAt`, and an invitation reuse or explicit rotation decision. The initial delivery mode is email; authorized one-time sharing is Conditional on a separate secret-delivery and replay contract. The `Idempotency-Key` is an HTTP header, never an authority or identity field in the body. Validate organization and Build management permission, project reachability, plan limits, normalized recipient identity, allowed capabilities, expiry, and publication policy before committing. Keep current granular membership and grant APIs as compatible administration operations. A published timestamp is the currently available optimistic comparison; do not invent a persisted policy revision.

One tenant transaction resolves or creates the Party/Contact through transaction-aware owner commands, records a pending portal membership and hashed invitation token, creates one project-scoped grant, and queues delivery in a transaction-bound email outbox. Invitation rows store a token hash; queued email content necessarily contains the usable link and needs restricted access, redacted diagnostics and bounded retention. Do not describe all storage as hash-only. Return the durable membership, grant and invitation IDs, masked recipient, individual states, delivery outcome, and allowed next action; no activation ID exists until an activation entity is deliberately introduced. Do not put a raw token or share URL into the generic command-fence response, which is durably replayed. `success` never describes an unsent email as delivered; report queued, suppressed, provider unavailable, or existing pending invitation without a new send. Email enqueue currently returns an outcome, not a delivery receipt; exact delivery tracking needs the Email owner contract.

Acceptance atomically claims one unexpired `PENDING` invitation and activates the matching membership. Minting failure rolls the claim back, and the caller receives the minted session only after the transaction commits. Duplicate and concurrent redemption must yield one winner and a safe generic rejection for the loser. Any grant remains project scoped and can be narrower than the portal membership.

## Revocation and recipient lifecycle reconciliation

The current legacy invitation identifies an organization, contact and audience without binding a target membership or session epoch. The membership unique index permits a replacement after revocation. Therefore, a pending legacy link cannot safely choose a replacement solely from contact identity. The `BLD-PORTAL-REVOCATION-04` source slice at backend `859f12e79` requires one unambiguous historical membership, locks membership before invitation, rejects missing/revoked/suspended/deleted identity, and removes acceptance's insertion fallback. The conditional claim measures expiry after acquiring the membership lock. Status suspension and revocation revoke matching pending invitations and advance the epoch in the same transaction. The organization-linked revocation path uses the same membership-before-invitation order. Generic status changes cannot resurrect a revoked membership. Current portal sessions require the correct membership audience, active state, nondeleted record, signed contact identity and current epoch. Source and the bounded real API observations below are Current verified; the full role, lifecycle and concurrency matrix is Current unverified.

Explicit regrant remains required customer behavior. Its planned producer creates an explicitly authorized target and binds the invitation to that membership and epoch using new schema fields and a same-tenant/contact composite reference. Bound acceptance selects that exact target, allowing legitimate regrant even when revoked history exists. Legacy ambiguity rejects safely and requires reissue; it is not a permanent ban on inviting a previously revoked client. `acceptedPortalMembershipId` records the acceptance result and must not be repurposed as the target binding. Timestamps are not lineage proof.

Recipient lifecycle is a separate required Party-owner handoff: validate a live contact, live parent Party and canonical email, coordinate email/deletion changes with invitation claims, and invalidate outstanding invitations and active portal sessions when recipient identity changes. `PartyService.loadContact` is private; do not introduce a second cross-module table reader to bypass ownership. Membership-only hardening and invitation binding do not establish these guarantees. Public token lookup must reject ambiguous hashes until the unique token index is proven on the target database.

Build client quota also needs an explicit owner contract. Current Party creation checks `crmContacts`, whose usage query counts customer mappings; a contact-only portal creation does not itself establish that usage. Reuse the accepted free/startup/professional/enterprise and top-up product decisions, but do not claim the existing CRM count enforces Build's client allowance. Serialize admission against the canonical Build client count before enabling the complete activation command.

The external read owner uses one effective-grant predicate across list, overview, change request, and signed file issuance: same tenant, active membership, active unexpired grant, nondeleted project, `portalPublishedAt IS NOT NULL`, and record/field visibility. Client projection excludes internal descriptions, private comments, hidden files, rates, and unapproved statuses even when an internal ticket links to the project. All denial paths use safe `401` or `404` without leaking another project.

## Proposed UI flow

The Build-wide Client Access page and project Client Portal settings open one project-aware `Invite client` dialog. Required fields are project, recipient, and access preset; an advanced section controls individual artifact capabilities and expiry. The initial delivery choice is email. Authorized copy-link delivery is Conditional and appears only after its secret-delivery contract is implemented. Preview shows exactly what the client will see. Submit has a stable pending state; retries reuse the same idempotency key. Success shows invitation and grant status as separate facts and a usable next action. An unsent invitation remains visible with a policy-authorized email retry. Refresh preserves the status. Revoke and unpublish update the guest view immediately.

## Recipient lifecycle implementation handoff

The required writer census includes contact email updates/deletion, parent Party deletion through shared write primitives and legacy/CRM import callers, and contact reparenting during merge/revert. Existing parent email is separate business metadata and is not a recipient fallback. Parent liveness currently means `deletedAt IS NULL`; do not invent a global active-status rule for its free-text status. A shared owner read should return a live same-tenant contact and parent plus a canonical deliverable email, allowing the mutation owner to repair an invalid legacy address. Auth and activation reject missing or invalid delivery identity.

Use a public Party owner interface with explicit transaction and parent → contact → membership → invitation locking. Email identity changes, contact deletion, parent deletion and reparenting must revoke pending invitations and advance membership epochs in that transaction; normalization-only email edits should not revoke access. Restore/revert must never reactivate old portal rows. Guard liveness alone does not invalidate a token after a same-contact email change. Resolve the dependency through an independently injectable Portal recipient-access service with no Party dependency, rather than a private table reader or query-builder type shared across owners. Party owns bounded contact selection and calls that service with domain IDs. Bulk parent operations need bounded batches and measured lock/transaction limits; lock ordering across organization revocation also needs concurrency proof. These are required next implementation steps, not delivered behavior.
