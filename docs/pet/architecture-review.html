One pet, many authorized skills

The user selected a universal natural-language entry. Existing Ask OS Tool providers span Build, CRM, mail, communications, calendar, HR, payroll, operations, and workspace. The pet should deepen that existing module rather than become a second action engine. Source presence is not release proof.

Strong

1 · Keep the Toolset as the capability seam

Files: ai/core/registry/ask-os-tool-registry.ts, ask-os-tool.types.ts, ai/core/tools/*-tools.ts, frontend/components/assistant/.

Problem: A Build-centric pet would obscure existing cross-module leverage. A second pet router would duplicate grants, Outcomes, and confirmation. Solution: The pet accepts every question and request, while the current per-turn Toolset determines which owner module can answer or propose an action. Its typed Outcome carries ambiguity, connection, denial, and failure to the panel.

Strong

2 · Require confirmation for every pet write

Files: self-actions-tools.ts, crm-copilot-tools.ts, confirm-actions/self-confirm-actions.ts, ask-os-tool.types.ts.

Problem: Clock-in, clock-out, break toggle, and CRM createTask are registered without a confirmable-action key, while the pet requirement says it proposes changes before committing them. CRM updateLeadStatus also picks the first partial-name match instead of clarifying multiple visible matches. Solution: Keep each owner and require a visible preview and explicit confirmation before exposing its write through the pet. Do not add a forwarding adapter that merely renames the Tool.

Worth exploring

3 · One reviewed capability inventory

Files: ai/core/tools/, ai/core/registry/, frontend/components/assistant/.

Problem: Launch suggestions, admin policy, and test coverage could drift if each gets a separate feature list. Solution: First inventory registered Tools and their owner, grant, connection, cost, and confirmation behavior. Add a shared metadata seam only if real use in at least two consumers proves leverage; avoid a speculative adapter.

Benefits: Higher leverage and clearer locality of capability policy. The interface is the test surface; do not add it until the design spike shows current metadata is insufficient.

Top recommendation

Start with the universal request path through the existing Toolset, then close its observed owner gaps: Documents-owned citable context for one Ask OS generation and exact Build BUG counts. Remove immediate self and CRM task writes from the pet Toolset until they use confirmation. Keep the idle shell light and measure the cross-module path in a pilot environment before setting latency budgets.
