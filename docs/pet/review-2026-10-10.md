# Companion implementation review — 2026-10-10

## Scope and evidence

Reviewed the current companion implementation in the frontend and backend repositories against their `CLAUDE.md` rules and the pet specification. The work covered prompt API authorization and history queries, query keys and cache invalidation, preference controls, voice and placement hooks, React lifecycle cleanup, and the live Account Settings page. The repository also had unrelated Build documentation and Mail edits in progress; their source files were left alone. Regenerating OpenAPI from the shared backend tree necessarily included the current Mail API edits in both contract copies.

## Fixes made

- Guard companion prompt reads, actions, and activity heartbeat with `ai:chat:use` on the API and through the shared frontend permission hooks. Preference reads and updates remain available to signed-in members.
- Apply category and effective outcome filters in the backend query before bounded cursor pagination. The frontend keeps filters in the URL and renders one cursor page through the shared pagination component.
- Refresh filtered history caches after prompt actions and refresh the next prompt when preferences change. An admin policy update refreshes active preference queries.
- Deduplicate friendly check-ins across tabs and sessions for a workday. The settings copy states this limit.
- Stop live voice tracks, connections, pending network calls, timers, and placement frames on stop or unmount. Handle voice tool calls in order so Ask OS's single-flight path does not drop later calls.
- Hide a claimed suggestion after its category is disabled or prompts are paused. Turning off check-ins now dismisses the prompt only after the preference save succeeds; failed saves show an error.
- Show a retryable history error without simultaneously showing stale empty results.
- Regenerate the backend OpenAPI document and vendor the matching frontend copy.

## Verification completed

- Frontend focused suites: 40 tests passed; after the final cache and copy refinements, the launcher and settings suites passed again (37 tests). Frontend TypeScript and targeted ESLint passed after those refinements.

The backend on port 1500 subsequently stopped, so the rewrite has **not** passed browser verification. The local `.env` and `.env.production` database logins both returned PostgreSQL `28P01` during read-only checks; the user is updating `backend/.env`.

## Open verification and risks

1. Restart the backend with working local database credentials. Repeat the authenticated browser history-filter flow for each outcome and test Retry, refresh, and a history page with real rows. Confirm the backend remains healthy. A schema/unit test does not close the observed live server error.
2. Run a live claimed-prompt revocation case: another device or admin disables the category, or its source becomes ineligible, while the bubble is open. The frontend reacts to refreshed preferences, but source revocation still needs an explicit revalidation contract.
3. Recheck consent revocation racing an in-flight activity heartbeat. The preference update and activity deletion are separate database operations; a heartbeat that already read consent may write after deletion.
4. Verify calendar/attendance notification category routing for non-meeting suggestions against the intended notification policy. Meeting prompts use `calendar.reminder`; other categories currently rely on companion toggles and global quiet hours.
5. Verify real speech, action confirmation, and prompt delivery in the browser with the backend running. Focused tests and rendered controls do not prove those paths end to end.

These are open release checks, not completed items.
