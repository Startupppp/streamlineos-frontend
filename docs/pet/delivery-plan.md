# Companion Pet — sequenced delivery and validation plan

**Status:** Proposed work breakdown, 2026-10-08. No product implementation is authorized by this document. [CP-00](00-experience-prd.md), [CP-01](01-intelligence-actions-prd.md), and [CP-02](02-proactive-governance-prd.md) are the requirements; the [ledger](verification-and-competition.md) identifies current evidence and missing proof.

## Release thesis and scope

The first-release experience must complete a visible loop: **ask or receive a timely prompt → show the source and scope → offer relevant next steps → preview a permitted change → require confirmation → show a real result and receipt**. Test whether this loop, the pet's quiet presence, and user control improve task completion for all pilot organization-member role clusters. The [200 candidates](wow-opportunity-catalog.md) are a discovery pool, not 200 build tickets or uniqueness claims.

**Included:** Original pet; desktop/mobile entry; text plus explicit short-form voice input through authenticated backend transcription and user-triggered spoken replies; universal organization-member core; existing history; natural-language questions and actions across validated StreamlineOS and approved connected-tool capabilities; source-backed KB answers; exact permission-scoped Build counts and bug search; existing permitted actions through confirmation; preference/admin controls; eligible meeting, clock-in, break, and opted-in friendly prompts; accessibility and release evidence. **Later:** arbitrary websites/computer control, external client-portal guests, voice/persona selection, deep automation, repository bug diagnosis, pet marketplace, and unverified catalog ideas.

## Architecture and performance constraints

- Preserve the owner seams in [CONTEXT.md](../../CONTEXT.md): Ask OS owns Tool, Toolset, Proposal, Directive, Actor, and Credit ledger; Documents owns Retrieve and Citation; Build owns Ticket queries and `applyTicketChange`; Calendar and Notifications own reminder identity and delivery. A pet-only copy of these rules would create drift.
- The general request path is the product architecture. Build and Documents remain important owner-specific gaps, but their Tools do not become a routing template for unrelated domains. Keep owner query/write logic local; use the existing Toolset for reach and typed Outcomes. Bound per-turn calls, rows, bytes, time, and credit spend; independently measured reads may run concurrently while dependent writes require ordered confirmations.
- Use the existing `ScopedRead` and request-local `AuthContext` contracts ([ADR 0005](../docs/adr/0005-a-datascope-is-spent-not-read.md), [ADR 0004](../docs/adr/0004-auth-facts-resolve-once-per-request.md)). Capability chips and role starters derive from the resolved actor snapshot rather than role-name switches. Recheck access when an action is redeemed or a citation is opened.
- Keep the idle character and state data light. Load the full conversation panel only when opened, following `AskOsProvider`; pause decorative animation when hidden and under reduced motion. Do not start a model turn or poll all modules just to animate or choose a reminder.
- For exact counts, make one bounded aggregate in Build and return a separate bounded preview. Measure query plans as the non-owner application role with representative tenant sizes before adding a cache. If caching is warranted, key by organization, actor/scope, filters, and revision; invalidate on Ticket/status/project-access changes and display `asOf`.
- For prompts, reuse Calendar's outbox identity and Notifications' quiet hours. Coarse activity consent must avoid keystroke/screen capture and high-frequency telemetry. Define a small retained foreground-session signal, server-side dedupe, and no individual activity report to administrators; verify the wording does not imply continuous work.
- Record performance baselines and budgets for initial shell payload, idle CPU/animation, panel-open latency, count-query buffers, Documents answer latency/credits, and prompt delivery lag in a named nonproduction environment. Baseline and target values are measurements to establish, not numbers inferred from source.

## Priority and candidate validation

Treat CP-W001/008 (pet state tied to verified outcome), CP-W021/024 (content answer and citation), CP-W041/042 (exact BUG count and filters), CP-W046/165 (confirmed write and receipt), CP-W061/081/086 (eligible prompts), CP-W161/173 (why a capability or prompt appeared), and CP-W193/200 (role starters and outcome feedback) as the first integrated discovery set. Prototype and test the full loop with real tasks; a visually impressive motion state that does not improve trust or completion is not a release gate. CP-W181/182 (daily cross-module plan and multi-action cards) are sequenced after the first single-action loop is proven but remain first-release requirements for supported Tools; more autonomous workflows remain later exploration.

| Gate | Minimum measurable condition | Evidence status now |
| --- | --- | --- |
| Access and isolation | Zero unauthorized records or actions in the agreed role, project, tenant, and revocation matrix; no known high-severity leak open. | UNVERIFIED. |
| Count and answer truth | Every fixture total equals the canonical authorized query; every cited assertion opens an accessible supporting source; no capped preview presented as total. | UNVERIFIED for new companion behavior. |
| Action integrity | Every tested confirmed write produces one owning-module result and receipt; duplicate, expired, conflicted, or revoked proposals produce zero extra writes. | UNVERIFIED end to end. |
| Prompt control | Every disabled/quiet/leave/holiday/focus case suppresses; each eligible source event produces at most one actionable pet prompt per user; reason is inspectable. | UNVERIFIED end to end. |
| Cross-role experience | One complete real starter journey per enabled pilot role cluster, plus denied and unavailable state; keyboard and screen-reader equivalence. | UNVERIFIED. |
| Cross-module capability | The approved launch inventory has a verified answer or honest unavailable path for each representative request; at least one mixed-module answer and one partially completed multi-step action have truthful source and receipt states. | UNVERIFIED. |
| User value | Baseline, pilot sample, task-completion target, and interruption threshold agreed before pilot readout. | NEEDS-MEASUREMENT. |

The first four gates are correctness criteria, not claims of proof from current tests. Latency, reliability, prompt effectiveness, and task-time targets require a named environment and baseline; do not invent numerical promises. Any failed gate retains `CURRENT UNVERIFIED` or `NO-GO` in the release record.
