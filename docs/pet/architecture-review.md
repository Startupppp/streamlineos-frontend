## Architecture decisions now fixed

1. **Ownership:** Ask OS owns conversation, actor, Toolset, metering, proposal, and confirmation; owner modules own facts and writes; Access/RBAC owns grants; Calendar/Notifications/HR own prompt facts and delivery. The pet owns presentation, preferences, and prompt policy composition. See [CP-03](03-implementation-architecture-prd.md).
2. **No unreviewed execution:** The registered Toolset is necessary but not sufficient for companion exposure. A server-side companion allowlist or equivalent reviewed policy excludes unadapted immediate writes and any capability that fails the launch contract. It intersects, never replaces, RBAC/module/connection checks.
3. **No false atomicity:** Independent reads may run within bounded fan-out. Each side effect is proposed and confirmed separately. Failure or decline stops dependent work, preserves truthful earlier receipts, and offers an explicit recovery path.
4. **No assumed release proof:** Source inspection and focused tests establish seams only. The [verification ledger](verification-and-competition.md) and [delivery plan](delivery-plan.md) require non-owner DB, browser, persistence, role, project, tenant, worker, and deployment evidence.

## Report limitations to carry into implementation

- The diagram's `Owner Tool → Typed Outcome` arrow omits object-level permission, target disambiguation, connection, error, and revocation checks; [the implementation contract](implementation-contract.md) supplies them.
- `Toolset → safe suggestions` is conditional. Current provider metadata does not itself prove a suggestion is executable or suitable for that user's current record. The server computes effective availability and the owner validates the target.
- `Proposal → confirm → owner receipt` is the desired contract. Existing confirmation result shapes and action-specific idempotency must be audited; the diagram alone does not establish a uniform receipt or exactly-once behavior.
- The report does not specify prompt persistence, appearance assets, browser states, accessibility, or release operations. [CP-00](00-experience-prd.md), [CP-02](02-proactive-governance-prd.md), and [the implementation contract](implementation-contract.md) fill those requirements.
