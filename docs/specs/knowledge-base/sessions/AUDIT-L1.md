- [x] FIXED — Revocation propagation test against the documented bound (p95 < 15 s, hard 60 s). Investigation found the real mechanism is **synchronous, not TTL-based**: authorization itself is always a live query (`revoked_at IS NULL` is re-evaluated every request — proven in `kb-revocation-after-indexing.spec.ts` "Revocation dimension 4"), so list/detail access is instant. But vector search enforces an additional strict fence, `eq(kbArticleChunks.aclRevision, kbPages.aclRevision)` (`kb-candidate.service.ts:230`), applied to **every** page in **every** vector query. I found `KbPageGrantsService.create`/`revoke` bumped `kbPages.aclRevision` but never synced `kb_article_chunks.acl_revision` for that page — unlike the equivalent space-membership path (`KbIndexingService.bumpSpaceAclRevision` → `syncAclRevisionForSpace`, `kb-indexing.service.ts:229-251`, wired from `KbMembersService`). Net effect: **creating or revoking any page grant silently fenced that page out of vector search / Ask / citations for every user, indefinitely**, until an unrelated content edit or space-membership change happened to resync it — a regression far outside the documented 60 s hard bound, not a slow-propagation issue. **Fix** (within my territory, `kb-page-grants.service.ts`): added `private syncChunkAclRevision(orgId, pageId)` running `UPDATE kb_article_chunks c SET acl_revision = p.acl_revision FROM kb_pages p WHERE c.page_id = p.id AND c.org_id = … AND c.page_id = … AND c.acl_revision != p.acl_revision`, called after commit from both `create()` and `revoke()` alongside the existing `invalidateSpaceScope`. Added 3 tests to `kb-page-grants.spec.ts` proving the sync fires with the right org/page binding on both paths. **Bite proof:** removed the two `syncChunkAclRevision` call sites → 3 new tests failed (0 execute calls instead of 1); restored → all 25 tests in the file pass (`npx jest --runTestsByPath src/modules/kb/wiki/kb-page-grants.spec.ts` → 25 passed both before-fix-confirmed-broken and after-fix-confirmed-fixed runs).

No backfill migration exists (`find backend/migrations -iname "*grant*"` → only `1168_kb_page_grants.sql`, which is schema-only, no `INSERT`).
