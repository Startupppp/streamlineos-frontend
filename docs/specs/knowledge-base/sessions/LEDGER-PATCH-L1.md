**HANDOFF 1 — `kb_page_grants` has no writer in the product (S03, new ledger row needed).** The grant CRUD surface is complete, audited and object-level-authorized, and `GET /kb/pages?sharedWithMe=1` reads it correctly, but no frontend code calls `POST`/`DELETE /kb/pages/:pageId/grants`. In production "Shared with me" is therefore structurally always empty. The S03 requirement table never scoped a grant-creation UI, so no existing box covers this — it needs a new one. It is not purely an implementation task: the picker needs a grantee directory, and `useOrgMembers` (`frontend/hooks/api/organization.ts:78`) is gated on `settings:view`, which a page manager holding `kb:pages:update` will usually not hold, so it would render empty for the intended users (FE-47). **Decision needed:** either (a) add a narrow, `kb:pages:update`-gated grantee lookup endpoint (membership id + display name only, no user table exposure per BE-46), or (b) restrict page grants to *roles* only, which needs no directory and is already a first-class grantee arc in the schema, or (c) accept that grants are API-only for now and say so in the ledger. Until one is chosen, S03 ships a read surface for data nothing writes.
