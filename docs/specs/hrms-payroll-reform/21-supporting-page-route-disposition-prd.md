# HRMS settings, implementation pages and module-boundary PRD

**Status:** Target-state UI and backend contract. **Owners:** People Platform, Payroll Platform, Security and Customer Implementation. **Scope:** Secondary HR settings, implementation cockpit and module-level RBAC. The 100 canonical primary pages are specified in [PRD 18](./18-self-service-page-ui-backend-prd.md), [PRD 19](./19-hr-administration-page-ui-backend-prd.md) and [PRD 20](./20-payroll-page-ui-backend-prd.md). The current route reconciliation is [PRD 22](./22-current-route-disposition-prd.md).

## Module-level RBAC: independent HRMS and Payroll modules

The product catalog must expose **HRMS** and **Payroll** as independent module entitlements. HRMS administration may be enabled without Payroll; Payroll administration may be enabled without the wider HRMS UI. The HRMS umbrella includes separately enabled Core HR, Workforce, Talent/Rewards and Service capabilities, so a subscription or role need not expose every HR submodule. Employee self-service uses the narrow entitlement of the underlying job (`people-self`, `core-hr`, `time`, `leave`, `payroll-self`, etc.), not a blanket HR administrator grant. The existing [route manifest](./07a-page-permission-manifest-prd.md) is the permission source of truth; this section requires its runtime enforcement.

| Actor/module combination | HRMS navigation and records | Payroll navigation and records | Cross-module handoff |
|---|---|---|---|
| HRMS admin only | Only entitled HR submodules, object scope and allowed fields | No Payroll operator routes, salary, bank, tax, run, payout or export | HR exit/onboarding/payroll readiness status only when specifically granted; no amounts |
| Payroll operator only | No general worker directory, case, talent or document access | Only authorized Payroll stages, pay groups/entities and field classes | Versioned, minimum Core HR Employment Facts and approved input snapshots through service contracts |
| Both modules | Union of independently granted actions; a broad role name alone is insufficient | Stage and field grants remain separate | A cross-module screen checks each source before querying or caching it |
| Neither | Only eligible self-service/other products | Only `payroll-self` if separately entitled to own published pay | No administrative data by fallback |
| Owner/executive | Explicit audience policy and scoped admin permission | No automatic self-service or payout ability from broad backend grants | Owner UI is filtered consistently in sidebar, command palette, search and AskOS |

Enforce the same decision in the route loader, API controller, application service, database scope, object/file download, list count, export, scheduled job, analytics/chart, Calendar projection, notification, search and AskOS tool. The decision input is `{tenant, actor, module entitlement, action permission, object scope, field purpose, record state, effective time}`. Resolve it **before** any query, cache fill or AI retrieval. Cache keys include entitlement/permission epoch, field class and scope fingerprint; revocation invalidates affected keys. Denied and disabled-module responses differ without revealing record existence. Direct URL and guessed IDs must not bypass the sidebar. Payroll setup, salary changes, bank changes, run calculation/approval, funding, payout release, statutory filing and accounting acknowledgement have distinct action grants and maker-checker constraints. HR cases/medical/accommodation fields have separate class grants. A combined dashboard never materializes a broad unfiltered payload and hides columns afterward.

**Module acceptance matrix:** test HR-only, Payroll-only, both, neither, employee, manager, owner, auditor, delegated actor and revoked actor against sidebar, command search, direct URL, API, export, document download, query-cache reuse, Calendar/chart and AskOS. Begin with denied/disabled/stale/guessed-ID cases, then successful cases. Assert database enforcement under the application role and tenant context, not only component mocks. A pending module purchase or tier does not masquerade as an empty dataset.

## Shared secondary-page contract

Each page below inherits PRD 18's loading, empty, denied, disabled, conflict, partial, success, keyboard, mobile, accessibility and URL-state rules. Settings write paths use draft, validation, preview/diff, named approval when sensitive, effective date, published immutable version, rollback or supersession plan and audit. Never mutate a setting already referenced by a locked pay run or signed document. Implementation pages are hidden from ordinary HR/Payroll navigation and require the independent implementation entitlement plus project membership and task-specific HRMS or Payroll access for sensitive payloads. A consultant cannot infer Payroll access merely from implementation membership.

## Implementation blueprint for every UI/backend item in PRDs 18–21

For **each page row**, the implementing agent records a short page contract before source changes: canonical route and tier; actor and parent/child module entitlement; action permission, DataScope and field classes; owning aggregate and effective-time rule; list/detail read envelope; command/state transition; external handoff and recovery; query/cache keys and invalidation writers; Calendar/chart/AskOS consumers; and behavior-level negative/success evidence. Link the contract to the ticket and AC ledger. A page row is complete only after these fields have a current implementation or an explicitly documented inapplicable decision. The words “UI item” and “Backend item” identify two deliverables, not permission to skip integrations.

Use the existing frontend Next.js route as a thin server permission gate, then compose domain page/task components. Keep interactive state in leaf client components. Define form fields and conditional steps from the page row and owner policy; validate client input for usability and repeat validation at the API. Use an accessible responsive collection/detail/form pattern rather than a one-off page shell. A route with tabs has one authorized source for tab selection and URL-backed filters; a disconnected placeholder is not a delivered page. Reuse shared page states and semantic design tokens. Verify at 375/768/1280, light/dark, keyboard and screen reader on the complete task.

In the NestJS/Drizzle backend, keep the controller thin and validated with owner-module strict Zod body/query/params and declared response schemas. Put business transitions and scoped reads in the owning service; query Drizzle through the existing service pattern, without adding a generic repository or cross-module table read. Schema changes specify stable tenant/worker/engagement/pay-group IDs, foreign keys, unique/idempotency constraints, effective intervals, version and state, provenance and created/updated actor/time, retention class and indexes for the declared filters/cursors. Use a real migration and backfill/rollback or forward-correction plan. Read projections select only needed columns and apply tenant, relationship, object and field predicates before aggregation; list pages have a stable bounded cursor and server-side counts. No fixed safety cap may silently truncate a business-complete operation.

For commands, specify transition preconditions, expected version, idempotency key, actor, source version and effective business date. Commit owner facts, audit and required outbox intent atomically; external consumers use inbox deduplication, receipt and repairable unknown/partial state. Frozen Payroll snapshots and published documents remain immutable, with correction generations instead of in-place repair. The response distinguishes validation, disabled module, denied, not found, conflict, partial and successful receipt without revealing a forbidden object's existence.

For frontend data, define one domain-local TanStack Query options factory per read, including normalized key, fetcher, response contract, stale time, abort signal and SSR/infinite page envelope. Keep authenticated key arrays tenant-free under the existing scoped QueryClient hash, but include every response-shaping filter and identity. Mutation success patches the exact known entity or invalidates true prefixes for affected lists, badges, source consumers and aggregates; revocation/org switch/logout removes protected data and late responses cannot refill it. Backend Redis keys include tenant, authorization shape, filter, field class, version and freshness policy; authorization precedes cache lookup/fill. Avoid request-path wildcard invalidation.

Calendar receives only source-owned visibility-safe events and cancellation updates; chart/report/export drill-through uses the same authorized cohort, period, grain, currency, coverage and source version; AskOS calls owner read tools with the actor's current grant and cites provenance. For any cross-module card, deny its source independently and render restricted/partial rather than a fabricated zero. These integration requirements apply even when their UI is only a small card on another page. Repository rules in `frontend/CLAUDE.md` and `backend/CLAUDE.md`, plus [architecture PRD 16](./16-architecture-hardening-prd.md), override this blueprint where they prescribe a stricter current convention.

## Route retirement rule

The route decision table in [PRD 22](./22-current-route-disposition-prd.md) is a migration contract, not immediate deletion authority. Before removing a page, prove its feature is owned elsewhere, migrate every inbound sidebar/command/search/deep link, preserve or intentionally sunset bookmarks, test the redirect and direct URL, confirm zero remaining callers, and verify denied users cannot gain access through an alias. Remove an obsolete UI only after its unique behavior and data operations have a tested canonical home. Every replacement must preserve audit, history and legal/financial evidence.
