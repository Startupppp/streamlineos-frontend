Problem

Three mechanisms say "this chat thing points at that business thing": an untyped entityType/entityId pair, a hard linkedDealId FK beside it, and free-form metadata.entities on the message. The only actions that exist are four Build endpoints importing another module's tables — which §5 forbids. A fifth module means writing that controller again.

Solution

One module, one interface. resolve returns a display card or null when the reader lacks access; actionsFor returns what this actor may do. Each product module registers an adapter.

Security, not style — re-verified. An unfurled ticket renders from metadata.entities, captured at send time. A reader who never had — or has since lost — build:tickets:view still reads its title in scrollback. resolve() re-asserts object-level access at read time, degrading the reference to "a ticket you can't see".

Wins

  • Leverage: one interface, every module
  • Chat stops importing Build schema
  • Access re-checked at render, not send
  • Two adapters justify the seam on day one
  • Mentions, unfurls and slash-actions share it
  • Delete the polymorphic pair and linkedDealId

Two corrections to the 2026-08-20 report

1 — "FE PERMISSIONS is 206 keys short" is not a defect. That array is the seed list for role templates, not the granting picker. The picker reads GET /rbac/permissions — the live backend catalog. The subset is deliberate and covered by catalog-sync.test.ts, which asserts every entry in it is real. Deleting it, as the report proposed, would delete the role templates.

2 — The union is no longer generated-by-hand-and-hoped. catalog-sync.test.ts runs five assertions in the default frontend suite, both directions: no frontend key absent from the backend, no backend key absent from the union, no union-only ghost, no duplicate, every key parseable into a module segment. A drift is a failing test today.

Caveat worth carrying forward: those assertions read the backend as source text via regex, not as imported values. They are a real net, but a refactor that changes how a key literal is written would blind them.

What did land, on the module-owner half of the card

ACCESS_MANAGED_MODULES went from 10 to 14 — home, workflows, blog, directory added. Chat, mail, calendar and notifications are now administered by Home rather than getting four separate ladders. billing remains the one module with no per-module access surface.

mergeIfKnown still drops an unknown grant key — but it now logs a warning once per key with org, key and source, so the silent part is fixed.

After — one module, four deletions

the only implementation

namespacesForModule("home")
→ ["home","chat","mail",
"calendar","notifications"]

A module's namespaces include its own. That single change is the 27-vs-29 discrepancy and the reason a Home module owner cannot open their own screen.

Problem

Every other module's keys begin with its own name, so the naive first-segment slice is accidentally right for thirteen of fourteen — the exact condition under which a wrong implementation survives review. Home is the only module that administers namespaces beyond its own, and it is broken in three visible ways.

Solution

Keep the shared vocabulary, delete the other four, and move the never-delegate bar out of the grant paths into permission resolution — so the unsafe state becomes unrepresentable rather than guarded.

Already spec'd, not yet built. docs/specs/2026-08-23-module-namespace-seam.md is complete — 47 user stories, implementation and testing decisions, out-of-scope list. Its own baseline records the proof: one failing backend spec out of 4,374, and that failure is the organization-only chat-settings assertion this work fixes. That spec is untracked in git.

Problem

3′ · The module-namespace seam

The 2026-08-20 report's C1 has shipped, so its top recommendation is spent. The correct successor is not C2 — it is the defect C3 was groping at. One question, does this key belong to this module, has five implementations returning 27, 29, 2, 29 and 2 for the same module. The PRD is written, the failing spec is the regression net, and every other candidate on this page is cheaper to reason about once module authority has one interface.

Deepen next, before building on it

2 · The EntityReference seam

Unchanged since 2026-08-20 and still the only candidate that unblocks product work rather than paying down debt. Sharing tickets, leads and HRMS records in chat today means a fourth reference mechanism and a second controller importing another module's tables. One interface — resolve + actionsFor — with one adapter per module gives every combination and re-checks access at read time.

Revised order

  1. C3′ — module-namespace seam; PRD ready, one red spec is the proof
  2. C7 — config sweep; mechanical, parallelisable, and the count is climbing 17 reads/day

  6. C1 residue — partitioning, identity PKs, reactions, invite-token hashing, the 500-channel cap
