> **RBAC/entitlements engine + auth guards were entirely unwrapped under RLS — the single biggest gap in the rollout (2026-08-01)**: Follow-on from the two-phase-tenant-resolution pass above. Root cause: **Guards run before Interceptors** in NestJS (Middleware → Guards → Interceptors → Handler), so `TenantContextInterceptor` has not yet set the GUC when any Guard's own DB queries run — and `AccessService`/`EntitlementsService`, the entire permission/module-entitlement engine behind `PermissionGuard` and `@RequirePermission`, had **zero tenant wrapping**, relying entirely on ambient context that guards don't have. **Why this went unnoticed:** `authorize()` short-circuits to `{allow:true}` for `ctx.isOrgOwner` BEFORE touching the DB — so the org owner (whoever tests the app) never exercises the broken path; the first non-owner user hitting ANY `@RequirePermission` endpoint on a cache miss would 500. Fixed by wrapping every public entry point that takes `orgId` in `runInTenantTransaction(this.db, ..., { orgId })` — `AccessService.getPermissionsVersion/resolveUserPermissions/getUserDeniedModules/setUserModuleAccess/getAccessSnapshot/membersWithPermission` and `EntitlementsService.getModuleMap/setModuleEnabled` — nested private helpers (`computeUserPermissions`, `isOrgOwner`, `resolveModuleFlags`, …) inherit automatically since they all read through the same ALS-proxied `this.db`; `runInTenantTransaction` no-ops onto an existing ambient context, so nothing changes for the many callers that already had one. **Two guards were ALSO directly broken, independent of the above:** `JwtAuthGuard.fetchOrgContext` (its `organization_members` read used no identity GUC at all, so `organization_members`'s non-raising dual-arm policy — `org_id = current_org_id_or_null() OR user_id = current_user_id_or_null()` — silently returned EMPTY rows rather than erroring, meaning any JWT missing an `orgId` claim, e.g. right after signup before token refresh, got wrongly bounced with "Organization not found"; its `subscriptions` read raised the 42501 the user saw directly). This is also the likely cause of "invitations failing during onboarding": the invite step runs right after org creation, when the session JWT often still lacks the new `orgId` claim, forcing exactly this broken fallback path. Fixed with `withIdentity` (org not yet known) then `runInTenantTransaction` (org now known) — the same two-phase shape as the public-token fixes. **`AgentTokenGuard`** (AI-agent `Bearer slos_...` tokens) had the SAME bug as the `@Public()` token flows — `agent_tokens.token_hash` is a genuine secret but was read with no context at all, crashing before signature/expiry checks ever ran; fixed with `withPublicToken` + `runInTenantTransaction`, and `agent_tokens`/`token_hash` added to migration `0384`'s token-arm list. **Two more cron discovery queries** (`chat-reply-reminders.service.ts`, `support-kb-gap.service.ts`) did the same bare cross-org `SELECT`/`selectDistinct` as the ones fixed earlier — moved to the established `forEachOrg` helper, preserving each original "only orgs matching X" pre-filter as an in-loop check (matching the `exceptions-detector.service.ts` shape) rather than changing which orgs get scanned. **Caught and reversed my own mistake:** migration `0384`'s original list included `git_connections`/`id` — a serial PK — which would have opened blanket read access to `webhook_secret` and every other column for any future unguarded query against that table, not just the one webhook handler. Removed; the git webhook now uses a new narrow SECURITY DEFINER resolver `app.resolve_git_connection_org_id` (`0387`, same shape as `0385`/`0386`) returning only `org_id`, matching the "only high-entropy secret columns get a policy arm" rule stated in `0384`'s own comments. > **Every `@Public()` token flow was dead under RLS — two-phase tenant resolution (2026-08-01)**: Follow-on from the org-creation P0 below. An audit of all 59 `@Public()` handlers found **28 affected routes across 16 controllers**: with no authenticated user, `TenantContextInterceptor` opens no tenant transaction, so 0378's `tenant_isolation` policy raised 42501 on the endpoint's **first SELECT** — before any write. Invitation accept, e-sign signing, offer accept/counter, application tracking, referrer + vendor portals, interview self-booking, portal invites, public forms/leads/NPS, surveys (collector · session · live), CSAT, feedbucket widget, whiteboard share links, KB public pages, careers, intake and the payment/support webhooks were **all** returning 500s. **Canonical fix — two-phase resolution:** `withPublicToken(db, token, fn)` (`common/tenant/with-public-token.ts`) sets ONLY `app.public_token`, the row's policy admits exactly the one row bearing that token, its `org_id` is read, then everything after re-enters through `runInTenantTransaction(..., { orgId })`. Migration `0384` adds the non-raising `app.current_public_token_or_null()` accessor + a second `USING` arm on **19 token tables**, applied from `pg_catalog` in a DO block that detects `org_id` vs `organization_id` per table and skips a bad pair with `RAISE NOTICE` rather than shipping a policy that admits nothing. `WITH CHECK` stays strict everywhere — a token can FIND an org, never write into one. **Deliberately NOT given a token arm** (guessable serial ids → would be new cross-tenant enumeration surface): `csat_surveys.id` and `survey_response_sessions.id`; the latter got the narrow SECURITY DEFINER resolver `app.resolve_survey_session_org_id` (`0386`) returning only `org_id`, as did public intake's `projects.id` (`app.resolve_project_org_id`, `0385`) — a `projects` policy arm would have exposed every column of every project to anyone who can guess a small integer. **`job_postings` is the one status-keyed arm** (`OR status = 'OPEN'`): `/careers` is a single global unauthenticated board with no org param and `listOpenJobs()` already discloses every org's OPEN postings by design, so the arm grants nothing new while draft/closed postings stay isolated. Endpoints already carrying the org in the URL/query (roadmap, public KB, HR forms, support inbound, payment webhooks) skip phase one and just wrap. Also fixed this pass: AI credits were silently never granted after purchase (42501 swallowed by `.catch(logger.warn)`), `transitionToPastDue` never ran, billing dunning never ran (silent revenue loss), timesheet exception detection was dead, and `pnpm backfill:rbac` failed outright — cron paths moved to the existing `forEachOrg` helper. Secondary org creation needed a new primitive, `runInNewTenantTransaction`, which escapes the ambient ALS store: it runs inside the caller's existing org context, where a plain wrap would either trip the cross-org guard or nest a savepoint and silently rewrite the ambient tenant GUC for the rest of the request.
