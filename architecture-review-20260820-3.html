You asked me to validate the two specs I wrote. I tested their load-bearing claims rather than re-reading them. Both contain errors. One is mine, in the exact place you made a decision from it.

Correction — this one changes a decision you already made

The person spec says "hr_employments hangs off organization_members, so consolidating naively would have removed the ability to pay a non-member." I asserted that. It is false.

What I claimed

hr_employments → organization_members
∴ employment requires membership
∴ contractors impossible on this chain

What the catalog says

hr_employments → hr_people (person_id)
no FK to organization_members at all
hr_people.user_id is NULLABLE

A person can exist in hr_people with no login and no membership, and hold an employment. The HR chain can already represent a contractor. What it lacks is a payroll entry point keyed by person — payroll has one keyed by user and one keyed by worker, and no third. That is a missing function, not a missing capability.

What this means for your decision. You chose "keep workers as the contractor lane" partly because I said consolidating would delete a capability. It would not. That choice may still be correct — it is less work — but the reason I gave you was wrong, and you should get to re-decide on the real one.

2 · The key grammar is documented, violated 53 times, and enforced nowhere

newStrong

Before — grammar as prose

Written rule

module:resource:action — three segments
action ∈ view create update delete manage
assign export approve reject import

Actual keys

build:create · accounting:read · branch:view
chat:channels:read · calendar:write · blog:ai:use

53 keys are two-segment. read, write, use, report are not permitted actions. No validator exists.

After — grammar as a type and a test

PermissionKey — constructed, not typed by hand

`${Module}:${Resource}:${Action}`

catalog test: every key parses · action ∈ allowed set

A malformed key stops being a runtime surprise and becomes a failing build.

Problem

Two-segment keys break the assumption that a key's module is segment one and its resource segment two — which is exactly how module-scoped grants, the module catalog filter and the access screen slice the catalog. build:create is a phase-one key in this state.

Solution

Settle the grammar, migrate the 53, and add a catalog test so the next module cannot reintroduce the drift. Do this before authoring eight new catalogs, or the new ones inherit the inconsistency.

Sequencing consequence: this now sits ahead of the ladder in the PRD, not inside it. Authoring eight catalogs against an unsettled grammar would triple the migration later.

Problem

The genuine defect is not two person models — it is that payroll's eligibility has one door keyed by user and one keyed by worker, and a person recorded only in HR with no login can be employed but never paid. That is a hole the original spec missed because it was reasoning from the wrong premise.

Solution

The seam is still right; its justification changes. One resolver over a three-way subject, with payroll's two assertions becoming thin wrappers that preserve their current errors.

The good news: the spec's conclusion survives. One resolver, both models retained, no data migration. Only the reasoning needed replacing — and the corrected reasoning is stronger, because it names a real hole rather than defending a hypothetical one.
