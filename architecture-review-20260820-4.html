1 · The scoped ticket read is the most expensive query in the product

measuredStrong
  • modules/build/core/projects-tickets-read.service.ts — the DataScope clause

The clause every non-admin hits

scope !== "all"
  ? or(
      eq(tickets.assigneeId, u.userId),   // indexed (org_id, assignee_id, …)
      eq(tickets.reporterId, u.userId),   // NO INDEX EXISTS
      sql`EXISTS (SELECT 1 FROM ticket_assignees ta WHERE …)`,  // 171,431 rows
    )
  : undefined

Three different access paths joined by OR. A single index cannot satisfy an OR across three columns, one of which is unindexed and one of which is a correlated subquery. And the list sorts by created_at, which is not the trailing column of either assignee index — so even the indexed branch cannot return rows in order.

Before — measured, 200k tickets, under RLS

scoped my-work 373.2ms

14,883 buffers ≈ 116 MB read per page view

assignee-only 33.5ms

11,881 buffers — still a scan, wrong sort column

project list 1.2ms

25 buffers — the partial rank index works perfectly

After — one membership path, one index

Collapse three paths into one

ticket_participants (org_id, user_id, ticket_id)
— assignee, reporter and co-assignee
all become rows in one relation

index (org_id, user_id, created_at DESC)
→ ordered index scan, no OR, no sort

The read becomes a single indexed lookup that returns rows already in display order.

Problem

"Which tickets are mine" is expressed three different ways, so it cannot be indexed as one question. Every non-admin page view reads ~116 MB. On Neon that is billed compute, and it is the default path — not an edge case.

Solution

Make participation a single relation rather than three columns. Assignee, reporter and co-assignee become rows; the scope clause becomes one indexed predicate with the sort column in the index.

Cheaper interim fix, if the relation is too big a change: add an index on (org_id, reporter_id, created_at DESC) and one on (org_id, assignee_id, created_at DESC) so the planner can BitmapOr two indexed branches instead of scanning. That will not reach 25 buffers, but it should take a large bite out of 14,883 — and it is a migration, not a redesign. Measure it; do not assume it.

Wins

  • The hottest read stops scanning
  • Locality: one definition of "mine"
  • Database compute billed drops
  • Sort served by the index, not a sort node

Problem

HRMS works — but not through the model it was designed around. The employees endpoint reads membership and identity directly, while hr_people, hr_employments and 93 sibling tables hold nothing. Every future HR feature faces the same fork, and picks differently.

Solution

Decide which model is canonical and route every read through one seam — the Person Directory spec. With 95 empty tables there is no migration cost, and tables that stay empty after the decision are deletion candidates rather than architecture.

This measurement strengthens the Person Directory spec considerably. It was argued on reference counts; the row counts now say the same thing far more bluntly — and confirm the spec's "no data migration" claim outright.

4 · Schema files declare tables the database does not have

Worth exploring

The HR schema folder declares several attendance table families — event store, projections, correction links, evidence. The database has two attendance tables. Directory declares worker_assignment_periods and worker_reporting_lines; neither exists.

This is the same class of defect as the chat org_id failure, in the opposite direction: there, the database had a column the schema did not declare, and every insert died. Here the schema declares tables the database lacks — so any query against them fails at runtime while passing every static check.

Problem

Neither typecheck nor a module-graph tool can see this. It surfaces only as a runtime 42P01, on whichever feature touches the missing table first.

Solution

A drift check comparing declared tables against the catalog, run in CI. The org_id scanner written earlier is the same shape and can be generalised.

Problem

One module sits in its own namespace while eighteen others share public. That affects search_path, how RLS policies are applied, cross-schema foreign keys and every ad-hoc query — I hit it myself when a count returned "no such table".

Solution

Either commit to schema-per-module and move the rest, or fold Build back into public. The costly state is the current one — a single exception nobody remembers.

Marked speculative because this may be a deliberate in-progress migration rather than drift. Worth one sentence from you before anyone acts on it.

1 · Collapse the three definitions of "my tickets" into one

It is the only finding here that is both measured and on the default path. Every non-admin ticket list currently reads about 116 MB, and Build is a phase-one module with a 10M-user bar. Start with the two-index interim fix and measure — if that gets close enough, the participation relation can wait; if it does not, the measurement justifies the redesign. Either way the decision is made on numbers, not argument.

What is genuinely healthy — do not touch it

  • The project-scoped ticket list is 1.2ms and 25 buffers on 200k rows. The partial (org_id, project_id, rank) WHERE deleted_at IS NULL index is doing exactly its job.
  • Tickets carry 15 indexes, most org-leading composites with partial predicates — this table has been thought about carefully.
  • RLS failed closed with 42501 the moment I queried without the tenant GUC. The isolation is real, not nominal.
  • Both APIs return correct data. Neither module is broken.
