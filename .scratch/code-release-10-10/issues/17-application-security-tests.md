# 17 — Application security tests across session, injection and transport surfaces

**What to build:** Executable coverage for the code-level security behaviours in §11: session lifecycle attacks, the injection family, and secret handling.

**Blocked by:** None — can start immediately.

**Status:** done — all 7 boxes closed, 133 tests in `backend/test/security/appsec/`

- [x] Session fixation and replay, revoked membership, invitations, password reset, MFA/recovery, brute force and credential stuffing each have a test asserting the correct rejection.
  - Evidence: `nice -n 10 npx jest test/security/appsec --maxWorkers=2` → 7 suites, 133 tests, 0 failures. Fixation/replay in `session-fixation-replay-and-credentials.spec.ts` (21), MFA/recovery in `mfa-and-recovery-codes.spec.ts` (13), brute force/stuffing in `rate-limits-and-brute-force.spec.ts` (17). Revoked membership was already covered by `src/modules/auth/jwt-guard-revocation.spec.ts`.
  - Note: there is no password anywhere in this backend — auth is passwordless (magic link + email OTP + Google). The password-reset equivalent is the one-time magic-link/verify-email credential, and that is what is tested (single use, hashed at rest, generic refusal).
- [x] Session revocation is proven to actually log the session out. A database flag alone revokes nothing while a valid token remains; the revocation must be enforced at token-check time.
  - Evidence: `nice -n 10 npx jest test/security/appsec/session-revocation-enforced.spec.ts --maxWorkers=2` → 13 passed. Each of `revokeCurrent`/`revokeOne`/`revokeAllForUser`/`revokeAllOthers`/`enforceMaxSessions`/`publishRevocations` is driven into a shared Redis fake, then a REAL EdDSA token for that session is put through a REAL `JwtAuthGuard` and must 401. Neuter proof: deleting `this.tombstone([sessionId])` from `revokeCurrent` turned 3 tests red; restored byte-identical.
- [x] CSRF, XSS, SSRF, SQL injection, unsafe redirect, path traversal, CORS/CSP/header, payload-limit and rate-limit behaviours are each tested.
  - Evidence: `injection-surfaces.spec.ts` 35 passed (SSRF/SQLi/XSS/traversal/redirect), `transport-hardening.spec.ts` 16 passed (CORS/CSP/headers/payload), `rate-limits-and-brute-force.spec.ts` 17 passed, CSRF posture in `secrets-cookies-and-keys.spec.ts` 18 passed.
- [x] The SSRF guard is the shared one, not a new local copy — a duplicate guard written from scratch missed IPv4-mapped IPv6 loopback.
  - Evidence: `injection-surfaces.spec.ts` asserts exactly one file in `src` implements the private-address blocklist (`src/common/security/ssrf-guard.ts`), that all 14 callers import it (or the sanctioned `build/core/webhook-url-guard.ts` re-export), and exercises `::ffff:127.0.0.1` / `::ffff:7f00:1` / `::ffff:7f00:0001` / packed private + link-local forms through that shared guard. Neuter proof: breaking `mappedIpv4` so it misses the packed form turned 2 tests red; restored byte-identical.
- [x] CORS is registered before the body parser; registered after, an oversized request returns a 413 with no CORS headers and surfaces to the client as an unexplained network error.
  - Evidence: `transport-hardening.spec.ts` boots two real `NestExpressApplication`s, one in each order, POSTs an oversized body with an `Origin` header, and shows both return 413 but only the cors-first one carries `access-control-allow-origin`. That reversed-order control is a permanent built-in neuter. It also pins the order in `src/main.ts`; neuter proof: swapping the two blocks in `main.ts` turned that assertion red; restored byte-identical.
- [x] Rate-limit tiers fail closed on an unknown tier, and any multiplier does not mask the 429 the test is asserting.
  - Evidence: `rate-limits-and-brute-force.spec.ts` 17 passed. Unknown/typo'd tiers deny at both the service and the guard; every one of the ~60 literal tiers used anywhere in `src` resolves through `effectiveRateLimit`; a TRAP test shows that exhausting the DECLARED limit (5) never 429s under `NODE_ENV=test` because `DEV_LIMIT_MULTIPLIER` is 10, and every flood test drives `effectiveRateLimit(tier)` instead. Neuter proof: making the unknown tier return `allowed: true` turned 3 tests red; restored byte-identical.
- [x] Secret and PII redaction, secure cookies, generic authentication failures and key-rotation behaviour are verified.
  - Evidence: `secrets-cookies-and-keys.spec.ts` 18 passed — redaction of credential-bearing fields with a non-sensitive control, no hard-coded secrets in `src`, env validation refusing a short secret, rotation overlap + retirement proven through the REAL `JwtAuthGuard`, and a regression test for the JWKS private-key leak found and fixed this session. Generic auth failures in `session-fixation-replay-and-credentials.spec.ts`: unknown user / wrong code / no live code / disabled account / deleted account produce ONE distinct response. Cookies: the API sets none and the guard never reads one, so there is no ambient credential to secure or to ride cross-site — that is the honest form of this requirement for a Bearer-only API.
