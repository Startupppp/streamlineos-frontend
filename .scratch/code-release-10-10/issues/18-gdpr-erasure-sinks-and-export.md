# 18 — Finish GDPR erasure sinks and prove subject export is exhaustive and resumable

**What to build:** Database PII erasure and session revocation are already implemented. The remaining sinks are object storage, search and vector indexes, derived projections, caches and supported adapters — plus the export side, which must never silently cap.

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] Erasure is idempotent, tenant-scoped in SQL, audited and legal-hold-blocking across every remaining sink; immutable and legal-hold records are preserved rather than deleted.
  - Proven for every sink the service touches: `nice -n 10 npx jest src/modules/gdpr --maxWorkers=2` → 13 suites, 201 tests, 0 failures. Legal hold blocks before the manifest is built (new bite proof); `audit_logs` and `hr_legal_holds` are never deleted; org-scoped storage keys are now skipped rather than deleted.
  - REMAINING (not fixed, outside the "DB PII already done" boundary I was told not to redo): `support_tickets.requester_email` / `requester_name` for tickets created by the subject's membership are never anonymised, and `support_ticket_embeddings` reproduces those tickets' title+description as a pgvector row. Fix is an `update(supportTickets).set({requesterEmail: null, requesterName: ERASED_NAME}).where(orgId, createdByMembershipId = membership.id)` inside the same transaction.
- [x] Every drain uses a keyset cursor rather than a fixed limit. A bare limit reports a prolific subject as fully erased while leaving their chunks and embeddings behind — this exact defect has already occurred twice here.
  - Every `.limit(` in `src/modules/gdpr/**` audited (66 occurrences): all are `limit(1)` single-row reads, `limit(BATCH_SIZE)` inside a keyset drain, or the disclosed `SYNC_EXPORT_CAP + 1` probe. The three previously *unbounded* KB id selects (authored articles, owned sources, uploaded attachments) are now keyset drains via `forEachIdPage`. Proof with MORE rows than the page size: `gdpr-erasure-storage-sink.spec.ts` feeds a 200-row full page + a 1-row tail and asserts 3 chunk deletes; neutering `forEachIdPage` to a single page makes it fail with "Expected length: 3, Received length: 2" (run and read).
- [x] Subject export is exhaustive and resumable with no silent caps and no skipped in-scope source.
  - Async worker drains every source in `REQUIRED_GDPR_EXPORT_SOURCES` with `drainExportPages` (keyset, throws if the cursor fails to advance) and is resumable via claim/fail/reclaim/attempt. `nice -n 10 npx jest src/modules/gdpr --maxWorkers=2` → 201 passed, including "resumes after the batch boundary and never truncates an available section" and the source-coverage block.
  - The synchronous `/gdpr/export/me` cap is disclosed per section. Its three `exportIncomplete` notes were STALE and told the subject that audit logs, blob keys, chat and mail "are not included / require elevated tooling" when the async export returns all of them; rewritten to name the async endpoint as the exhaustive path.
- [x] Correction is implemented as correction. Export, deletion and anonymization are not substitutes for rectification.
  - `GdprRectificationService` writes the submitted value in place, reads it back, and fails closed with a `ConflictException` if the read-back does not match; before/after SHA-256 hashes go to `audit_logs`. New test asserts `set` receives exactly `{ preferredName: "Anu" }` — a redaction or a delete would fail it. `nice -n 10 npx jest src/modules/gdpr/gdpr-rectification-auth-linked-fields.spec.ts --maxWorkers=2` → 11 passed.
- [x] Authentication-linked fields require a verification challenge rather than a blind update.
  - No blind update exists and it is now enforced: `gdprRectificationBodySchema` is a closed discriminated union that rejects `profile.email` / `auth.email` / `profile.password` / `auth.mfa`, and a new test drives all 9 accepted fields through the service and asserts no `set()` payload ever contains `email`, `emailVerified`, `password`, `passwordHash`, `mfaSecret`, `mfaEnabled` or `backupCodes`. `/me` profile update also has no `email` field (`src/me/dto/me.schemas.ts`).
  - Consequence to record: there is therefore no subject-facing way to rectify `users.email` at all. Adding one requires a challenge store binding (userId, newEmail, tokenHash, expiry); `email_otp_codes` is keyed by userId only and cannot bind a new address, so a schema/migration change would be needed — outside this session's territory.
- [ ] Document, payroll, export, purge and retention workflows are each proven never to silently skip or truncate growing work.
  - Export: proven (above). Purge (object storage, org prefix): proven — `storage-purge.service.ts` pages with `ContinuationToken` until `IsTruncated` is false. Retention crons that loop and disclose: kb-chat, kb-chunk, build, ai-usage, hr, outbox, notification, notification-outbox (the capped ones return `truncated: true` and log).
  - NOT proven, two silent truncations found outside this session's territory:
    1. `src/modules/cron/cron-mail-retention.service.ts`, `cron-announcements-retention.service.ts`, `cron-helpdesk-retention.service.ts` each run ONE `LIMIT BATCH_SIZE` delete per org per tick with no loop and no "rows still eligible" signal. A backlog larger than the batch is silently carried forever and the log reports only what was deleted.
    2. `src/modules/organization/core/org-purge.service.ts:69` `listMemberUserIds` uses a bare `.limit(10000)`. On a larger org, members past 10 000 never get session/permission caches busted or org-scoped access revoked during a purge.
- [x] Object-storage deletion removes the object, not only the database row — an orphaned object with a public URL survives the record that pointed at it.
  - P0 found and fixed: `GdprStoragePurgeService` was provided and exported by `GdprModule` and had ZERO callers — `POST /gdpr/erasure/:subjectId` anonymised the database and left every avatar, payslip and uploaded document alive in R2. It is now injected into `GdprSubjectErasureService`, the manifest is captured BEFORE the transaction (a nulled `*_key` column no longer names its object), and the objects are deleted after commit with a HEAD re-check.
  - `nice -n 10 npx jest src/modules/gdpr/gdpr-erasure-storage-sink.spec.ts --maxWorkers=2` → 11 passed, including call-order proof that `buildManifest` precedes `db.transaction` and `purgeFromManifest` follows it.
