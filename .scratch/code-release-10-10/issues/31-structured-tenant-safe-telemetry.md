# 31 — Structured, redacted, tenant-safe logs, metrics and traces

**What to build:** One user intent is traceable through HTTP, database, cache, provider adapters, outbox publication, queue and event consumers, cron jobs and AI streams — without any of it logging something that must not be logged.

**Blocked by:** None — can start immediately.

**Status:** done — all eight PRD §9 boundaries propagate; three module-owned durable queues are routed to their owners (see the last sub-bullet of box 1)

- [x] Trace context propagates across every named boundary, correlating asynchronous work back to the originating intent.
  - All eight enumerated and verified against current source, not the prior report. **HTTP** — `common/http/correlation-id.middleware.ts` (global `app.use`, ahead of routing) sanitises an inbound `x-correlation-id`/`x-request-id` or mints one, joins an inbound `traceparent` rather than replacing it, echoes both back, and opens the request span *inside* the observability context. **Database** — `db/query-telemetry.ts` (`db.query.execute`, `db.guc.setup`) and `db/pool-telemetry.ts` (`db.pool.wait`); `startSpan` captures the context at open time, so a span ending after the async scope is torn down still carries the id. **Cache** — `common/cache/cache.service.ts` `withSpan(seam: cache.roundtrip)`. **Provider** — `common/outbound/call-provider.ts` (one span per attempt + `outboundTraceHeaders()`), `common/http/outbound-request.ts`, and `common/outbound/safe-webhook-transport.ts` (**was the gap; fixed here**). **Outbox** — `OutboxWriter.emit` defaults the id from the ambient context, `OutboxPublisherService` restores it from the row. **Queue/event consumers** — the workflow relay restores it, and the workflow drain now does too (**was the gap; fixed here**). **Cron** — every cron entry point is an HTTP controller under `src/modules/cron/`, so the middleware covers it, and `common/tenant/for-each-org.ts` opens a per-organisation context carrying the trigger's id. **AI streams** — closed by session S3 (ticket 12) in `modules/ai/core/telemetry/ai-correlation.ts`: `resolveAiCorrelationId()` now reads `getObservabilityContext()?.correlationId` and `AiCallMetrics.begin` opens `ai.gateway.call` from it. Verified in source; the box's previously-blocking `randomUUID()` at seven gateway entry points is gone.
  - **P1 fixed — the workflow drain executed every run under the cron tick's id.** `workflow_runs.correlation_id` was written by `startRun` and named in **no projection that read a run back**: `claimDueRuns`' `RETURNING` list omitted it, `RunRecord` had no field for it, and `WorkflowRunnerService.drain` inherited whatever context `/cron/workflow-tick` was running under. Exactly the failure the checkbox describes — the id rode on the persisted row and the consumer minted a new one. `boundDrain()`, whose comment claimed the relay used it for this purpose, had **zero callers**; deleted.
  - **P1 fixed — the DNS-pinned webhook transport sent no trace context.** `postSafeWebhook` is the one outbound path that cannot use `outboundRequest` (it pins DNS to the SSRF guard's resolved addresses, which `fetch` cannot express) and it reimplemented the omission with the transport: no `traceparent`, no `x-correlation-id`, no span. Now merged in without ever overwriting a header the caller signed, inside a `provider.webhook` span whose name deliberately excludes the customer's host.
  - Both halves of every hop now go through one seam, `common/observability/async-hop.ts` — `correlationIdToPersist()` for the producer, `runInRestoredContext()` for the consumer — and the publisher, the relay and the drain were all refactored onto it. `randomUUID()` now appears exactly once across all three consumers, inside the helper.
