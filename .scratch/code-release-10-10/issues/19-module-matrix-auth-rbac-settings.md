# 19 — Module release matrix for authentication/identity/organization, RBAC and Settings

**What to build:** The §10 inventory-and-verdict pass applied to the three access-governance modules, plus their specific §10.1, §10.2 and §10.4 criteria.

**Blocked by:** 14.

**Status:** audited — 3 of 7 closed; full report at `reports/19-auth-rbac-settings.md`

- [x] Each module's backend folders, controllers, implementations, DTO/Zod schemas, database schema files, migrations, workers, cache keys, event consumers, frontend routes, components, hooks, query keys, tests, fixtures and scripts are inventoried and classified KEEP/REFACTOR/REMOVE with the concrete failure named.
  - Evidence: 243 backend files (auth 19, rbac 88, organization 120, settings 16) + ~90 FE `features/settings/**` files + 24 FE global settings routes + `hooks/api/access*` classified in report §1, every non-KEEP naming its failure. Verified against source, not the PRD.
- [x] Membership and session reads are bounded and indexed; session, effective-access and organization caches invalidate immediately on change.
  - Evidence: `pnpm -s check:tenant-indexes` → exit 0, **745/745** tenant tables with a leading tenant index. Two invalidation defects found and fixed (`updateFeatureFlag` left `org:settings`/`org:profile` stale; `updateMemberRole` + `updateUserRole` left `user:session:<id>` stale for the 60s TTL). `jest settings-member-role-authority.spec.ts` → **3/3**; bite-proof: invalidation stripped → **1 failed / 3**.
- [ ] Role, grant and module-access CRUD has strict Zod contracts, stable OpenAPI, idempotent mutations and exhaustive owner/descendant protection.
  - Strict Zod ✅ (gap: nested automation `config` objects, `createHrAnnouncementSchema`). Owner/descendant protection ✅ (`assertTargetNotOwner`, `assertNotLastStructuralAdmin`, `assertPermissionsGrantable` billing bar, `isImmutableSystemRole`, `assertOwnerOnly`).
  - **Idempotent mutations: FAIL.** 118 controllers repo-wide use `@Idempotent`; auth + rbac + settings have **zero**, organization has one. Every role create, grant write, group-role assignment, template materialisation and the workspace-onboarding bulk generate is replayable.
  - BLOCKED: stable OpenAPI cannot be verified here — `main.ts` builds no document outside development. Closest proof run: `check:route-classification` → exit 0, 3602 handlers, **0 undeclared**.
- [ ] Effective-permission resolution is batched and cached; scope expansion is bounded; indexes cover subject, role, permission, module and tenant paths.
  - Batched + cached ✅ (`access-resolution-cost.spec.ts` measures pooled-connection borrows cold vs warm and asserts a version bump forces a re-read). Subject/role/module/tenant indexes ✅.
  - **Scope expansion bounded: FAIL.** `access-permission.resolver.ts:283-297` reads role grants with an unordered bare `.limit(500)`. The 14 module-admin rungs sum to **564** keys (hr 135, crm 82, build 75, accounting 73, inventory 49, …), so a member holding ~9 rungs silently and non-deterministically loses permissions.
  - **Permission-path index: FAIL.** `role_permission_grants` has no index leading with `permission_key`; four live queries filter on it.
  - Not fixed: `src/modules/access/**` is outside this ticket's territory. Handed to that owner.
- [ ] Global settings hold organization configuration and access governance only. Module-owned surfaces — custom fields, automations, integrations, data hub — live in their own module's settings, and operational work is not in Settings at all.
  - **Frontend: PASS.** All 24 global `/settings/*` routes are org config or access governance; custom fields / automations / integrations / import-export exist only in module trees; workforce at `/directory/workers`, payroll admin at `/payroll/*`, neither reachable from `/settings/*`.
  - **Backend: FAIL.** `SettingsController` still owns 14 of 23 routes as module surfaces (`/settings/custom-fields`, `/settings/automations`, `/settings/integrations/git`, `/settings/ai-usage`), and the module screens call them. Their gating keys are held by OWNER and ORG_ADMIN only — verified against the live catalog — so **a CRM/HR/SUPPORT/ACCOUNTING module admin gets a 403 on their own module's custom-fields and automations screens.** Six module settings trees affected.
  - Not fixed: widening a role rung is a product decision and needs a backfill migration; both out of territory.
- [x] Workspace and onboarding gates, organization-switch state, query-key tenant isolation and auth error states are covered by allow/deny/cross-tenant tests.
  - Evidence: FE `jest lib/query-scope-isolation lib/prefetch/access lib/wizard-gate lib/membership-lifecycle-route hooks/api/access` → **8 suites / 44 tests passed**. BE `jest src/modules/organization` → **57 suites / 393 tests passed**, including 14 tenant-isolation specs and `org-switch-revalidation.spec.ts` (asserts `userSession` + `accessVersion` invalidation on switch). Query-key isolation is structural: `QueryProvider` remounts a new `QueryClient` keyed on `authenticated:<orgId>:<userId>`.
- [ ] A permission-key addition to a role template is accompanied by a backfill migration, or it is inert for every organization that already exists.
  - **FAIL, and the repo's own gate proves it.** `jest src/modules/rbac/__tests__/backfill-slugs-exist.spec.ts` → **1 failed / 5 passed**, offender `0990_support_template_grant_backfill.sql: CUSTOMER_SUPPORT`.
  - Migration `0990` filters `is_system = true AND slug = 'CUSTOMER_SUPPORT'`. `CUSTOMER_SUPPORT` is only ever created by `RoleSeedService` with `isSystem: false`; `seedSystemRolesForOrg` mints only `ORG_ADMIN`/`MEMBER`/`<MOD>_MODULE_*`. **The predicate matches zero rows in every organisation.** Correction to the brief: `access_versions` is not bumped either — the second statement re-uses the same dead predicate. The rollback inherits it too.
  - Second, structural failure: `role_permission_grants.permission_key` has an FK to `permissions.name`, and `permissions` is filled by `PermissionCatalogSyncService.onModuleInit` — at **boot**, after `db:migrate`. So **a migration can never backfill a grant for a key added in the same release.** Every future template widening inherits this.
  - Not fixed: `BE/migrations/**` is out of territory. Do NOT add `0990` to `KNOWN_INERT_BACKFILLS` — that list carries a "must not grow" contract and suppressing it hides the bug. Repair direction in report §0.
