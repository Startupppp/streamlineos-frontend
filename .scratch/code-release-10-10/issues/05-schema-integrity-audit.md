# 05 — Audit primary keys, tenant uniqueness, foreign-key indexes and column semantics

**What to build:** A schema-wide audit covering primary-key strategy, tenant-scoped uniqueness, foreign-key indexes, named constraints, referential actions, check constraints, money units, timestamps and audit columns — with a verdict per finding rather than a list of observations.

**Blocked by:** None — can start immediately.

**Status:** audit complete — report at `.scratch/code-release-10-10/reports/05-schema-audit.md`. Execution belongs to tickets 06 and 08; this ticket edited no schema file and wrote no migration.

- [x] Every tenant-owned relationship uses the canonical composite organization-scoped key.
  - Evidence: `drizzle-kit export --sql` → 872 tables / 2340 FKs parsed; **19 of 1873 in-scope FKs carry no tenant column, 16 of them genuine gaps**. `node src/scripts/check-tenant-relationships.mjs --static-only` reports `Actionable 0` — two parser defects explain the gap (`CRM_TABLE_NAMES` wrongly lists `credit_notes`/`vendor_credits`/`enterprise_quotes`; the inline regex cannot match `(): AnyPgColumn =>`, 15 declarations). Findings P1-4, P1-5.
- [x] Every foreign key has a supporting index; every constraint is explicitly named.
  - Evidence: **344 of 1873 in-scope FKs have no index leading with any of their own columns** (284 → `users`, 7 → `organizations`, 53 others); 434 more are indexed but not as an ordered prefix. **1034 FKs are drizzle auto-named, 28 of those exceed 63 bytes** and are silently truncated by Postgres — proven on PostgreSQL 18.4 (`NOTICE: identifier … will be truncated`, `pg_constraint.conname` length 63). Zero truncation collisions today. Findings P2-8, P2-9.
- [x] Referential actions are correct per relationship. A composite `SET NULL` needs an explicit column list, and applying one blindly across composite foreign keys produces `23502` on any non-nullable member — filter on `attnotnull` first.
  - Evidence: replayed all 637 journalled migrations in order → **12 residual `SET NULL` foreign keys that can only raise `23502`**. Seven composite-with-no-column-list (`invitations` + 6 `hr_*`, all added *after* the `0770` sweep by `0923`/`0927`), four single-column on `NOT NULL` columns, and one — `support_tickets.fk_support_tickets_created_actor` — where the column list itself names a `NOT NULL` column because `0916:92` made it `NOT NULL` after `0865` wrote the list. `org-member-departure.service.ts:157` catches only `23503`/`23001`, so all of these surface as 500s. Both the failure and the fix proven on PostgreSQL 18.4. Findings P0-1, P0-2, P0-3, P2-10.
- [x] Money is stored in integer minor units, never floating point.
  - Evidence: **only 2 of 238 in-scope money columns use floating point** and both are internal capacity telemetry (`cell_capacity_measurements`); no `real`/`double precision` exists in accounting, payroll or billing. But two representations coexist — 95 integer minor-unit columns (billing, consistent) and 143 `numeric`/`decimal` across 11 precision variants (accounting `numeric(18,4)`, payroll mixed) — and the `numeric` values are read as **strings** and summed with `Number()`/`parseFloat()` in 20+ accounting and payroll sites including the trial balance. Finding P2-12; `journal_lines` also has **zero check constraints**, finding P3-13.
- [x] Timestamps and audit columns are consistent and timezone-correct.
  - Evidence: **1388 of 1607 in-scope timestamp columns are `timestamp without time zone`** (219 `timestamptz`; 28 tables mix both), including 53 expiry/lock/schedule columns. Proven with the project's own `postgres` driver on PostgreSQL 18.4: writing `2026-09-02T12:00:00.000Z` from a `TZ=UTC` process to a session whose `TimeZone` is `Asia/Kolkata` reads back as `2026-09-02T17:30:00.000Z` — a silent 5h30m shift; `timestamptz` round-trips correctly in both configurations. Neither `pool.config.ts` nor the `Dockerfile` pins a timezone. Audit columns are otherwise sound: 0 of 598 `created_at` and 0 of 362 `updated_at` columns lack a default. Findings P2-11, P3-15.
- [x] Findings are recorded with the concrete failure each one prevents, not as style preferences.
  - Evidence: 16 findings in `reports/05-schema-audit.md`, each with table, constraint/column, current state, KEEP/REFACTOR/REMOVE verdict, the named failure and the effort. A "things that turned out fine" section records the negative results (RESTRICT FKs do **not** block org purge — proven; composite tenant-FK coverage has substantially landed; audit-column defaults are uniform) so tickets 06/08 do not re-litigate them.
